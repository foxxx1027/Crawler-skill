# 检测对抗分诊

## R — 原文 (Reading)

> 所谓的反调试笔者的理解是，只要影响正常调试的都属于反调试，包括压缩混淆加密，以及本节内容中的无限debugger、控制台状态检测、蜜罐和内存爆破。
>
> — 李玺, 第3章 3.11 常见反调试, PAGE 115

---

## I — 方法论骨架 (Interpretation)

1. 先接受前提：这不是 bug，是**对抗**。调不动通常意味着对方正在检测某个信号，而不是你的工具坏了。
2. 把"反调试"放宽到"一切让你调不动的东西"：无限断点、控制台被禁、页面卡死/内存爆破、混淆、蜜罐，都属于同一类问题，先归类再谈解法。
3. 分诊的核心动作只有一步：把现象**翻译成一个具体信号**——断点是否存在、控制台是否打开、进程名、调试端口、调试函数返回值、代码执行时间差、自动化框架属性、Root/su 痕迹、注入框架特征。
4. 解法按**侵入性**排序：改工具配置（条件断点、禁用此处断点、换浏览器、改进程名/端口）→ 替换或重写目标代码（本地覆盖、中间人替换、重写定时任务）→ 改运行时（Hook 让检测函数返回假值、持久化注入）→ 改客户端本体（重打包，成本与副作用最大）。
5. 一次只动一个信号。把一整套"过检测"工具全堆上去，会引入新的可检测特征，反而更容易被识别。
6. 绕过有**有效期**：检测随对方版本迭代，所以策略是"设投入上限 + 准备备选载体"，而不是无限修补。
7. 停的标准是"够用"：能稳定拿到参数或数据就停，不追求永久干净的环境。

## A1 — 书中的应用 (Past Application)

### 案例 1: 网页无限 debugger 与控制台检测
- **问题**: 打开控制台查看请求就被断在一串代码处，反复断点；有的站点按 F12 打不开，有的打开就跳走，有的格式化代码后浏览器直接卡死。
- **方法论的使用**: 先按现象分型，再按侵入性给出对应手段——加条件断点、禁用此处断点（前两级只对静态 `debugger` 有效）；对定时器型的无限断点只能走"本地保存 JS 后改写"或"注入脚本重写定时任务"；卡死类则用暂停按钮看调用栈定位到那一段检测代码，再用本地覆盖替换。
- **结论**: 同一现象背后可能是不同机制（静态断点 / 定时器 / 状态检测），手段要跟着机制走，不能一套通吃。
- **结果**: 逐类给出可操作方案，并明确"方案一、二并不能应对所有场景"（案例已过期，仅演示流程）。

### 案例 2: 自动化框架被识别（webdriver）
- **问题**: 网站用 JS 检测自动化框架的特征属性，用来挡住 Selenium。
- **方法论的使用**: 先确认对方查的是哪个属性，再逐版本换招：早期用启动参数隐藏自动化提示；浏览器修复该问题后，改为在页面加载前覆盖属性；再失效时改用启动配置隐藏自动化特征；仍不行就换浏览器/换驱动。
- **结论**: 这不是"一次配置永久有效"的问题，而是**版本博弈**——对方的修复会让上一招失效。
- **结果**: 作者记录了从旧版本到新版本连续失效与替换的过程，并给出"换浏览器"作为兜底（案例已过期，仅演示流程）。

### 案例 3: 某监管 App 的 Root 检测
- **问题**: App 启动即检测设备是否 Root，不通过就进不去。
- **方法论的使用**: 先静态搜 `su`（因为多数 Root 检测基于 su），得到若干候选；逐个调试排除，发现名字最像的那个并不是真正负责检测的函数；真正的方法是把系统目录遍历一遍、发现 su 痕迹就返回真。
- **结论**: 信号是"su 痕迹"，对应动作是让该检测方法返回假值，而不是去删 su 或换设备。
- **结果**: Hook 后进入主界面；作者补充：非 spawn 方式注入时，必须在注入后重开 App 才生效（案例已过期，仅演示流程）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 打开开发者工具就无限断点、控制台打不开、格式化后浏览器卡死。
2. 注入/附加进程时 App 直接退出、报"找不到进程"或无法启动。
3. 自动化脚本一跑就被识别（页面提示异常、返回空、直接封），手动浏览器却正常。
4. App 检测 Root、检测模拟器、检测注入框架，过不去就闪退。
5. 已经套了一堆"过检测"工具，结果比之前更容易被识别。

### 语言信号 (用户的话里出现这些就应激活)

- "无限 debugger / 一开控制台就断 / F12 打不开 / 控制台被禁"
- "attach 就退出 / 附加不上 / 双进程 / 检测到调试器"
- "webdriver 被检测 / 自动化被识别 / 无头浏览器被拦"
- "Root 检测 / 模拟器检测 / 反注入 / 反调试"
- "anti-debug / anti-bot detection / debugger detection / frida detected"

### 与相邻 skill 的区分

- 与 `captcha-cost-routing` 的区别: 本 skill 处理"调试器/自动化被识别"（要不要改信号、改哪个信号）；那条处理"人机验证要不要过、花多少钱过"。二者现象都表现为"被拦住"，但原因与解法完全不同。
- 与 `capture-failure-triage` 的区别: 那条解决"请求根本看不到"（代理、证书、通道）；本 skill 解决"看得到但调不动"。
- 与 `android-param-locate` 的区别: 那条是"找到代码"，本 skill 是"让调试/注入能进行下去"；前者可能因为后者卡住而无法开始。
- 与 `js-env-patch-loop` 的区别: 那条是补运行环境让源码跑通；本 skill 是让"调试过程"不被中断，对象是检测逻辑本身。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **现象归档**
   - 用一句话写清"什么动作触发什么反应"（打开控制台 → 断点；附加 → 进程消失；访问 → 返回异常页）。
   - 完成标准: 现象可复现，且触发动作单一。

2. **信号归因**
   - 列出 1–3 个候选信号，并为每个候选写一个"只改这一个变量就能验证"的检查方式。
   - 完成标准: 候选数量 ≤3，且每条都有可观察的判别依据（不是猜测）。

3. **按侵入性阶梯处置**
   - 从最低一级开始（工具配置），逐级向上（替换代码 → 改运行时返回值 → 改客户端本体），每级只改一处。
   - 完成标准: 每级都记录"改了什么、行为有什么变化"；未验证效果前不叠加下一级。
   - 判停条件: 若出现**新的**异常（原本能用的功能失效、出现新的拦截），立即停止加码并回到第 2 步重新归因。

4. **设定投入上限与备选**
   - 在开始前写下时间/次数上限，以及备选载体（换端、换更简单的载体、降低频次、走官方接口）。
   - 完成标准: 上限与备选是具体可执行的，不是"再看情况"。
   - 判停条件: 到达上限仍未打通 → 执行备选，不再继续修补。

5. **收尾与有效期登记**
   - 拿到目标数据后停止，并登记"这次绕过依赖对方的哪个版本/哪次更新"。
   - 完成标准: 有一条可复核的失效触发条件（例如对方前端/客户端版本变化后需重验），而不是"应该没问题"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **根本抓不到包**：先解决通道问题（代理/证书/协议），与本 skill 无关。
- **卡在验证码**：那是人机验证的成本问题，走 `captcha-cost-routing`。
- **只是代码混淆读不懂**：混淆提高阅读成本但不改变执行语义；先问"能不能跑起来"，再谈反混淆，且这与"被检测"是两件事。
- **没有授权或目标非自有**：不属于本 skill 的适用场景。
- **一上来就想"全套过检测"**：这正是作者警告的反模式，会引入新的可检测特征。

### 作者在书中警告的失败模式

- 把某一种解法当成万能：书中明说部分方案"并不能应对所有场景"，定时器型必须改代码（PAGE 115）。
- 认为绕过是一次性配置：同一检测在浏览器/系统版本更新后失效，需要继续换招（PAGE 132）。
- 只改表象不改信号：例如没找到真正负责检测的方法就 Hook"名字最像"的那个，结果无效（PAGE 345）。
- 注入方式与生效时机不匹配：非 spawn 注入不重开 App 就不生效（PAGE 346）。

### 作者的盲点 / 时代局限

- **版本强绑定**：书中的应对集中在自动化框架属性、控制台状态、进程名/端口、Root 痕迹等"老一代"信号；这些手段在 TLS/JA3 指纹、设备指纹、云端行为模型、动态混淆（如瑞数类）面前收益快速衰减。
- **重招式轻验证**：大量篇幅在"怎么绕"，缺少"如何判定绕过已彻底生效""如何量化成功率与失效概率"的判定环节。
- **宿命论倾向**：作者有"逆向工作本身就很看运气"的表述，容易让读者把成功率当成不可管理变量，而不是可量化的工程指标。
- **立场单一**：只从采集方视角写，不分析对方为何这样设计（风控成本、业务损失、黑产治理），因此会低估对方的迭代速度。

### 容易混淆的邻近方法论

- `captcha-cost-routing`（人机验证的成本分路）与本 skill 常被混为一谈：两者的共同点只是"被拦住"，决策变量完全不同（前者是钱与频次，后者是信号与侵入性）。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
