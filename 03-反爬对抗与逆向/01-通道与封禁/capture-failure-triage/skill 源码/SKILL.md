# 抓不到包的分诊

## R — 原文 (Reading)

> 现象：charles 抓不到包，但Wireshark、HttpAnalyzor 可以抓到包。此时可以使用postern、drony 将移动设备的请求直接转发到抓包软件，相当于抓Android 系统的包。
>
> — 李玺, 第8章 8.2「不走代理」, PAGE 278

---

## I — 方法论骨架 (Interpretation)

"抓不到包"不是一种失败，而是几种互不相同的通道问题，解法彼此冲突。作者的做法是先记录失败现象，再让现象反推通道。

代理装了、证书也装了，抓包工具里却完全没有请求，而且开不开代理 App 都正常加载——这说明请求根本没进系统代理，此时要看第二通道（Wireshark/tcpdump）有没有流量。第二通道有、抓包工具空，"不走代理"基本成立。

有请求但返回网络错误、拿不到数据，多半是客户端只信任内置证书（单向 pinning）；若明确提示"未发送客户端证书"，那是双向认证。两者现象相似，解法相反：前者要绕过校验，后者要把客户端证书 dump 出来装进抓包工具。

HTTP 抓包工具完全看不到包、App 却正常工作，且流量是 TCP 长连接或 UDP，就要怀疑协议层被换掉（SPDY / QUIC / 私有长连接），手段变成协议降级或直接 Hook 开关。

所以判断的顺序是：分现象 → 定通道 → 再选工具。只有当包已经可见、但字段不完整时，才轮到"参数被加密"这一支，进入逆向环节。

## A1 — 书中的应用 (Past Application)

### 案例 1：某新闻 App——把环境当成变量（案例已过期，仅演示流程）
- **问题**: 要抓某新闻 App 的列表接口，但证书信任问题很容易让整套抓包流程在第一步就断掉。
- **方法论的使用**: 作者先把环境固定下来：某新闻 7.2.7、夜神模拟器（Android 5）+ Charles、Jadx、Frida；并明确"先查壳，所幸未见明显加固，所以直接反编译"。
- **结论**: 同一 App 在不同系统版本上证书信任策略不同，抓包方案要先验环境，再谈对抗手段。
- **结果**: 通道一次通过，抓到 `/Api/news/recommendList` 接口，直接进入参数分析（第9章 9.1，PAGE 284）。

### 案例 2：阿里系 App 的 SPDY——不是证书问题（案例已过期，仅演示流程）
- **问题**: 用 HTTP 抓包工具完全捕获不到数据，继续调证书没有意义。
- **方法论的使用**: 按"HTTP 工具无包、App 正常"判为协议层被换；不纠缠证书，转而反编译全局搜 `enableSpdy`，定位到 `mtopsdk/mtop/global/SwitchConfig` 的开关方法 `za()`，Hook 让它返回 false。
- **结论**: 让客户端退回 HTTP，抓包工具才看得见流量。
- **结果**: 改用 httpCanary 成功抓包（第8章 8.4.2，PAGE 280–281）。

### 案例 3：双向认证——要出示证书，不是绕过校验（案例已过期，仅演示流程）
- **问题**: 打开抓包工具后返回 `No required SSL certificate was sent`。
- **方法论的使用**: 按现象分诊为"服务端要求客户端身份"，去 assets / res 目录按 client、cer、pfx、p12、bks、crt 等关键词找客户端证书；若有密码，再回代码里找密钥。
- **结论**: 双向认证的解法与单向 pinning 相反——要把证书导入抓包工具；找不到证书或密钥时，"选择其他抓包方式"。
- **结果**: 作者给出证书 dump + 导入的路径，并保留退路（第8章 8.1.2，PAGE 278）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 代理和证书都装好了，抓包工具里一条请求都没有，但 App/客户端照常能用。
2. 抓到了一部分请求，目标接口却一个都不出现；或者只有首页接口出现。
3. 一开抓包工具，App 就报网络错误，或弹出"需要客户端证书"。
4. Wireshark 能看到流量、Charles 是空白；或看到大量 UDP 443 / 长连接流量。
5. 换了模拟器、换了系统版本，现象就变了（通了或彻底不通了）。

### 语言信号 (用户的话里出现这些就应激活)

- "抓不到包 / 一条请求都没有 / empty capture / nothing shows up"
- "SSL pinning / 证书校验 / 双向认证 / client certificate / No required SSL certificate"
- "不走代理 / no proxy / Wireshark 有但 Charles 没有"
- "UDP 443 / QUIC / SPDY / 长连接 / 私有协议"
- "换了模拟器就好了 / 换系统版本就好了 / works on Android 5 only"

### 与相邻 skill 的区分

- 与 `js-param-locate-ladder` 的区别: 后者从"包已经可见、只是参数被加密"开始；本 skill 停在"让包可见"，不碰参数。
- 与 `anti-debug-triage` 的区别: 后者处理"调试器/自动化被识别"；本 skill 处理"流量进不了抓包工具"，两者现象都在"动不了"，但对象不同。
- 与 `reverse-cost-ladder` 的区别: 后者决定"要不要逆、逆到哪一级"；本 skill 是它的前置入口，入口没通时不应进入排序。

## E — 可执行步骤 (Execution)

1. **把"抓不到"拆成可记录的事实**
   - 完成标准: 写下四条之一——(a) 抓包工具零请求且 App 正常加载；(b) 有请求但返回网络错误；(c) 提示需要客户端证书；(d) 只有非 HTTP 流量（UDP/长连接）。

2. **开第二通道交叉验证**
   - 完成标准: Wireshark/tcpdump 在该时段能看到流量，或明确确认"连流量都没有"。

3. **按现象落到一个通道格子里**
   - 完成标准: 判定为 不走代理 / 单向证书锁定 / 双向认证 / 协议降级（长连接）/ QUIC / SPDY 之一。
   - 判停条件: 若抓包工具零请求且第二通道也没有流量 → 先怀疑设备侧根本没走代理（VPN、转发、模拟器网络模式），回到步骤 2。

4. **选手段并预写改判规则（只做判断，不写绕过配方）**
   - 完成标准: 给出一个首选手段 + 一个兜底手段，并写明"若现象变成 X 则改判为 Y"。
   - 判停条件: 做完降级后出现证书/网络错误 → 说明仍有 pinning，回到步骤 3 改判，不要继续加固降级方案。

5. **确认包"完整"后再交接**
   - 完成标准: 产出接口清单（URL、方法、全部表单/头部字段），标出可疑的 sign/token/Cookie 字段，交给参数定位环节。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已经能抓到完整请求，只是参数看不懂——问题在参数，不在通道。
- 纯网页目标、没有 App/客户端，加密发生在浏览器 JS 里——抓包代理不是瓶颈。
- 目标返回静态 HTML，抓包只用于确认结构，没有对抗面。
- 目标不在授权范围内。

### 作者在书中警告的失败模式

- JustTrustMe 一类模块"针对固定名称的特定函数"，遇到不友好的模拟器或 App 时会失效；sslunpining 相对更好用，但仍需按目标调整（PAGE 277）。
- 双向认证找不到客户端证书或密钥时，作者的建议是换抓包方式，而不是死磕（PAGE 278）。
- 工具与环境强绑定：夜神 6.8.5 + Android 7、httpCanary、Xposed 等配方照抄即失败（PAGE 279–280）。

### 作者的盲点 / 时代局限

- 全书未涉及 TLS/JA3、HTTP/2 指纹层面的识别；2023 年后大量风控在这一层判定，**抓包成功 ≠ 请求被接受**（BOOK_OVERVIEW 批判段）。
- 环境配方绑定 Android 5/7 与 Xposed/夜神；Android 8+ 已换成 LSPosed/Zygisk，证书信任策略也变了，按书照做会卡在第一步。
- 未讨论请求预算与频控：通道打通之后的大量重放本身会触发风控，书里没有"通了之后怎么用"的约束。

### 容易混淆的邻近方法论

- 通用网络排障（连通性、DNS、路由）——它解决"能不能到达"，本 skill 解决"到达了但看不见"。
- `anti-debug-triage`——对象是调试行为，不是网络通道。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
