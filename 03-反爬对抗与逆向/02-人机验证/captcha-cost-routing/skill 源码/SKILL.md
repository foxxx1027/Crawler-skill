# 验证码按频次与总成本分路

## R — 原文 (Reading)

> 第二种方式是分析滑块验证成功时所请求的接口，一般请求成功会携带滑块验证的坐标和一些加密参数，通过构造请求完成滑块验证，这种效率很高，适合处理频繁访问时的验证。
>
> — 李玺, 第10章 10.2 滑块验证码, PAGE 358

> 针对你遇到的网络爬虫来说，不太可能需要比OCR 或基于API 的验证码服务更多的验证码处理功能，不过如果你对尝试训练自己的模型感兴趣的话，首先需要找到或创建正确解码的大型验证码数据集。
>
> — Jarmul / Lawson, 第7章 7.5 验证码与机器学习, PAGE 169

## I — 方法论骨架 (Interpretation)

1. 先算账再选路。总成本 ≈ 开发成本 + 单次成本 × 预计次数；**识别率不是决策变量，总成本才是**。
2. 频次是第一分界：低频（一次性登录、每天几次）→ 自动化/人工过一次，拿到 Cookie/Token 后转协议请求；高频（每次请求都触发）→ 才值得做协议还原或自建模型。
3. 复杂度是第二分界，构成一条三级阶梯：普通图文 → 开源 OCR（必要时先做图像预处理）；复杂/新型 → 付费打码（按次计费）；自有量大且形态稳定 → 自建模型（固定成本被摊薄）。阶梯是**由便宜到贵**，不是由"先进到落后"。
4. 类型决定手段：滑块 = 缺口定位 + 轨迹模拟（自动化）或复刻验证接口（协议）；点选 = 目标检测 + 文字识别；短信 = 设备侧拦截（涉及他人身份，通常不进入方案）。
5. 会话复用是隐藏杠杆：把"每次请求都要过验证"变成"每 N 天过一次"，往往比任何识别技术都便宜，也更能绕开"服务器没有桌面环境"这类部署约束。
6. 设成本护栏：单次成本上限、总预算、通过率下限、重试上限；一旦触发就换路（降频、换端、换数据源、走官方接口）。
7. 合规分界必须写清：付费打码是**成本问题**；接码/群控/猫池涉及他人身份与隐私，是**合规问题**，不进入方案。

## A1 — 书中的应用 (Past Application)

### 案例 1: 邮箱登录的滑块（低频场景）
- **问题**: 登录表单触发滑块验证，但登录本身只发生很少几次。
- **方法论的使用**: 按"低频"分路——用浏览器自动化做行为模拟：取验证图与滑块图，用模板匹配算缺口距离（注意本地图与页面显示尺寸的比例换算、滑块起始偏移），再用动作链按住—拖动—释放完成验证。
- **结论**: 定位到"一次性通过"模型：真正要交付的不是"永远能过滑块"，而是"过一次拿到会话凭证"。
- **结果**: 通过后取得 Cookie，后续采集全部转为协议请求，不再重复过验证（案例已过期，仅演示流程）。

### 案例 2: 数美滑块（高频场景）
- **问题**: 同一类滑块如果每次访问都要过，单次成本会被次数放大。
- **方法论的使用**: 改走"协议还原"：先取验证配置接口，从下发的 SDK 脚本里提取参数名与协议版本，再注册验证码取得图片，用图像匹配算缺口距离，最后把距离、轨迹、鼠标行为等参数组装成验证请求提交。
- **结论**: 高频场景下，还原接口一次投入、后续单次成本接近零，比反复做行为模拟划算。
- **结果**: 提交后返回成功标识，验证通过；参数里多项是加密值，作者明确"JS 就不具体分析了"（案例已过期，仅演示流程）。

### 案例 3: 图文验证码的成本对照
- **问题**: 图文验证码既有开源 OCR 可解，也有付费打码可用，还有自建模型可选。
- **方法论的使用**: 按阶梯比较：开源 OCR 对简单图够用但复杂图不稳；自建（如按字符切分后训练分类器、或用训练工具产出模型再部署）前期成本近似固定、量大时摊薄；付费打码按次计费。
- **结论**: 作者在章首直接给出结论性判断——"昂贵的识别费用无法支持爬虫大规模的采集"（PAGE 347），即规模化时打码不划算。
- **结果**: 书中给出两条自建路径（轻量分类器与训练部署），并说明识别速度与样本量的关系（案例已过期，仅演示流程）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 抓取过程中开始频繁出验证码，不确定该做自动化、打码还是干脆放弃这条路。
2. 已经有方案（比如自动化过滑块），但通过率不稳、成本随量上涨，想换路。
3. 目标只在登录时出验证码，之后接口不再要，想确认"是不是过一次就够了"。
4. 服务器没有桌面环境，但目标验证码必须人工过，纠结部署方式。
5. 团队在讨论"要不要上打码平台/自建模型"，需要一份成本对照而不是技术对比。

### 语言信号 (用户的话里出现这些就应激活)

- "验证码过不去 / 滑块 / 点选 / 图文 / 缺口识别"
- "打码平台 / 识别率 / 一次多少钱 / 能不能自建模型"
- "一天要过几百次 / 每次请求都要验证 / 低频登录"
- "过一次拿 Cookie 行不行 / 会话能保多久"
- "captcha cost / slider captcha / OCR accuracy / captcha solving service"

### 与相邻 skill 的区分

- 与 `anti-debug-triage` 的区别（本 skill 必须讲清的分工）: 本 skill 管**人机验证**——决策变量是频次与钱（过不过、花多少过、要不要会话复用）；`anti-debug-triage` 管**调试器/自动化被识别**——决策变量是对方查的哪个信号与改法的侵入性。两者都表现为"被拦住"，但一个问"总成本"，一个问"改哪个信号"。
- 与 `capture-failure-triage` 的区别: 那条解决"请求看不到"；本 skill 假设请求已可见，只是被人机验证挡住。
- 与 `reverse-cost-ladder` 的区别: 那条是"参数还原"的投入排序（拦截 → 自动化 → RPC → 复写 → 脱壳）；本 skill 是同一成本逻辑在"人机验证"这个对象上的专门化。
- 与 `scraping-compliance-layering` / `scrape-preflight-and-entry-ladder` 的区别: 那两条做授权与合规的 go/no-go；本 skill 在合规通过之后才谈路线，且把"接码/群控"直接划出方案。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **量化输入（先算账）**
   - 写出：预计请求次数与时间窗、验证码触发条件（每次请求还是仅登录）、可接受单次成本、会话能复用多久。
   - 完成标准: 四个数字/条件都有明确取值；缺项就先去测，不要直接选方案。

2. **分类与定位**
   - 判定验证码类型（图文/滑块/点选/短信）与触发点（登录/提交/高频）。
   - 完成标准: 一句话说清"什么类型、在什么时机触发、每次都要还是偶尔"。

3. **先试最低成本路（会话复用优先）**
   - 先验证"过一次、拿凭证、转协议"是否成立；记录凭证有效期。
   - 完成标准: 用最小样本证明数据可用，并测出凭证的实际有效时长。
   - 判停条件: 若凭证可复用时长 ≥ 目标采集周期 → 到此为止，不再做识别技术。

4. **判断是否必须逐次通过**
   - 若验证码是每次请求都触发，进入高频路线；若否，回到第 3 步优化复用策略。
   - 完成标准: 明确"逐次通过"是事实而非假设（有抓包/日志证据）。

5. **高频路线三选一（附成本估算与放弃线）**
   - 在"协议还原 / 付费打码 / 自建模型"中选一条，写出：前期投入、单次成本、预计总成本、通过率下限、放弃线。
   - 完成标准: 总成本可算、放弃线可触发；不允许"都做一点"。

6. **工程护栏**
   - 加通过率监控、重试上限、预算熔断、失败降级（降频/换端/换数据源/走官方接口）。
   - 完成标准: 任一指标越线时系统会自动降级，而不是继续烧钱或被封。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **问题不是人机验证**：请求看不到、证书不过、参数算不出来，都不属于本 skill。
- **调试器/自动化被识别**：那是 `anti-debug-triage` 的事；把"被识别"当成"验证码"会导致选错手段（例如给一个反自动化检测去上打码平台）。
- **真实瓶颈在封号/IP/设备关联**：验证码只是表象，此时识别技术投入再多也不解决可持续性问题。
- **涉及他人身份凭证**（接码、群控、猫池）：这是合规问题，不是成本问题，不应进入任何方案。
- **未获授权的目标**：不属于本 skill 的适用场景。

### 作者在书中警告的失败模式

- 把打码当通用解：作者明说"昂贵的识别费用无法支持爬虫大规模的采集"（PAGE 347）。
- 只按类型选方案而不算频次：同一滑块，低频用自动化、高频必须走协议（PAGE 358）。
- 忽视图像尺度与页面偏移的差异，导致缺口距离算错（PAGE 359–360 的比例换算与起始偏移提示）。
- 把"能过"当成"可持续"：没有通过率与成本护栏，量一上来就崩。

### 作者的盲点 / 时代局限

- **缺少量化模型**：全书把 OCR、滑块、点选都当作"可解"，但没有"识别率—重试—成本"的量化公式，也没有通过率阈值建议（BOOK_OVERVIEW 批判段）。
- **重招式轻验证**：案例停在"返回 success / 识别结果一致"，没有讨论行为风控、设备指纹、云端模型对同一套轨迹的识别率衰减。
- **案例站点与版本强绑定**：具体站点、图片尺寸、参数名与加密方式随版本变化，配方不可复用，只能当流程演示。
- **立场盲点**：站在采集方视角，未讨论目标站点的可用性影响、授权与数据分级；对接码类灰产只作一句"不推荐"处理。

### 容易混淆的邻近方法论

- `anti-debug-triage`：管"调试器被识别"；本 skill 管"人机验证要不要过、花多少钱过"。这是 MERGE_PLAN 明确写下的分工，两个 skill 不应互相抢调用。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
