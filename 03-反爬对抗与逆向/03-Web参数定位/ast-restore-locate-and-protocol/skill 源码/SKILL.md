# 加密参数定位与协议逆向：先判值来源，再选手段

## R — 原文 (Reading)

> data字段的值有两种来源：服务器返回,该值在抓到的所有数据包中可以找到。
>
> — 李岳阳、卓斌, 第11章 11.1「协议逆向」, PAGE 224

---

## I — 方法论骨架 (Interpretation)

这套流程解决的不是"怎么读混淆代码"，而是"该不该为这个值去读代码"。

第一步永远是判来源：把目标值拿去全部抓包记录里搜。搜得到，就是服务器下发或回显，工作量落在复现上游请求、会话链与字段回填上；搜不到，才判为 JS 生成，进入逆 JS。两类错误的代价极不对称——给服务器给的值逆算法，等于凭空造一个不存在的函数。

判为 JS 生成后，定位手段按成本从低到高排：加限定符的全局搜索 → Initiator 调用栈 → XHR/fetch 断点 → 事件断点 → 条件断点插桩 → 本地覆盖或 Ajax-hook 改执行环境。每级只试一次，命中过多（经验阈值约 20 条）或零命中就换级，不在同一级扩关键词。

值还要判生命周期：换验证码（业务动作）变不变、刷新页面（会话动作）变不变。刷新即变的是会话级随机，只有业务动作才变的是交互级，两者决定要复现哪一段。

代码还原之后，搜索链并未结束：按属性字符串键逐跳上溯（data → this["$clientid"] → $strlen → getId），而不是按已经被改名掉的变量名。

最后一步是反向验证：改一个字节看服务端是否拒绝，确认它真的被校验，而不是被原样回显。

## A1 — 书中的应用 (Past Application)

### 案例 1：网易易盾滑块——data 搜不到，转调用栈
- **问题**: 滑块 POST 里的 data 是一长串，全局搜 data 命中太多，无法判断该从哪个函数进。
- **方法论的使用**: 按"命中过多即换级"放弃继续搜 data，去 Network 看该请求的 Initiator 调用栈，从最上方的请求往下点：verifyCaptcha（2178 行）→ onMouseUp（3919 行），看到 data 由轨迹采样结果拼接；再全局搜 traceData，在 3882 行 push 处断下。
- **结论**: 生成逻辑不在发送层，而在鼠标抬起回调与轨迹采样层；真正要还原的是轨迹三要素（横向位移、纵向位移、耗时）与字符异或函数。
- **结果**: 在 p 函数看到 charCodeAt 与 XOR，拿到真实轨迹即可复现 data（第2章 PAGE 48）。

### 案例 2：图片点选验证码站——先比四个参数，只逆两个
- **问题**: POST 有 clientid、data、username、password 四个参数，不知道逆向目标该收敛到哪。
- **方法论的使用**: 先做"哪些参数变了"的对比而不是先啃整份混淆脚本：password 明文未变，username 只是在原值前加了固定前缀 e5，两个都可排除。
- **结论**: 真正要还原的是 clientid 与 data；其余是常量与前缀拼接。
- **结果**: 工作量从整份混淆脚本收敛到两个字段（第5章 PAGE 84）。

### 案例 3：靶站 data——判来源、判生命周期、按属性键上溯
- **问题**: 第11章靶站的 data 看着像加密串，全量抓包里搜不到同值，刷新页面又变。
- **方法论的使用**: 先判来源：全量抓包零命中，判为 JS 生成；再做两次对照——换验证码时该值不变、刷新页面时该值改变，判定它是刷新即重新生成的会话级值，必须实时计算；还原后按属性字符串键上溯：搜 data → clientid 来自 this["$clientid"] → 搜 $clientid 的赋值（Math.random 与 Date.now 拼接）→ 搜 $strlen → 搜 getId。
- **结论**: 关键不是找某个"算法"，而是把随机源、时间源与常量逐跳定位；该值刷新即变，抓一次包写死必然失效。
- **结果**: 用还原后的脚本实时生成，与抓包值同构；两次对照实验把值的生命周期写进了交接结论（第11章 PAGE 224、PAGE 246）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 抓包里有个 32 位或 64 位字段，全局搜参数名零命中。
2. 搜 data、password、sign 命中几百条，点进去全是第三方库或同名注释。
3. 参数只在点击、滑完、切 tab 之后才出现，请求时断点里根本看不到。
4. 同一个值，刷新页面变、换验证码不变（或反过来），不知道该复现哪一段。
5. 只知道一个密文值和对应接口，连参数名都不知道。

### 语言信号 (用户的话里出现这些就应激活)

- "这个值是哪来的 / where does this value come from"
- "服务器给的还是 JS 算的 / server-generated or client-computed"
- "全局搜不到 / search returns nothing"
- "命中太多 / too many matches"
- "Initiator / 调用栈 / call stack / 从哪个请求进来的"
- "协议逆向 / protocol reversing / 上游请求 / upstream request"
- "刷新就变 / changes on refresh / 换验证码不变"
- "只知道这个值 / only have the ciphertext"
- "data 参数 / clientid / token 怎么生成的"
- "改了会不会被拒 / does the server validate it"

### 与相邻 skill 的区分

- 与 `js-param-locate-ladder` 的区别: 那套从"手上有什么信息"直接选定位手段；本 skill 前置一道"值来源判定"，先决定这个值要不要定位，并补上还原后按属性键上溯的搜索链与生命周期对照。
- 与 `sign-reproduce-acceptance` 的区别: 后者在函数已找到后验"复现值对不对"；本 skill 只到"找到生成链"为止。
- 与 `obfuscation-fingerprint-triage` 的区别: 后者判代码用了哪几层混淆；本 skill 判"这个值是否值得为它去读代码"。
- 与 `data-path-cost-ladder` 的区别: 后者按取数路径降成本（打印版、接口、浏览器）；本 skill 按值来源与定位手段降成本。
- 与 `page-owned-api-recon` 的区别: 后者找站点自己的 JSON 接口；本 skill 在接口已有时判定字段来源。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **固定样本集**
   - 完成标准: 同一次会话内至少拿到三类样本——刷新页面、换验证码、正常业务动作，能看出值在哪类动作下变化。

2. **判值来源**
   - 完成标准: 在全量抓包中搜索目标值，命中位置归入"响应体 / 请求体 / 本地生成"之一，并写明证据（第几个包、哪个字段）。
   - 判停条件: 若命中在响应体或其它响应中，跳到步骤 5，复现产生它的上游请求，不进入逆 JS。

3. **排定位手段并逐级执行**
   - 完成标准: 加限定符搜索 → Initiator 栈 → XHR/fetch 断点 → 事件断点 → 插桩 → 本地覆盖，每级只做一次，找到候选函数或记录"零命中/超阈值"。
   - 判停条件: 单级命中超过约 20 条，或连续两级无结果，直接跳到 XHR/事件断点，不再扩关键词。

4. **确认入口与出口，并验服务端是否真校验**
   - 完成标准: 有一组输入/输出样本对，且知道改一个字节后服务端是接受还是拒绝。
   - 判停条件: 服务端并不校验该值，降级为"格式复现"，不再继续逆。

5. **上溯生成链**
   - 完成标准: 拿到生成函数、输入清单、随机源与常量清单；用属性字符串键逐跳上溯，而不是用改名后的变量名。

6. **整理交接物**
   - 完成标准: 一页交接单，含值来源结论、值的生命周期、生成链、一个真实明文/密文样本对，可直接交给复现验收。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 包还没抓全、接口没摸清，连 HTTP 版本与是否走代理都没确认——先解决抓包通道，再谈定位。
- 值只是 base64、URL 编码或 JSON 转义——先肉眼比对一次，不必上断点。
- 需要决定"整套逆向值不值得做"——那是成本决策（`data-path-cost-ladder`、`reverse-cost-ladder`），不是定位。
- 目标每次访问下发不同脚本与令牌（瑞数类动态混淆），静态搜索整条阶梯失效，应换策略而不是继续换关键词。

### 作者在书中警告的失败模式

- 用通用词硬搜：搜 data 命中太多仍逐个下断点，作者明确改为查看目标资源的函数调用栈（PAGE 48）。
- 只抓一次包就断定值固定：必须用换验证码与刷新页面两组对照，确定值是会话级还是交互级（PAGE 246）。
- 只看发送层：生成逻辑常在业务回调（表单校验、鼠标抬起），栈要往下点（PAGE 48、PAGE 84）。

### 作者的盲点 / 时代局限

- 样本量 = 1：唯一端到端靶站大概率由作者自造混淆器生成，"用自己的混淆器喂自己的还原器"是闭环，不能证明对商业方案通用（BOOK_OVERVIEW 批判节）。
- 2021 年环境快照（Chrome 79、Node 12.18.2）：今天 TLS/JA3、HTTP2 指纹与设备环境采集往往先于参数加密生效，通道层要先过。
- 未讨论 sourcemap 这一更便宜的入口；也未覆盖 wasm/Rust 编译型加密与瑞数类动态混淆（PAGE 82 仅点名，全书零分析）。
- 合规与频率框架零覆盖，案例的授权状态未声明。

### 容易混淆的邻近方法论

- `js-param-locate-ladder`——按信息类型选手段，不含值来源门。
- `sign-reproduce-acceptance`——函数找到之后的复现验收。
- `obfuscation-fingerprint-triage`——判代码层数，不判值来源。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
