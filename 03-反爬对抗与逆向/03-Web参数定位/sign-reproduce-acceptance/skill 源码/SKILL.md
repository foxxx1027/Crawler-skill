# 参数复现的验收与反证协议

## R — 原文 (Reading)

> 笔者修改了URL 的部分参数后，再次请求，返回了{" sign：签名校验失败" }，可以知道sign 的生成和page、size、timestamp 这些都有关系，如图9-2 所示。
>
> — 李玺, 第9章 9.1.1「接口分析」, PAGE 285

---

## I — 方法论骨架 (Interpretation)

"还原成功"不是"跑通了一次请求"，而是两个可比对的事实：参与签名的字段集合对了，产物对得上。

第一步是反证，不是复写。固定其它参数，只改一个（page、size、timestamp 之一），如果服务端返回"签名校验失败"，说明这个字段参与签名；如果照常返回，说明无关。用失败来得到输入集合，比猜算法便宜得多，而且它是后面所有工作的输入——集合少一个，算法再对也永远失败。

第二步才是比对产物：本地算出的值与抓包值逐字符对照，一致才算还原。不一致时只有三种可能，按顺序排查：

① 字段集合漏了东西——接口路径、某个 header、一个被忽略的固定值；
② 用的是静态推导值而不是运行时值——密钥、设备值、初始化结果来自运行时；
③ 接口绑定——A 接口的签名函数套到 B 接口必然失败，因为签名原文里绑了路径或业务标识。

比对要在批量请求之前做，它是门，不是事后补验。另外要留意随机化：带 nonce、时间戳或随机 padding 的参数，逐字符比对根本不成立，此时判据换成"服务端接受 + 同输入可重复"。

## A1 — 书中的应用 (Past Application)

### 案例 1：某新闻 App——用服务端的报错反证字段集合（案例已过期，仅演示流程）
- **问题**: 接口带 `sign=9819bfa26e8e93d4378068337e259c8c`，不知道哪些字段参与签名。
- **方法论的使用**: 抓包先列出 category、timestamp、App_id、page、size；然后修改 URL 的部分参数再请求，服务端返回 `{"sign：签名校验失败"}`。
- **结论**: sign 与 page、size、timestamp 相关，参与签名的输入集合被确定下来。
- **结果**: 有了这个集合，反编译时才能读懂 `sortedMap → 按 = 拼接 → 加 app_secret → MD5` 的流程，并用 Frida Hook 验证（第9章 9.1，PAGE 285–287）。

### 案例 2：新榜榜单——跨接口套用签名函数必败（案例已过期，仅演示流程）
- **问题**: nonce 与 xyz 两个参数，调试时发现"每个接口对应的 a（`/xdnphb/***`）是不同的"。
- **方法论的使用**: 作者把接口路径本身当成签名输入的一部分，结论是"要根据不同接口进行修改"。
- **结论**: 把 A 接口的签名函数套到 B 接口的失败，不是算法错，而是"参与签名的输入集合"判断错——属于三分法里的第 ③ 类。
- **结果**: 每个接口单独维护原文模板（第3章 3.6.2，PAGE 75）。

### 案例 3：CNVD 加速乐——验收前先把现场复位（案例已过期，仅演示流程）
- **问题**: Cookie 由多次请求链式生成，带着旧 Cookie 观察，看到的永远是链条的最后一段。
- **方法论的使用**: 先在 Application 里删除现有 Cookie、刷新页面（或直接开无痕），让三次请求的生成链完整暴露：第一次 `_jsluid_s`、第二次 `_jsl_clearance_s`、第三次 `_jsl_clearance_s` 变化并请求成功。
- **结论**: 验收的前提是"现场干净"，否则比对的是被污染的状态。
- **结果**: 按三次请求链在本地模拟，补齐 `window`、`window.navigator` 后跑通（第3章 3.6.7，PAGE 82–85）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 函数找到了、也复写出来了，但本地算的值和抓包值不一样。
2. 跑通了一次，过一会儿或换台机器就失败。
3. 同一个算法套到另一个接口，服务端直接报签名错误。
4. 接口带一次性 nonce 或 timestamp，不确定它们参与不参与签名。
5. 想主动确认"到底哪些字段被签了"，而不是继续猜。

### 语言信号 (用户的话里出现这些就应激活)

- "sign 对不上 / value mismatch / 算出来不一样"
- "跑通了但 403 / works once then fails"
- "签名校验失败 / invalid signature / 签名错误"
- "哪些字段参与签名 / which params are signed"
- "nonce 是不是一次性的 / timestamp 有效期"

### 与相邻 skill 的区分

- 与 `js-param-locate-ladder` 的区别: 后者负责"找到生成代码"；本 skill 从"代码已经找到"开始。
- 与 `js-env-patch-loop` 的区别: 若本地值稳定、算法也对，但服务端仍拒绝，先怀疑"被拼进签名的环境值"，那是环境问题；本 skill 先处理字段集合与接口绑定。
- 与 `reverse-cost-ladder` 的区别: 后者是"要不要投入"，本 skill 是"投入之后如何判定做完了"。

## E — 可执行步骤 (Execution)

1. **固定现场**
   - 完成标准: 清 Cookie / 开无痕、固定一套请求头、留存一个可复现的完整请求（含响应）。

2. **做字段反证**
   - 完成标准: 对每个可疑参数单独改一次，得到"参与签名 / 不参与"两列清单。
   - 判停条件: 若改任何参数服务端都不报错 → 该接口没有签名校验或校验在别处（如 Cookie/网关），停止本流程。

3. **判定 nonce / 时间戳性质**
   - 完成标准: 同一 nonce 重放两次，记录"第二次是否被拒"，据此定为一次性或时间窗；这决定工作量级。
   - 判停条件: 若被拒且无法预测生成规则 → 先解决 nonce 生成，再回头做算法。

4. **逐字符比对**
   - 完成标准: 本地产物与抓包产物长度、字符集、逐位一致；不一致时落进三分法（字段集合 / 运行时值 / 接口绑定）之一并写明依据。

5. **稳定性验收**
   - 完成标准: 连续若干次（含跨分钟、跨接口）本地生成的值被服务端接受，并记录失败率与失败形态。

6. **交接**
   - 完成标准: 产出"参与签名的字段清单 + 算法描述 + 一组样本对（明文/密文/响应）"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没定位到生成代码——先做定位。
- 接口本来就没有签名校验，失败原因是频控、账号态或 IP——那是另一类问题。
- 对象是验证码 token 或人机校验——按成本分路，不适用本协议。
- 只想"再跑一次试试"，而不打算建立可比对的判据——这会把运气当成结论。

### 作者在书中警告的失败模式

- 跨接口复用签名函数："每个接口对应的 a 是不同的，所以要根据不同接口进行修改"（PAGE 75）。
- 用静态推导代替运行时值：`_sig` 一类参数在静态提取的密钥与运行时值不一致，本地算对必须用运行时值（第9章 9.2）。
- 作者的成功判据是"生成结果与接口数据对比无误"（PAGE 77）——这个判据对**确定性**算法成立，对 RSA PKCS1_v1_5（随机 padding）、带随机盐的签名并不成立，此时逐字符比对会误判为失败。

### 作者的盲点 / 时代局限

- BOOK_OVERVIEW 明确指出全书"重招式轻验证"：对"如何证明复现值在服务端真的通过（除了一次成功请求）""是否还有二次校验/时间窗/一次性 nonce"缺乏系统论述。本 skill 正是对这处缺口的补丁，但证据仍来自零散案例，不是作者的系统方法论。
- 未讨论字段漂移与回归成本：接口字段、签名版本变更后，原有比对样本会失效，书里只有"案例会过期"一句免责。
- 未区分"客户端校验"与"服务端二次校验"：部分目标在网关或风控层另有一层校验，本地全对仍可能被拒。

### 容易混淆的邻近方法论

- `js-env-patch-loop`——同属"本地算不对"，但归因在运行时环境而非算法输入。
- 单元测试里的 golden-sample 比对——形式相似，但这里的"golden"由对手随时更新。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
