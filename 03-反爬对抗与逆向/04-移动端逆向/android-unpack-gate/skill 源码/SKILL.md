# 查壳—代际—脱壳"够用即止"

## R — 原文 (Reading)

> 在爬虫逆向的开发中，主要的需求是分析源码中的加密参数，所以对脱壳的要求没有那么高。在反编译工具无法正常反编译或者拿不到关键代码的时候才需要去脱壳，脱壳后只要能获取关键的Dex 文件即可，不需要完美的脱壳和修复。
>
> — 李玺, 第6章 6.6 章首, PAGE 251

---

## I — 方法论骨架 (Interpretation)

1. 在采集语境里脱壳是**手段**：目标是看到生成参数的那段逻辑，不是交出一个能回编译的工程。
2. 判断"有没有壳"要走**两条通道**：① 特征表（so 库名、壳入口类）；② 产物形态（类数量、目录残缺、关键类能否搜到、多种工具是否都失败）。第二条更可靠，因为改个 so 名就能骗过第一条。
3. 把厂商名翻译成**保护机制代际**：整体加密后动态加载 → 不落地加载 → 指令抽取 → 指令替换（VMP）→ 虚拟机保护。代际决定思路和工具，品牌不决定。
4. 代际越靠后，越不能指望"一把工具 dump 全"；要做的是选对**脱壳时机**与 Hook 点，甚至接受产物不完整。
5. 时机决定完整性：先让 App 正常启动、把目标模块点全（触发类加载），必要时断网，再 dump；否则只拿到已加载的片段。
6. 产物处理是工程问题：改名成 `classes*.dex` 塞回原 APK；内存不够就按体积分批，只反编译可疑批次，并**记录已排除范围**（目标类可能分散在不同批里）。
7. 停止条件明确：能搜到并读出参数生成逻辑就停；补完所有批次仍搜不到，才转 native 分析。

## A1 — 书中的应用 (Past Application)

### 案例 1: 某资讯 App（360 加固）的 signature
- **问题**: 查壳工具报 360 加固；直接用反编译工具找不到关键代码。
- **方法论的使用**: 按代际判"需要用内存 dump"；脱壳后手动把产物改名为 `classes*.dex`，塞回原 APK 再进反编译工具；因为全部合并内存吃不消，按体积排序分两批、每批约十个。
- **结论**: 解压出的 Dex 里还有壳自身的文件，不是全部都要；目标类分散在不同批次——查找用的类在前一批，签名类在后一批。
- **结果**: 分批反编译成功定位到签名逻辑，但作者特别提示"必须记住已经排除过哪些 Dex"，否则会误判"没有这个类"（案例已过期，仅演示流程）。

### 案例 2: 某新闻 App（腾讯加固）的 sn
- **问题**: 查壳工具的特征匹配**没有命中**，看似无壳。
- **方法论的使用**: 不信单一通道，改看产物形态——反编译出来文件极少、"这明显不对"，且在产物里看到腾讯壳的入口类名。
- **结论**: 判定有壳（第二/三代）：壳入口 + 类数异常少，说明 Dex 未真正落地。
- **结果**: 断网后启动 App 并点到目标模块，dump 出多个 Dex，替换原 Dex 后重新反编译，"能看到非常多的 class 文件"（案例已过期，仅演示流程）。

### 案例 3: 查壳工具本身的局限（通用）
- **问题**: 作者给出的查壳脚本是"解压 APK、按 so 文件名匹配厂商"。
- **方法论的使用**: 把它当成第一通道，而不是结论；同时用"多工具反编译失败 / 缺失大量关键代码 / 源码里有加固特征"作为第二通道。
- **结论**: 静态文件特征"局限性很大"，改 so 名或仿造别家特征就会失效。
- **结果**: 书的结论是"掌握加固的基本概念，在反编译时结合经验判断"，即代际判断优先于品牌识别（PAGE 254–255）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 反编译出来的类只有几百个、目录结构残缺，某个业务类怎么都搜不到，但 App 在真机上跑得好好的。
2. 查壳工具输出"未发现加固/未知"，用户据此认为可以直接读代码，实际读不出东西。
3. 已确认有壳，但在工具清单里挑不出来：不知道该用内存 dump、Hook dump 还是注入框架。
4. dump 出来的 Dex 一堆，不知道哪些有用、怎么合并、合并后内存爆掉。
5. 想判断"要不要继续脱壳"——已经能看到目标方法了，还在纠结要不要"脱干净"。

### 语言信号 (用户的话里出现这些就应激活)

- "有没有壳 / 查壳 / 这是什么加固 / 第几代"
- "反编译只有几百个类 / 目录不全 / 搜不到 deviceId"
- "脱壳 / unpack / dump dex / 内存 dump / 脱不干净"
- "classes.dex 改名 / 塞回 APK / 合并 Dex / Jadx 内存不够"
- "is it packed / unpacking tool / dex dump / packer generation"

### 与相邻 skill 的区分

- 与 `android-param-locate` 的区别: 本 skill 只管"让代码变得可读"；一旦可读，定位是那条 skill 的事。产物正常时不要调用本 skill。
- 与 `native-hook-or-unidbg` 的区别: 本 skill 处理 Dex 层；若 dump 完所有 Dex 仍找不到关键类，才交给它去做 so 层黑盒调用。
- 与 `reverse-cost-ladder` 的区别: 那条讲"什么时候根本不该脱"（换载体、拦截、自动化）；本 skill 假设已经决定要脱，只解决"怎么脱、脱到什么程度"。
- 与 `anti-debug-triage` 的区别: 脱壳前后遇到的"注入就退出、运行即崩"属于检测对抗，不在本 skill 内。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **定性：先回答"需不需要脱"**
   - 用反编译工具试读，检查关键业务类是否可见、逻辑是否可读。
   - 完成标准: 明确写下"可直接分析"或"需要脱壳"。
   - 判停条件: 若可直接分析 → 结束本 skill，转 `android-param-locate`。

2. **双通道查壳**
   - 通道一：特征表（解压 APK 看 so 库名、壳入口类）；通道二：产物形态（类数量、目录残缺、多工具是否都失败）。
   - 完成标准: 两条通道各写一条结论；冲突时**以产物形态为准**，并记录冲突原因。

3. **判代际（而不是认品牌）**
   - 依据"类数多少、有无壳入口、是否整体加密、是否只有 native 桩、方法体是否为空/被抽取"推断保护机制代际。
   - 完成标准: 能说出"属于第几代 + 判断依据"，并据此选出工具类别（整体解密 dump / 内存 dump / Hook 重组 / 放弃完美还原）。

4. **定脱壳时机**
   - 规划顺序：正常启动 → 把目标模块点全（触发类加载）→ 必要时断网 → dump。
   - 完成标准: 写下时机方案，并说明"为什么这个时机能拿到完整产物"（对应哪一代的加载特征）。

5. **合并与分批反编译**
   - 产物改名 `classes*.dex` 并入原 APK；按体积排序分批；小体积壳文件可舍弃。
   - 完成标准: 列出每批包含哪些 Dex、以及**已排除范围**清单，避免把"没搜到"误判成"不存在"。

6. **停止判定**
   - 逐批检索关键类与参数生成方法。
   - 完成标准: 找到并读出参数生成逻辑 → 停；全部批次都无 → 转 `native-hook-or-unidbg`，不再追求"完整脱壳"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **反编译正常、关键类可见**：不需要脱壳，作者的立场就是"工具能反编译出关键代码就不必脱"。
- **把脱壳当成目的**：追求"能回编译、能重打包签名"的完美还原，与本 skill 的目标（读到参数生成逻辑）不同，成本会失控。
- **参数已判定在 native 层**：脱 Dex 解决不了 so，转 `native-hook-or-unidbg`。
- **未获授权的目标**：不属于本 skill 的适用场景。

### 作者在书中警告的失败模式

- 相信查壳工具的单通道结论："如果厂家修改一下so 名就无法查到了"，静态特征"局限性很大"（PAGE 254–255）。
- 直接分析带壳源码："反编译的第一步永远是查壳，最好不要去分析带壳的源代码"（PAGE 332）。
- 脱壳时机错误：不先启动、不点全模块就 dump，只能拿到部分已加载代码。
- 合并后不记录批次：目标类分散在不同 Dex，忘记排除范围会导致重复劳动或误判（PAGE 325）。

### 作者的盲点 / 时代局限

- **工具版本强绑定**：夜神 Android 5/7、Xposed 系脱壳工具、特定 Frida-Dexdump 版本、Jadx 默认内存上限——这些"环境配方"在 Android 8+ 与 LSPosed/Zygisk 世代已不适用，照抄即失败。
- **重招式轻验证**：只讲"怎么 dump 出来"，对"如何确认 dump 产物完整、如何确认关键方法体没有被指令抽取"缺少判定标准。
- **对高代际加固过于乐观**：书中把虚拟机保护称为"未来方向"并承认强度很高，但对"第五代是否可脱"没有给出可操作结论；实际应把这类目标直接归入"换载体/换数据源"决策。
- **默认绕过正当**：未讨论授权、ToS 与对目标的影响。

### 容易混淆的邻近方法论

- `reverse-cost-ladder` 的"能读关键代码就不脱壳"与本 skill 的"够用即止"是同一条原则的两个位置：前者决定要不要投入，后者决定投到什么程度。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
