# 04 移动端逆向

## 解决什么

Android App 上的同类问题，但层数不同：**先判有没有壳、脱到什么程度够**，再在 Java 层找参数生成代码，落到 native 层时用 hook 或 Unidbg 黑盒调用。

## 触发信号（用户原话）

- "App 里 sign 在哪生成 / Jadx 搜出来几百处"
- "查壳说未加固，但只有几百个类"
- "有壳 / 该不该脱 / 脱到什么程度"
- "参数在 so 层 / Unidbg 加载返回空 / Frida RPC"

## 包含的 skill

| skill | 作用 | 来源 | 何时调用 |
|---|---|---|---|
| `android-unpack-gate` | 判断"有没有壳、哪一代、该不该脱"，以及脱到什么程度算够 | 逆向进阶实战 | 拿到 APK 的第一道门 |
| `android-param-locate` | 在 APK 里定位 sign/x-sign/sn 的生成代码；Jadx 命中过多时按调用关系收敛 | 逆向进阶实战 | 已能反编译、要找到生成函数 |
| `native-hook-or-unidbg` | 参数落在 so 层时，在"Unidbg 黑盒调用"与"Frida RPC 导出成接口"之间选一个，并处理返回空/异常值 | 逆向进阶实战 | 已定位到 JNI 方法但不想逆汇编 |

## 类内推荐顺序

```
判壳（android-unpack-gate）→ Java 层定位（android-param-locate）→ native 层（native-hook-or-unidbg）
```

判壳必在第一：反编译只有几百个类时，"未加固"的结论本身就不可信，直接定位会一直搜不到。

## 不该在这里解决

- 抓不到 App 的包 —— 转 `01-通道与封禁` 的 `capture-failure-triage`。
- 参数其实还在 Java 层 —— 不必上 Unidbg，留在 `android-param-locate`。
- 载体是 Web / 小程序 —— 转 `03-Web参数定位`。
- 未授权目标 —— 不做。

## 内容速览

- 判壳的三个反常识信号：类数异常少、关键业务类搜不到、查壳工具报"未加固"但反编译残缺。
- 定位不到时的降级链：搜关键词 → 搜字符串 → 搜调用点 → 动态 hook 打印。
- Unidbg 与 Frida RPC 不是"谁更强"，而是"要不要复现完整执行环境"与"能不能接受真机依赖"的取舍。

## 使用示例

### 示例 1：只有 400 个类
**用户说**：「Jadx 打开这个 APK 只有 400 个类，搜 sign 什么都搜不到，查壳工具说未加固。」

**路由**：`android-unpack-gate` —— 反编译残缺时，"未加固"的结论本身就不可信，先判壳再定位。

**执行**：
1. 看三个信号：类数异常少、关键业务类缺失、Manifest 里类名对不上 → 判为有壳。
2. 判代际（整体加密 / 抽取式 / VMP 类），据此选脱壳方式。
3. 明确"脱到什么程度算够"：能反编译出业务类、能搜到关键字符串即可，不必追全量 dex。

**产出**：判壳结论 + 脱壳方案；完成后再进 `android-param-locate` 找生成函数。

### 示例 2：参数在 so 里
**用户说**：「Java 层找到了 JNI 方法，但参数是 so 算的，要不要把汇编逆出来？」

**路由**：`native-hook-or-unidbg` —— 先选"黑盒调用"还是"真机 RPC"，逆汇编是最后选项。

**执行**：能接受真机依赖 → Frida RPC 把函数导出成接口；需要离线批量 → Unidbg。若返回空数组/异常值，先查 JNI 参数与内存初始化，而不是直接上 IDA。

**产出**：一个可调用的函数接口，或"必须逆汇编"的明确结论。
