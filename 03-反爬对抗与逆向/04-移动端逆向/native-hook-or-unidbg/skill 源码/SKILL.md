# 不逆 so：Unidbg 黑盒调用 vs Frida RPC 导出

## R — 原文 (Reading)

> 也不是说只要找到了方法位置，so 就能100%调用，大部分场景都需要在Unidbg 中补环境。补环境和Js 补环境有些相似，一般是运行环境缺失或者上下文缺失。环境缺失还好办，根据报错提示缺什么就补什么……
>
> — 李玺, 第6章 6.3.3 Unidbg 案例, PAGE 245

---

## I — 方法论骨架 (Interpretation)

1. "不逆 so"应当作为**默认策略**：先用黑盒调用拿到正确的参数，再决定要不要读汇编；读汇编是最后手段，不是入门动作。
2. 有两条可交付的路线：Unidbg 在模拟器里直接调用 so 的 JNI 方法（无需真机、可离线批量、但必须补环境）；Frida RPC 在真机/模拟器里把 App 已有方法暴露成本机 HTTP 接口（最接近真实运行环境、可复用 App 内已完成的初始化，但依赖设备与进程常驻）。
3. 选路看四个量：调用量、是否需要离线/批量、环境可控性（能否拿到真机）、对方是否有反注入。少量且要真实环境 → RPC；量大、要离线、设备不够 → Unidbg。
4. 补环境不是玄学，先做**二分归因**：环境缺失（缺 API、通常会抛错，按报错补）与上下文缺失（少了初始化步骤，往往静默返回空值或异常值）。
5. 二分法直接决定动作：报错 → 补 API；不报错但值不对 → 回溯 Java 层调用链，找到真正做初始化的入口，用上层方法"带跑"，或按内存接口手工补全局状态。
6. 必须有成本护栏：补到第 N 轮仍不收敛就换路线（Unidbg↔RPC↔拦截/自动化），而不是在同一条路上无限投入。
7. 交付判据与路线无关：同一输入稳定复现、且与抓包值逐字符一致，才算打通。

## A1 — 书中的应用 (Past Application)

### 案例 1: 用 Unidbg 直接调 so 生成 xgorgon
- **问题**: 签名在 so 里，强行逆汇编"可能会消耗大量时间和资源"。
- **方法论的使用**: 静态只做到"定位到 so 中的目标函数"这一步，然后用 Unidbg 建 ARM 模拟器、加载 so、执行初始化入口、按类全路径与方法签名解析目标类，再以黑盒方式调用该 JNI 方法取回结果。
- **结论**: 找到了函数位置不等于能调用成功，大多数场景仍要在模拟环境里补东西。
- **结果**: 能在模拟环境里产出参数；作者同时把"补环境"拆成环境缺失与上下文缺失两类，作为后续排障的第一归因（案例已过期，仅演示流程）。

### 案例 2: 用 Xposed 把 App 内方法暴露成本机接口
- **问题**: 只需要少量调用，不想为它搭一套模拟环境。
- **方法论的使用**: 在目标 App 进程内起一个轻量 HTTP 服务，把 App 里已有方法通过反射暴露出去，再用端口转发让本机访问。
- **结论**: 让"App 里已经跑通的初始化"为我所用，绕开了补环境这一大块成本。
- **结果**: 本机请求本地地址即可拿到参数；限制是依赖设备/模拟器在线且进程常驻（案例已过期，仅演示流程）。

### 案例 3: 多重载方法 → Frida RPC + Flask
- **问题**: 目标方法在 so 层，且 Java 侧有多重载入口，直接调不好写。
- **方法论的使用**: 先用 Frida 逐个试出参数签名（按报错提示改），把目标方法用 `rpc.exports` 暴露，再用一个极薄的 Web 服务包成 HTTP 接口；同一案例的另一条路是用 Unidbg 直接调 so。
- **结论**: 两条路都能交付"本地可调用的参数生成器"，差别在环境依赖：RPC 依赖真机与进程，Unidbg 依赖补环境的工作量。
- **结果**: 两条路各自跑通并服务化，作者随后提示"不同版本和环境下可能很难兼容"（案例已过期，仅演示流程）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 已经确认参数在 so 层（Java 层全算法 Hook 都排除了），但不想/不会读 ARM 汇编。
2. Unidbg 能加载 so、能调到方法，但返回空数组、空字符串或明显错误的值。
3. 要在"装 App + Frida 常驻"和"离线跑模拟器"之间做选择，纠结哪种更省事、更稳。
4. 需要批量跑几万次签名，担心 RPC 方案撑不住或设备掉线。
5. 补环境补了十几轮还在报新错，想知道是不是该换路线了。

### 语言信号 (用户的话里出现这些就应激活)

- "Unidbg 返回空 / 调用成功但结果是空数组 / 值不对但没报错"
- "补环境 / 缺 JNI / 上下文缺失 / registerNatives"
- "Frida RPC / rpc.exports / 把方法暴露成 HTTP"
- "不逆 so / 黑盒调用 / 不想看汇编 / 直接调 JNI"
- "unidbg empty result / call native method / frida rpc exports / black-box so"

### 与相邻 skill 的区分

- 与 `android-param-locate` 的区别: 那条负责"判断参数在不在 Java 层、在哪一层"；本 skill 只在"已经确定在 native 层"之后启动。
- 与 `js-env-patch-loop` 的区别: 补环境的**报错驱动闭环**形态相同，但对象不同（浏览器 JS vs Unidbg/JNI）；不要拿 JS 的检测点清单套到 so 上。
- 与 `android-unpack-gate` 的区别: 本 skill 明确绕开 Dex 层；若关键类因为没脱壳而搜不到，先脱壳。
- 与 `reverse-cost-ladder` 的区别: 那条决定"要不要走到 native 这一级"；本 skill 决定"到了这一级选哪条路"。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **确认层：先证明不在 Java 层**
   - 回看全算法 Hook 记录或自定义算法证据。
   - 完成标准: 有明确记录说明"标准 Java 加密均未命中且接口值对不上"。
   - 判停条件: 若证据不足 → 回 `android-param-locate` 重新做批量排除，不要直接进 so。

2. **定位 JNI 入口**
   - 获取三项：类全路径、方法名与参数签名（Smali 语法）、so 文件路径。
   - 完成标准: 三项齐全且能对应到抓包里那个参数；缺一项就继续静态确认。

3. **选路线（写清理由）**
   - 按调用量、是否需要离线、能否拿到真机/模拟器、对方是否反注入打分。
   - 完成标准: 产出一句决断 + 三条理由；不允许"两条都试试"作为结论。

4. **首跑与归因（二分法）**
   - 观察是"报错"还是"静默返回异常值"。
   - 完成标准: 明确归入"环境缺失"或"上下文缺失"，并写出下一步动作（补 API / 回溯调用链找初始化入口）。
   - 判停条件: 若归因为上下文缺失、回溯成本高且调用量小 → 转 RPC 路线，停止继续补环境。

5. **稳定性验收**
   - 同输入连续多次调用，比较输出一致性，并与抓包值逐字符比对。
   - 完成标准: 多次结果一致且与抓包值完全相同；不一致按 `sign-reproduce-acceptance` 排查输入集合，而不是立刻怀疑 so。

6. **工程化护栏**
   - 明确部署形态（离线批量 / 常驻服务）、失效场景（设备掉线、App 升级、so 变更）与恢复方式。
   - 完成标准: 写下"哪种变化会导致方案失效、如何检测、如何回退到另一条路线"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **参数还在 Java 层**：直接 Hook/复写即可，走到 native 是成本浪费。
- **只需要一两次调用**：自动化或拦截往往更便宜，不值得为它搭环境。
- **问题在通道而不是算法**：抓不到包、证书校验失败，属于 `capture-failure-triage`。
- **目标是自研虚拟化保护（高代际）**：黑盒调用常常拿不到正确上下文，此时应优先考虑换载体/换数据源，而不是继续加码。
- **未获授权的目标**：不属于本 skill 的适用场景。

### 作者在书中警告的失败模式

- 以为"找到方法位置就能 100% 调用"（PAGE 245）——这是本 skill 反复强调的第一误区。
- 把"返回空"当成"方法不对"而换方法，实际是上下文没初始化。
- 忽略环境绑定："不同版本和环境下可能很难兼容"（PAGE 331）；版本一升级，之前补好的环境可能整片失效。
- 只验证"能返回字符串"，不验证"值是否与服务端一致"，导致上线后整批失败。

### 作者的盲点 / 时代局限

- **工具版本强绑定**：案例锁定特定 Unidbg 版本与 Android/模拟器组合，升级即可能失效；书中给出的代码骨架不能当模板照搬。
- **重招式轻验证**：对"如何判定补环境已经收敛""返回值和真机值差异多大算失败"缺少可判定标准。
- **未讨论对抗升级**：真实环境里的反注入/反模拟器检测、TLS 指纹、设备指纹均未覆盖；黑盒路线在这些目标上收益有限。
- **未量化运维成本**：RPC 路线的设备掉线、进程被杀、账号/IP 关联风险没有成本模型。

### 容易混淆的邻近方法论

- `reverse-cost-ladder` 也讲"能 Unidbg 就不脱壳"，但它是投入排序；本 skill 是在同一级内部做二选一。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
