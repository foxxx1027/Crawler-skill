# Android 加密函数定位

## R — 原文 (Reading)

> 其实有快速判断的技巧，因为自定义的加密参数一般都在自己写的包里面，所以一些通用的包名不用点进去看，先去掉即可。另外也没必要在检索结果非常多的时候执着于单个查找，可以搜索接口中的其他参数名，接口参数往往都是在同一文件中进行添加的。
>
> — 李玺, 第9章 9.6.3 源码静态分析, PAGE 325

---

## I — 方法论骨架 (Interpretation)

1. 这件事的终点不是"读懂整个 App"，而是找到**返回最终密文的那一层代码**，并能在本地复现同样的值。
2. 起点先判可反编译性（有无壳），能直接反编译就不要碰脱壳；不能则先走脱壳。
3. 检索词的选择决定成败：不要用 `sign`、`MD5` 这类通用词，改用接口里**独一无二的业务参数**（设备号、城市 ID 之类），因为同一请求的参数通常在同一处组装。
4. 先做减法：按包名剔除网络库、JSON 库、图片库、统计 SDK，业务签名几乎不会在通用库里。
5. 静态仍收敛不了，就切换到**动态批量排除**：一次 Hook 全部标准加密入口，打印算法、密钥、明文、密文与调用栈。
6. "没命中"本身就是结论：若所有标准算法都能打出来、但接口里的值对不上，就可以判定 Java 层没有目标，转 native 或自定义算法。
7. 用**返回值形态**校验 Hook 点：打印出的是成品 URL 或拼接串，说明钩在组装层，必须继续往下探到真正吐密文的方法。
8. 有几处候选拿不准时，用 objection 观察类的入参与返回值，直接和抓包值比对，不必读代码。
9. 通关标准只有一个：同一输入在本地稳定算出同长度、同字符集、与抓包值逐字符一致的结果。

## A1 — 书中的应用 (Past Application)

### 案例 1: 某资讯 App 的 signature（360 加固）
- **问题**: 接口里有 `signature`，Jadx 全局搜索 `signature` 命中很多，第一个点进去发现是普通 MD5，不是要找的那个。
- **方法论的使用**: 按"去掉通用包名 + 换检索词"收敛——先剔除通用包的命中，再改用接口里的其它业务参数（`yd_device_id` 一类）去搜，因为同接口参数往往在同一文件里被添加。
- **结论**: 目标签名逻辑集中在自写包里的 `SignUtil`，MD5 只是过程中的一步，不是签名本体。
- **结果**: 定位到类之后改用 Frida Hook 该类的入参与返回值，与抓包值对上，随后进入还原（案例已过期，仅演示流程）。

### 案例 2: 某 App 的 Sign（APK 超过 100MB）
- **问题**: APK 体积过大，Jadx 无法把全部代码载入内存，静态检索基本不可用。
- **方法论的使用**: 先用 Frida Hook **全部**加密算法（MD5/AES/SHA/Hmac），以调用栈方式观察，而不逐个算法去猜。
- **结论**: 每次触发搜索接口都会打印一批加密调用，逐个试下来都不是目标 Sign——于是判定目标不在标准 Java 加密调用里，属 native 或自定义实现。
- **结果**: 停止在 Java 层消耗，转 native 方向（Unidbg 路线），这也是全书反复强调的"没命中也是一种结论"（案例已过期，仅演示流程）。

### 案例 3: 某新闻 App 的 sn（腾讯加固）
- **问题**: 静态搜 `sn` 命中不多但都不像，改搜 `sn=` 后进入某个类，Hook 了负责拼 URL 的方法。
- **方法论的使用**: 观察 Hook 的输出形态——打印出来的是"URL + params + 已含 sn 的成品链接"，说明钩在了组装层而不是加密层；回头确认最终加密由另一个类的方法完成。
- **结论**: Hook 点选错层；判据是返回值形态（成品链接 vs 密文）。
- **结果**: 改 Hook 到真正做 MD5 的那一层，拿到加密前原文与密文，在线 MD5 比对一致后完成还原（案例已过期，仅演示流程）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 已经抓到一个 Android 接口，参数清单里有一个看似哈希/Base64 的 `sign`，但不知道 APK 里是谁算的。
2. 打开 Jadx / Android Killer 搜 `sign`，命中几十到几百处，翻了几十个类都不是目标，开始怀疑方法有问题。
3. APK 很大或类很多，反编译工具卡顿，静态检索走不通。
4. 已经 Hook 到一个方法，但打印出来的是整条 URL，不确定是不是"对了"。
5. 想确认"这个参数到底是不是 Java 层算的"，好决定要不要转 native。

### 语言信号 (用户的话里出现这些就应激活)

- "sign 是哪个方法生成的 / 搜 sign 出来太多 / 换个关键词搜"
- "自吐算法 / Hook 所有加密算法 / 打印调用栈"
- "Jadx 搜不到 / 类太多 / 内存不够"
- "Hook 到的是拼 URL 的方法 / 返回值不对"
- "locate sign in APK / which method generates the signature / frida hook crypto"

### 与相邻 skill 的区分

- 与 `js-param-locate-ladder` 的区别: 同是"按已有信息选手段"，但那条阶梯的对象是浏览器里的 JS（搜索、Initiator 堆栈、XHR/事件断点、内存漫游）；本 skill 的对象是 APK，核心手段变成"包名减法 + 换词 + 全算法 Hook + objection"。
- 与 `native-hook-or-unidbg` 的区别: 本 skill 的出口之一是"判定不在 Java 层"；一旦判定完，后续怎么调 so 不在本 skill 内。
- 与 `android-unpack-gate` 的区别: 本 skill 假设代码已经可读；若反编译产物残缺、类数异常少，先回去脱壳。
- 与 `sign-reproduce-acceptance` 的区别: 本 skill 只负责"找到那一层"；"算出来的值服务端是否接受"的验收与反证由那条协议负责。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **定范围：先判可读性**
   - 记录包名、版本、Dex 规模、反编译工具是否成功、关键类能否搜到。
   - 完成标准: 产出一句判断——"可直接反编译"或"产物残缺需先脱壳"。
   - 判停条件: 若产物残缺/类数异常少 → 先转 `android-unpack-gate`，完成后再回到第 2 步。

2. **建参数清单，挑锚点**
   - 从抓包里列出动态参数与定值，标注长度、字符集、疑似算法。
   - 完成标准: 至少选出一个**唯一业务参数**作为检索锚点（不是 `sign`/`MD5` 这类通用词）。

3. **静态检索（先做减法再加词）**
   - 先按包名剔除通用库，再以业务参数检索，逐个查看命中点。
   - 完成标准: 待查看候选收敛到个位数（≤10 处）。
   - 判停条件: 仍数百处或工具无法承载 → 直接进第 4 步，不要继续扩关键词。

4. **动态批量排除（一次覆盖所有加密入口）**
   - 触发目标请求，Hook 全部标准加密入口，记录算法、密钥、明文、密文、调用栈。
   - 完成标准: 得到明确的"命中 / 未命中"结论，并写下已排除的层（Java 标准算法 / 自定义 / native）。
   - 判停条件: 全部标准算法均未命中且接口值对不上 → 转 `native-hook-or-unidbg`。

5. **校验 Hook 层（看返回值形态）**
   - 判断打印内容：密文 / 签名原文 / 成品 URL / 拼接串。
   - 完成标准: Hook 点满足"输入=签名原文，输出=接口里的那个值"。
   - 判停条件: 若输出是成品链接或已含参数的串 → 判为钩错层，回第 3/4 步继续下探。

6. **交付定位结论**
   - 写下生成链：参与输入的字段集合、算法、常量/密钥来源（含"来自 so 的字符串"这类外部值）。
   - 完成标准: 本地复算值与抓包值逐字符一致；不一致时按 `sign-reproduce-acceptance` 的字段反证流程排查，而不是继续换 Hook 点。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **代码本来就能读、关键类已能搜到**：直接读逻辑即可，套用"全算法 Hook"只会增加无谓动作。
- **参数已确认在 so / native 层**：本 skill 的批量排除已经完成使命，继续在这里打转是浪费；转 `native-hook-or-unidbg`。
- **抓不到包 / 包不完整**：没有参数清单就没有锚点，先走 `capture-failure-triage`。
- **载体是 Web 或小程序**：手段与工具链不同，走 `js-param-locate-ladder`。
- **目标不是自有系统、未获授权**：不属于本 skill 的适用场景。

### 作者在书中警告的失败模式

- 盲目线性阅读反汇编："可能需要阅读成千上万行的反汇编代码……这无疑是浪费时间"（PAGE 250）。
- 检索结果很多时"执着于单个查找"是无效功，应换词或换手段（PAGE 325）。
- 查到 Hook 点就以为成功，不看返回值形态，结果钩在 URL 拼接层（PAGE 341）。
- 把"没 Hook 到"当成失败而反复重试，忽略了它可以作为"排除 Java 层"的证据（PAGE 310）。

### 作者的盲点 / 时代局限

- **工具版本强绑定**：案例依赖 Android Killer、特定版 Jadx 内存上限、夜神 Android 5/7、Xposed 生态；这些环境配方照抄即失败，工具换代后步骤会变（BOOK_OVERVIEW 批判段）。
- **重招式轻验证**：书里大量篇幅在"怎么找到"，对"如何证明找到的就是唯一那一处""是否存在二次校验/时间窗/一次性 nonce"缺少系统论述。
- **未覆盖新形态**：设备指纹、TLS/JA3 指纹、WebAssembly 加密均未涉及；这些形态下"搜关键词 + Hook 标准算法"的命中率会显著下降。
- **默认绕过是正当的**：全书站在采集方视角，没有讨论授权、robots/ToS、请求预算与对目标可用性的影响。

### 容易混淆的邻近方法论

- `js-param-locate-ladder`（Web JS 同一问题的阶梯）与 `reverse-cost-ladder`（"能 Hook 就不逆 so"的成本排序）常被误当成同一件事：前者是定位手段表，后者是投入决策。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
