# 花指令剔除：两级递归与定义侧/引用侧

## R — 原文 (Reading)

> "本质是把二项式拆开成三部分：二项式的左边、二项式的右边和运算符。二项式的左边和右边作为另外一个函数的两个参数，二项式的运算符作为该函数的运行逻辑。"
>
> "上述过程只处理了ObjectExpression节点的属性值，最后还要对代码中引用的地方都进行替换（替换之前更新totalObj对象）。"
>
> — 李岳阳、卓斌, 第6章 PAGE 106 / 第11章 PAGE 237

---

## I — 方法论骨架 (Interpretation)

"花指令"在书里有两个所指，必须分开命名，否则递归一定写错。

字符串花指令是取值链：`_0x22b277['oiFIc']` 取出另一个对象，再取下一个键，直到落到一个 `StringLiteral`。终止条件就是"已经是字符串字面量"。

函数花指令是包装层：取到的值是一个函数，函数体只做一次运算（如 `return a+b`），但体内还可能引用别的属性；要继续下钻，直到函数体内不再含 `MemberExpression`。终止条件是"干净的函数"。

两类都要有索引。`totalObj` 按"变量名 → 属性名 → 值节点"建二级索引，让每次取值能 O(1) 找到定义侧节点；它是每轮的静态快照，不是永久真相。

替换必须分两遍。第一遍改定义侧：把 `ObjectExpression` 里的属性值递归解析成真实值或真实函数。第二遍才改引用侧：遍历全文件 `MemberExpression`，把 `_0x22b277['oiFIc']` 换成解析结果。只改定义侧等于白改，因为引用处仍指向旧对象。

两遍之间必须重新生成代码并重建 `totalObj`，否则引用侧拿到的是过期值。

删除是最后一步，而且要有引用计数。对象可能还承载真实配置，或仍被其它地方引用；引用不为 0 就保留，宁可留脏，也不要产出运行期 `undefined`。

递归前先证明终止：加 `visited` 集与深度上限。命中自引用环时，把它判为真实依赖，保留函数，只替换内部已解析干净的引用，不要伪造常量。

顺序上先字符串后函数：函数体里可能还含字符串花指令，先解决外层字符串，函数才可能变干净。

## A1 — 书中的应用 (Past Application)

### 案例 1：二项式被拆成函数调用（第6章 PAGE 105–107）
- **问题**: `a+b` 被改写成 `f(a,b)`，`f` 的函数体只做一次加法；还可以再套一层 `g`，形成多级嵌套。
- **方法论的使用**: 作者指出本质是把二项式拆成"左边、右边、运算符"三部分，左右作另一函数的两个参数，运算符作该函数的运行逻辑；识别要点是函数体只有一行、只做一次运算、且被大量不同名字重复定义。
- **结论**: 花指令是"稀释层/包装层"，还原时逐层看函数体，向下一层跟进，直到见到真实运算符。
- **结果**: 多级包装可以被逐层剥掉；"函数体只有一行 + 只做一次运算"成为识别函数花指令的硬信号（第6章 PAGE 106–107）。

### 案例 2：造侧刻意让同名去重失效（第9章 PAGE 186）
- **问题**: 混淆器把每个 `BinaryExpression` 都包成函数调用，如果同名复用，逆向方按函数名去重就能一次还原。
- **方法论的使用**: 作者对每个 `operator` 都生成不同名字的函数，让"同名函数"这条线索失效。
- **结论**: "每遍历到一个operator，都可以生成不同名字的函数"——逆向必须先按函数体去重再归纳，不能靠名字聚类。
- **结果**: 文件里出现大量异名但同构的包装函数；还原时按"函数体只有一行 + 一次运算"分组，而不是按名字（第9章 PAGE 186）。

### 案例 3：真实靶站的两级递归与两遍替换（第11章 PAGE 234–240）
- **问题**: 靶站把所有字符串和函数都塞进 `_0x22b277` 对象，既有 `_0x22b277['oiFIc']` 字符串链，也有 `_0x22b277['etrqc']` 函数包装。
- **方法论的使用**: 作者先建 `totalObj`（变量名→属性名→值节点），再对 `MemberExpression` 递归取值；字符串链终止于 `StringLiteral`，函数链终止于体内无 `MemberExpression` 的 `FunctionExpression`。每类跑两遍：先改 `ObjectExpression` 属性值，重算 `totalObj` 后改全文件引用处；最后检查引用再删对象。
- **结论**: 只改 `ObjectExpression` 内部等于白改；字符串与函数的终止条件不同，必须分开递归；删对象前先判断是否还有引用。
- **结果**: 间接层被折叠成真实值与真实函数，代码可读性恢复；删不掉的对象按作者建议先保留，避免运行期 `undefined`（第11章 PAGE 234–240）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 代码里反复出现 `_0x22b277['oiFIc']`、`_0x22b277['abc']['def']` 这类属性链取值。
2. 有大量名字不同、函数体却只有一行 `return a+b` 或 `return fn(args)` 的包装函数。
3. 只改了对象定义里的属性值，引用处仍是旧值，感觉"白改了"。
4. 同一个对象既装花指令属性，也装真实配置，删整个对象后运行时报错或出现 `undefined`。
5. 对象属性互相引用成环（`_0x1['a']` → `_0x1['b']` → `_0x1['a']`），递归不终止。

### 与相邻 skill 的区分

- 与 `constant-fold-and-decoding` 的区别: 后者折叠纯字面量运算与编码（`425871^425977`、`\u`、`eval('base64')`）；本 skill 解决"通过对象/函数间接层取值"，必须先建 `totalObj` 才能找到定义侧。
- 与 `string-pool-decrypt-revive` 的区别: 字符串池是"大数组 + 乱序 + 解密函数"；花指令是"对象属性链 / 包装函数"。两者都用引用点，但容器与终止条件不同。
- 与 `control-flow-flattening-restore` 的区别: 平坦化改控制流顺序；本 skill 去掉取值间接层，不改语句顺序。
- 与 `ast-restore-pipeline-acceptance` 的区别: 后者掌管全局七段顺序与验收；本 skill 是其中"剔花指令"这一段，但仍要服从"先字符串后花指令"的前置。
- 与 `scope-safe-rename` 的区别: 必须先剔花指令再改名；改名会断掉按属性字符串键搜索的线索。
- 与 `sign-reproduce-acceptance` 的区别: 后者验最终参数值；本 skill 验折叠是否改变语义，值不对时先查 `totalObj` 是否过期。

## E — 可执行步骤 (Execution)

顺序是一阶约束：定义侧是引用侧的数据源，先改引用会读到旧值；`totalObj` 是静态快照，不重算就会拿过期节点；删对象必须在引用清零之后，否则剩余引用变 `undefined`；字符串必须先于函数，因为函数体里可能还含字符串花指令；终止性检查必须先于递归，否则环会让递归永不结束。

1. **分类并列出两类间接层**
   - 完成标准: 对每个候选对象/函数标出类型（字符串链 / 函数包装）与终止条件（`StringLiteral` / 体内无 `MemberExpression`）。
   - 判停条件: 既没有属性链也没有包装函数 → 不属于本 skill；对象键是运行期计算的 → 静态索引不可用，停止。

2. **建 `totalObj` 二级索引**
   - 完成标准: 全文件每个 `ObjectExpression` 都能按"变量名 → 属性名 → 值节点"查到，且记录本轮快照时间点。
   - 判停条件: 存在 `obj[k]` 动态键、`Object.assign`、原型继承或别名赋值 → 索引不完整，标记为不可静态解析，不要盲替。

3. **定义侧递归解析，带终止性保护**
   - 完成标准: 每个属性值要么解析为 `StringLiteral`，要么解析为体内无 `MemberExpression` 的干净函数；环与超深节点被标记并保留。
   - 判停条件: 命中 `visited` 环或达到深度上限 → 停止下钻，按真实依赖保留；无法证明终止时默认它是真实代码。

4. **重算 `totalObj`，再改引用侧**
   - 完成标准: 重新 `generate → parse` 或重建索引后，遍历全文件 `MemberExpression`，把引用替换为解析结果；替换后引用计数下降。
   - 判停条件: 引用数不下降、或替换后又出现旧值 → 说明快照过期，回步骤 3 重算，不要继续批量替换。

5. **引用为 0 才删除对象**
   - 完成标准: 删除前全文件引用计数为 0，删除后 `generate` 与再次 `parse` 成功，无残留 `MemberExpression` 指向已删对象。
   - 判停条件: 仍有引用，或对象还承载真实配置 → 保留，宁可留脏；删除后出现 `undefined` → 回退并恢复该对象。

6. **抽查验收**
   - 完成标准: 抽查若干解析值与运行期真实取值一致，关键路径在样本回放中不因剔除而改变行为。
   - 判停条件: 值不一致 → 先查"是否用了过期 `totalObj`"与"终止条件是否判错"，不要重写整个递归。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 代码只有常量编码、十六进制、`\u` 转义或平坦化，没有对象/函数间接层——不属于花指令。
- 对象键或属性值依赖运行期状态（动态键、`getter`、原型链、闭包变量），静态索引拿不到真实值。
- 对象还承载真实配置或公共函数，整对象删除会破坏其它逻辑——只能替换已知花指令属性，不能删对象。
- 这是真实的工厂/注册表/依赖注入层，而非混淆包装——折叠它等于改变抽象与语义。
- 依赖图环多且无法证明哪些是花指令——默认按真实代码保留，不要为了"干净"强行折叠。

### 作者在书中警告的失败模式

- 只处理 `ObjectExpression` 的属性值，不替换引用处，等于白改；必须"对代码中引用的地方都进行替换"（第11章 PAGE 237）。
- 删除对象前不判断引用，删掉仍在用的对象，剩余引用变 `undefined`，还原产物运行时报错（第11章 PAGE 240）。
- 同一个运算符也生成不同名字的函数，按"同名函数"去重会失效，必须先按函数体去重再归纳（第9章 PAGE 186）。
- 把字符串花指令与函数花指令混为一谈，用同一个终止条件递归，会在字符串链上无限下钻或提前停止（第11章 PAGE 234）。
- 递归不检查终止性，遇到自引用环会栈溢出，或把环的一半替换成常量，留下半真半假的代码（第11章 PAGE 234–240）。

### 作者的盲点 / 时代局限

- `totalObj` 只是静态快照，书中未讨论动态键、别名（`a = obj`）、原型继承、`getter` 与 `Object.assign`；真实样本很容易让索引失真（第11章 PAGE 234–237）。
- "无引用就删"只覆盖显式 `MemberExpression` 引用；`Object.keys`、`JSON.stringify`、字符串拼接键、反射式访问仍可能在用该对象，书中未讨论（第11章 PAGE 240）。
- 递归终止性、环检测与深度上限是必要的工程补充，书中示例没有给出；直接照抄在环状样本上不成立。
- 样本只有作者自建靶站与自写混淆器，花指令形态限于"二项式转函数 + 对象属性链"；真实商业混淆常用不透明谓词、算术恒等式、多态包装，未覆盖（BOOK_OVERVIEW 批判节，PAGE 234–240）。
- 验收是"看起来解析干净了"，没有语义等价性证明或全量回放。

### 容易混淆的邻近方法论

- `constant-fold-and-decoding` 的 `evaluate` 折叠：那是对已知字面量表达式求值；本 skill 要先通过对象索引找到定义侧，再可能调用求值。
- 死代码消除（DCE）：按可达性删除无用代码；花指令剔除按"间接层折叠"处理，即使对象仍可达也要先替换引用。
- 内联优化（inlining）：编译器把函数调用展开；本 skill 只展开"单次运算的包装函数"，不改变真实函数的调用语义。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
