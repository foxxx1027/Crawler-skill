# 流程平坦化还原：分发器即置换表

## R — 原文 (Reading)

> "还原流程平坦化之前，应当先进行字符串解密以及剔除花指令。在还原流程平坦化的过程中，需要先获取分发器，因为分发器中记录着代码原先的真实顺序。"
>
> "//多循环几次，而不用去判断原始代码中到底有多少个switch流程平坦化"
>
> — 李岳阳、卓斌, 第11章 PAGE 241 / PAGE 244

---

## I — 方法论骨架 (Interpretation)

平坦化把一条执行链压成状态机：代码块被切碎、平级塞进 `switch` 的 `case`，外层用 `while(!![])` 反复执行，靠 `continue` 和分发器决定下一块。块的内容还在，真实顺序却被搬走了。

因此第一步永远不是找 `switch`，而是拿分发器。它通常是一个字符串，经 `split('|')` 得到数组，数组的第 `i` 位就是第 `i` 步要跳到的 `case` 号。这张表就是还原说明书；没有它，重排只能靠猜。

拿到表后按四件事走：`findParent` 找到保存分发器的变量声明，`getSibling` 找到相邻的 `while`，读出 `switch` 的 `cases` 并用分发器值映射到真实块，清空原 `body` 再按表顺序 `push` 回去。

嵌套平坦化不能一轮全改。父层与子层的 `body` 重排会互相覆盖，错误还是静默的。做法是每轮只命中一个、处理完立刻 `path.stop()`，外层反复重新遍历，直到没有可处理项。

不要精确数"到底有几个平坦化"。收敛比计数稳：宁可多跑几轮，也不因为少数一个而留下残余。

变体要按不变量处理：真实顺序一定存在某处、每块有唯一标识、控制流一定被"循环 + 分派"包住。循环可能是 `while`/`for`/`do-while`，退出可能是 `return` 而不是越界，分发器可能是数组或对象映射。

## A1 — 书中的应用 (Past Application)

### 案例 1：手工改造 `format` 函数的三步构造（第6章 PAGE 108–111）
- **问题**: 要演示平坦化如何把一段顺序代码变成状态机。
- **方法论的使用**: 作者把原语句切成块、平级塞进 `case`；用 `while(!![])` 反复执行 `switch`；再用 `'7|5|1|3|2|4|6'.split('|')` 加自增下标作分发器，决定跳转次序。
- **结论**: 平坦化 = 分块打乱 + 死循环 + 分发器；退出可以靠 `return`，也可以让下标越界取到 `undefined` 后走 `break`。
- **结果**: 同一函数被成功改造成平坦化形态；反过来说明还原时先拿分发器、按表重排即可恢复原顺序（第6章 PAGE 110–111）。

### 案例 2：造侧的生成公式 `dispenserArr[v.index]=i`（第9章 PAGE 198–202）
- **问题**: 混淆器要打乱块顺序，同时必须把真实顺序记下来供运行期跳转。
- **方法论的使用**: 给原始语句编号，`v.index` 是真实顺序；打乱后分配到 `case` 值 `i`，写入 `dispenserArr[v.index]=i`，最后 `join('|')` 得到分发器串。
- **结论**: 分发器串是"第 v.index 位写 i"的置换表；造侧的生成公式与拆侧的按串反查互逆。
- **结果**: 生成 `'0|1|4|5|3|2'` 这类串，运行期按串跳转；还原时读同一张表就能还原块顺序（第9章 PAGE 200）。

### 案例 3：真实靶站的前置顺序与嵌套收敛（第11章 PAGE 241–245）
- **问题**: `lebo.yzm.pc.min.js` 同时有字符串池、花指令和多处嵌套平坦化。
- **方法论的使用**: 作者先做字符串解密、再剔花指令，最后才平坦化；平坦化内部先取分发器，再定位 `while`/`switch`，清 `body` 按表重排。遇到嵌套时每轮只还原一个，处理完 `path.stop()`，外层 `for` 反复重跑。
- **结论**: "还原流程平坦化之前，应当先进行字符串解密以及剔除花指令"；嵌套时"多循环几次，而不用去判断到底有多少个"。
- **结果**: 多轮收敛后平坦化被清除，代码恢复为顺序结构；作者明确用收敛兜底替代精确计数（第11章 PAGE 241、244–245）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 文件顶部有 `var arr = '7|5|1|3|2|4|6'.split('|')`，下面紧跟 `while(!![]){switch(...){case ...}}`。
2. 已经还原了字符串，但代码块顺序仍然错乱，读起来像跳来跳去。
3. 同一文件有多处、甚至嵌套的 `switch` 平坦化，一次性全改后顺序更乱。
4. 分发器被花指令包住，形如 `a = _0x22b277['xYz'].split('|')`，按 `StringLiteral` 找直接失效。
5. `case` 里用 `return` 而不是 `continue`，不知道结束条件该怎么改。

### 与相邻 skill 的区分

- 与 `string-pool-decrypt-revive` 的区别: 后者解出字符串明文；本 skill 在明文已可读之后重排控制流，且必须在它之后。
- 与 `junk-instruction-elimination` 的区别: 若分发器是 `MemberExpression` 而不是 `StringLiteral`，说明被花指令包住；先剔花指令，再回来取表。
- 与 `ast-restore-pipeline-acceptance` 的区别: 后者掌管"字符串→花指令→常量→平坦化→改名"的全局顺序与验收；本 skill 只负责平坦化这一段。
- 与 `constant-fold-and-decoding` 的区别: 后者折叠字面量与编码，不改变语句顺序；平坦化改的是控制流结构。
- 与 `scope-safe-rename` 的区别: 改名必须放在平坦化之后；先改名会破坏按属性键搜索，也会在重排时制造作用域歧义。
- 与 `sign-reproduce-acceptance` 的区别: 后者验单个参数的值；本 skill 验控制流重排后的顺序与回放行为，值不对时先怀疑前置，而不是算法。

## E — 可执行步骤 (Execution)

顺序是一阶约束：分发器不可用就无法知道真实顺序；花指令没剔，分发器可能取到包装值，选择器会静默失效并误判"没有平坦化"；字符串没解密，`case` 内容不可读，重排后"顺序对、内容错"；嵌套不单步，父子 `body` 会互相覆盖且不报错。

1. **确认前置条件与分发器可直接取到**
   - 完成标准: 字符串已解密、花指令已剔除，分发器是可直接读取的 `StringLiteral`（或已解析出的等价值）。
   - 判停条件: 分发器仍是 `MemberExpression`（如 `_0x...['xYz']`）→ 回 `junk-instruction-elimination`；完全看不到分发器 → 不是本 skill。

2. **提取并校验置换表**
   - 完成标准: `split('|')` 得到数组，长度等于 `case` 数，元素覆盖 `0..n-1` 且不重复。
   - 判停条件: 出现重复、缺号或长度不符 → 说明是变体或已损坏，不要按这张表重排，先按不变量判断真实来源。

3. **定位变量声明、循环与 `switch` 三件套**
   - 完成标准: 用 `findParent` 拿到保存分发器的 `VariableDeclaration`，用 `getSibling` 拿到相邻 `while`，并能读出 `switch` 的 `cases`。
   - 判停条件: 循环是 `for`/`do-while`、`case` 用 `return`、或形状与样本不同 → 保留不变量，改选择器而不是硬套模板。

4. **按表重排 `body`**
   - 完成标准: `body` 被清空后，按分发器顺序把对应 `case` 的块 `push` 回去；语句内容原样保留，只改顺序。
   - 判停条件: 某块承担 `return`/`break` 的退出语义 → 先确定结束判据（用分发器长度，而不是依赖越界 `undefined`），再重排。

5. **嵌套场景单步收敛**
   - 完成标准: 每轮只处理一个平坦化并 `path.stop()`，外层重新遍历，直到一轮没有任何候选；达到预设上限仍未清完则记录残余。
   - 判停条件: 达到轮次上限 → 停止并报告残余位置，不要无限重跑；若每轮候选数不下降 → 检查是否误把真实状态机当平坦化。

6. **验收顺序与语义**
   - 完成标准: 重排后的代码可 `generate` 与再次 `parse`，块顺序与分发器一致，关键路径在样本回放中产出与还原前相同的值。
   - 判停条件: 顺序看起来对但值不对 → 回步骤 1 查前置（字符串/花指令），而不是继续调重排逻辑。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 控制流是真实的状态机，跳转依赖运行期数据（解析器、协议状态机）——重排会改变语义，这不是混淆。
- 分发器在运行期计算（拼接、加密、服务端下发），静态拿不到完整置换表——不要猜顺序。
- 只有常量编码、属性下标或字符串池，没有"循环 + 分派"结构——不属于平坦化。
- 代码含 `async/await`、生成器或 `try/finally` 且块被跨边界切开——简单重排可能破坏挂起与清理语义。
- 分发器是对象映射、数组索引或算术表达式，而手上只有 `split` 选择器——先做形状分析，不要硬套。

### 作者在书中警告的失败模式

- 还原顺序不正确会导致整链失败：平坦化之前必须先字符串解密、再剔花指令（第11章 PAGE 249、241）。
- 分发器被花指令包住时，按 `StringLiteral` 调 `split` 的选择器直接失效，会被误判为"没有平坦化"（第11章 PAGE 234–241、245）。
- 嵌套平坦化若一轮全改，父层与子层 `body` 顺序互相覆盖，且错误是静默的（第11章 PAGE 244–245）。
- 把某一种 `switch` 形态当通用模板；作者明言"switch流程平坦化混淆并不是只有这一种"，必须按原理现场分析（第11章 PAGE 245）。
- 退出若依赖"下标越界取 `undefined`"，遇到 `case` 内 `return` 就失效；结束判据要改成显式长度（第6章 PAGE 110–111、第11章 PAGE 245）。

### 作者的盲点 / 时代局限

- 书里的平坦化是单一模板，`for(i<20)` 是经验上限，既无收敛证明也无复杂度控制；真实商业混淆常用不透明谓词、状态变量、间接跳转与算术生成的分发器，未覆盖（第11章 PAGE 244–245）。
- 验收靠"看起来顺序对了"与少量回放，没有控制流图等价性证明；重排可能改变变量提升、`this` 绑定与块级作用域，书中未讨论（第11章 PAGE 245）。
- 样本量只有作者自建靶站，混淆器与还原器同源，存在循环论证；第二个站点或商业方案未验证（BOOK_OVERVIEW 批判节，PAGE 223–249）。
- `for` 轮次上限与全树 `traverse` 带来 O(20·N) 成本，书中没有超时、残余报告或失败退出。

### 容易混淆的邻近方法论

- `constant-fold-and-decoding` 的逗号表达式展平：那是把一条语句拆成多条，同属"结构还原"，但不涉及分发器与 `switch`。
- 一般的"代码美化/格式化"：只改排版，不改执行顺序。
- 编译器/反编译器里的控制流重建：从 CFG 恢复结构化语句，本 skill 只是按已有置换表重排块。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
