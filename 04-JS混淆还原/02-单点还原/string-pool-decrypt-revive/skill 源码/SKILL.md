# 字符串池解密与复活执行

## R — 原文 (Reading)

> "要完成字符串解密，先要得到原始代码中的三个部分，即大数组、还原数组顺序的函数和字符串解密函数，其中的字符串解密函数，还需要得到字符串解密函数的名字。"
>
> "再次强调，由于原始代码中存在格式化检测和内存爆破的代码，所以上述代码在生成字符串代码时，需要指定选项，使用压缩后的代码来执行，否则会内存溢出。"
>
> — 李岳阳、卓斌, 第11章 PAGE 232

---

## I — 方法论骨架 (Interpretation)

字符串池是真实混淆的第一道门：明文被搬进头部大数组，调用点只剩 `_0x2ba9('0x1f')` 这类索引。要还原，必须让"数组 + 乱序还原函数 + 解密函数"这三段先活过来。

关键在于分清引导代码与被保护代码。乱序还原函数自己要先运行，数组才可用；它内部用到的 `push`/`shift` 方法名一旦也被抽进数组，就变成"解密前先解密"，启动即死。

复活不是把三段留在原树里跑，而是复制进一个空 AST，生成一段干净的可执行串。生成必须 `compact:true`：源码里的格式化检测和内存爆破会在格式化输出时被触发，这是安全约束，不是代码风格。

`eval` 是不可信执行，必须在无网络、无文件写、限时限内存的隔离沙箱里做。解密完成后，`referencePaths` 是"所有出现位置"，不等于"所有调用位置"；只替换父节点为 `CallExpression` 的引用，属性引用要跳过。

删除三段要按之前记录的节点路径，而不是 `shift` 三次。删除前确认没有残留引用；删不掉就保留，避免产出静默崩。

## A1 — 书中的应用 (Past Application)

### 案例 1：乱序自执行函数不能被提池（第6章 PAGE 104–105）
- **问题**: 数组混淆把字符串集中到 `bigArr`，再用乱序函数打乱；乱序函数本身也要用字符串方法名。
- **方法论的使用**: 作者判断这段还原函数属于引导代码，它必须先于大数组可用；因此其中的字符串不能抽进 `bigArr`，只能用字面量方法名或十六进制编码保留可执行性。
- **结论**: "还原数组顺序的函数里用到的字符串，不能再提取到bigArr中"——引导代码与被保护代码必须分开。
- **结果**: 若违反，数组尚未就绪、方法名取不到，脚本启动即崩；这条自毁判据后来成为判断"哪段是引导代码"的通用准绳。

### 案例 2：真实靶站的三段复活（第11章 PAGE 232–233）
- **问题**: `lebo.yzm.pc.min.js` 头部有大数组、乱序自执行函数和 `_0x2ba9` 解密函数，全文调用点都是索引形式。
- **方法论的使用**: 取前三段与解密函数名，塞进 `parse('')` 的空 AST，`generate({compact:true})` 后 `eval`；再遍历 `referencePaths`，只处理 `parentPath.isCallExpression` 的引用并替换成明文字面量；最后 `shift` 三次删引导代码。
- **结论**: 四步顺序固定；`compact` 必须保留，否则命中格式化检测与内存爆破；`referencePaths` 里混着解密函数的缓存属性引用，必须按父节点类型过滤。
- **结果**: 全文 `_0x` 调用变为明文，后续花指令与平坦化才有可读输入；作者同时指出"shift 三次"依赖前三句的固定布局，是脆弱点。

### 案例 3：造侧的同一约束（第8章 PAGE 181）
- **问题**: 自研混淆器要把全文件字符串抽进大数组，但乱序还原代码自身也在文件里。
- **方法论的使用**: 作者对 `push`、`shift` 这类方法名只做十六进制编码，不放进池。
- **结论**: "由于这些代码处于还原数组顺序的代码中，因此无法把它们提取到大数组中"——造侧独立复述了引导代码白名单。
- **结果**: 产物保留可执行性；这也说明"引导代码不能提池"不是某个样本的偶然经验。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 文件开头是一个几百项的大数组，紧接着一个带 `push`/`shift` 的自执行函数。
2. 全文到处是 `_0x2ba9('0x1f')`、`_0x1234(0x2a)`，想把它们换成可读字符串。
3. 批量替换引用后，某些位置变成 `undefined`，或解密函数属性被误当成调用。
4. 本地 `eval` 能解出值，但 Node 进程内存飙升、被系统杀死或卡死。
5. 源码最前面还有 `'use strict'`、注释块或额外声明，不确定还能不能"删前三句"。

## E — 可执行步骤 (Execution)

顺序是一阶约束：没有三段就没有可执行串；不先生成再 `eval` 就没有明文；不先拿到明文就无法替换引用；不先替换就删除会失去解密来源；不先过滤父节点类型就会把属性引用改坏。这是数据依赖，不是文本顺序。

1. **按形状确认三段并记录路径，不按固定下标**
   - 完成标准: 找到 `ArrayExpression`、紧跟的乱序 `IIFE`、含 `atob`/`replace`/索引运算的解密函数，并记下三者的 `path` 与解密函数名。
   - 判停条件: 只有大数组没有解密函数，或数组是运行期多次 `push` 拼出来的 → 不要套"前三句"，先按形状重建；若连大数组都没有 → 不属于本 skill。

2. **在空 AST 组装引导代码，并强制 compact 生成**
   - 完成标准: 新 AST 只含三段，`generate({compact:true})` 输出单行可执行串，原树未被改动。
   - 判停条件: 生成结果仍是多行/带缩进 → 先修生成选项，绝不可直接 `eval`。

3. **在隔离沙箱求值，取回明文**
   - 完成标准: 解密调用返回字符串；沙箱无网络、无文件写、有超时与内存上限，执行后无外部副作用。
   - 判停条件: 出现 OOM、进程被杀或死循环 → 回到步骤 2 检查 `compact`；若代码尝试访问网络/进程/文件 → 立即中止，改用静态模拟而非执行。

4. **只替换真正的调用点**
   - 完成标准: 遍历 `referencePaths`，仅对 `parentPath.isCallExpression()` 的引用替换为字面量；属性引用原样保留并记录。
   - 判停条件: 替换数为 0 或大量引用被跳过 → 先确认 `binding` 是否来自当前解密函数；不要把属性引用强行求值。

5. **按记录路径删除三段，并回读验收**
   - 完成标准: 三段已删、全文无残留解密调用、`generate` 与再次 `parse` 成功，抽查若干明文与运行结果一致。
   - 判停条件: 任一段仍被引用 → 保留该段，不要用 `shift` 硬删；删除后出现 `undefined` → 回退到步骤 4 检查过滤条件。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 代码里没有字符串池，只有常量编码、属性下标或平坦化——先做指纹判别，别把编码当加密。
- 无法提供隔离沙箱，或不允许执行第三方代码——不要 `eval`，改为静态模拟解密函数。
- 解密依赖运行期状态（每次请求的随机数、服务端下发密钥、动态生成的对象键），静态复活不成立。
- 目标是改标识符名——必须先把字符串解出来；改名是另一个 skill。
- 只关心单个参数能否复现——直接走参数验收，不必整池复活。

### 作者在书中警告的失败模式

- 把乱序还原函数自身用到的字符串也抽进大数组，形成"解密前先解密"，脚本启动即崩（第6章 PAGE 105、第8章 PAGE 181）。
- 生成引导代码时不用 `compact`，源码里的格式化检测与内存爆破被触发，Node 内存溢出（第11章 PAGE 232）。
- 把 `referencePaths` 当"所有调用点"，连解密函数的缓存属性一起替换，得到 `undefined` 或报错（第11章 PAGE 233）。
- `shift` 三次依赖"引导代码恰好是前三句"的固定布局；前面插入 `'use strict'` 或额外声明就会删错（第11章 PAGE 232）。
- 只改引用不删引导代码，或删了但仍被引用，留下死代码或半截上下文，表现为"跑得动但值全错"（第11章 PAGE 232–233）。

### 作者的盲点 / 时代局限

- 书中把 `eval` 当普通函数调用，没有超时、内存上限与网络隔离；但它执行的是不可信第三方代码，安全边界必须由使用者自己补（第11章 PAGE 232）。
- 样本只有作者自建靶站，混淆模板与第9章同源，"用自己造的混淆器喂自己的还原器"存在循环论证；真实样本的数组拆分、运行期拼接、状态化解密未覆盖（BOOK_OVERVIEW 批判节，PAGE 231–233）。
- 默认"前三段即引导代码"，未讨论 AST 形状变化下的选择器稳健性；教材代码也未经可重复执行验证（BOOK_OVERVIEW 内部矛盾，PAGE 232）。
- 只处理静态字面量池；对象池、原型链取值、WebAssembly 侧字符串表不在覆盖范围。

### 容易混淆的邻近方法论

- `constant-fold-and-decoding` 的 `eval` 分支：那里求的是单个表达式或单行密文；这里是整池 + 乱序 + binding 引用点。
- `obfuscation-fingerprint-triage` 的"大数组 + push/shift"指纹：那只是判层，不等于会复活。
- 普通"字符串解码"：Base64/hex 解码器只还原字符，不解决数组、乱序和引用替换。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
