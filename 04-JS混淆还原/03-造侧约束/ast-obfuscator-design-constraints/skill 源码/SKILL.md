# 混淆器设计约束：先"可加密化"，再只保护值钱的那几行

## I — 方法论骨架 (Interpretation)

混淆工程的第一问题不是"选更狠的算法"，而是"哪些东西现在还没有资格被加密"。

`p.name` 里的 `name` 是语法成分，必须明确出现在代码里，改不动、也抽不进池；`p['name']` 里的 `name` 是字符串，是数据，才能被拼进大数组、做 base64/hex/unicode。所以第一步是"把语法改成数据"，不是挑算法。没做这层改造，后面的加密无处下手。

同一条规则在内置对象上重演：`Date`、`Math`、`JSON` 原本只能点号访问，必须先写成 `window['Date']` 这种形式，属性变字符串，才有加密与拼接空间。这是"属性改下标"和"内置对象混淆"两条线的交汇点，做晚了等于白做一半工作量。

例外是引导代码。字符串池的乱序还原函数、解密函数、分发器构造，这些代码本身必须在数组就绪之前运行；如果把它们用到的字符串也提进池，就成了"解密前先解密"，脚本启动即崩。所以必须给引导代码开白名单——这不是优化，是产物能不能跑的前提。

覆盖面的判断与直觉相反。全量逐行加密会在文件里留下大量同构的 `eval` + 长字符串调用，特征一眼可见，而且解密脚本一写就全解；只加密关键几行，反而把攻击面收敛到少数位置，更耗对手时间。

顺序上是硬约束。逐行加密以"整行文本"为单位做 base64/ASCII，会把行内的标识符一起加密；先加密再改名，密文里已经没有可识别的 `Identifier` 节点，改不动。所以必须"标识符混淆 → 逐行加密"。数值常量混淆不影响节点类型，可与改名任意先后。

关键性属于业务语义，AST 只看得到语法。自动化无法判断哪一行是签名、哪一行只是埋点，作者自己的结论是：除非用户在代码里加标记。可行的做法是用行尾注释（如 `//Base64Encrypt`）当锚点，脚本只处理带标记的语句，处理后还要 `delete trailingComments`，否则标记本身既是特征又暴露意图。

不要堆层。属性下标、hex 属"造贵拆廉"，平坦化与标识符混淆接近对称；对核心几十行，优先上后两者，而不是把便宜的层堆到十几层。

最后，造与拆是同一套手法正反两用，但覆盖不成对：造 12 类、拆 7 类。设计时就该问一句"这几层我自己拆得掉吗"，答不上来的层，收益要打折。

## A1 — 书中的应用 (Past Application)

### 案例 1：属性访问方式的对比（第6章 PAGE 97）
- **问题**: 同一段逻辑，用 `p.name` 与 `p['name']` 写出来的混淆潜力完全不同，需要先判断该改哪一种。
- **方法论的使用**: 作者逐条对比：`p.name` 中 `name` 是一个标识符，必须明确出现在代码中，不能加密和拼接；`p['name']` 中 `name` 是一个字符串，既然是字符串，访问的时候就可以进行拼接和加密。由此得出结论：JS 混淆中一般会选择方括号字符串这种方式来访问属性。
- **结论**: 混淆的第一步是"把语法变成数据"——方括号里的字符串才是可抽池、可加密的原料；点号访问的属性名根本没资格进池。
- **结果**: 书中后续所有字符串池、base64/hex/unicode 的示例，都建立在大面积 `obj['xxx']`、`this['xxx']` 之上；这也解释了真实样本里为什么几乎见不到点号属性（第6章 PAGE 97）。

### 案例 2：内置对象先 `window` 化（第8章 PAGE 174）
- **问题**: `Date`、`Math`、`JSON` 这类内置对象是点号访问的，属性名改不动，无法参与字符串加密。
- **方法论的使用**: 作者指出内置对象一般都是 window 下的属性，因此可以转化为 `window["Date"]` 这种形式来访问，这里的 `Date` 是一个字符串，可以进行加密与拼接。
- **结论**: 同一条"先可加密化"的规则在另一类对象上重复出现——不是特例，是通用前置动作。
- **结果**: 不做这层改造，内置对象的加密与换名无处下手；做了之后，`Date` 才能进入与普通属性相同的字符串池流程（第8章 PAGE 174）。

### 案例 3：用行尾注释标出"关键那一行"（第9章 PAGE 188）
- **问题**: 逐行加密只想保护关键几行，但自动流程不知道哪一行是关键。
- **方法论的使用**: 源码行尾手写 `//Base64Encrypt`，在 AST 里表现为 `trailingComments` 节点；逐行解析时加判断，如果有注释且值为 `Base64Encrypt` 就加密，处理完再 `delete v.trailingComments` 抹掉标记。Base64 与 ASCII 两种方案各用一个标记。
- **结论**: 注释是"人工指定保护范围"的锚点；标记必须删，否则既留下特征又暴露加密意图。
- **结果**: 混淆器可以只处理带标记的语句，其余保持可读；这条同时印证了作者的判断——自动化看不出业务语义，关键性必须人来给（第9章 PAGE 188）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队要自研 JS 混淆器，需求是"只保护 sign 算法那几十行，其余保持可读便于维护"。
2. 混淆器产物一启动就崩，报某个方法名取不到、或数组还没就绪。
3. 纠结要不要整文件逐行加密，觉得"覆盖面越大越安全"。
4. 装配顺序拿不准：先加密还是先改名、常量层插在哪。
5. 评估第三方混淆器：层数很多，但不知道强度是否成比例，想加更多层。

### 与相邻 skill 的区分

- 与 `sign-reproduce-acceptance` 的区别: 那边验参数值复现是否正确；本 skill 只保证产物可运行、保护面收敛，不评价算法是否被破解。
- 与 `constant-fold-and-decoding` 的区别: 那边把加密的常量还原；本 skill 决定加密什么、放在哪一层、哪些层不值得上。

## E — 可执行步骤 (Execution)

顺序的根源是数据依赖：字符串必须先"变成数据"才可加密；引导代码必须先运行，所以不能进池；标识符必须先定名，逐行加密才不会把它一起固化；关键行必须先被人标出，脚本才有作用对象。

1. **划出"必须保护"的行**
   - 完成标准: 有一份明确的行清单（签名、时间戳、随机源、核心拼接），并由业务方确认。
   - 判停条件: 说不清哪几行关键 → 停止。关键性属业务语义，AST 看不到；先做业务梳理，不要写"智能判断"的脚本。

2. **可加密化改造**
   - 完成标准: 目标行的属性访问全部改成下标形式，内置对象改成 `window['Date']` 一类；改造后代码仍可运行。
   - 判停条件: 存在无法字符串化的语法成分（关键字、解构简写、私有字段）→ 记录下来并接受它不可加密，不要硬改语义。

3. **立引导代码白名单**
   - 完成标准: 数组乱序还原函数、解密函数、分发器构造被显式排除在抽池与加密之外；产物启动可运行。
   - 判停条件: 产物启动即崩、报方法名或数组取不到 → 回退该段，先确认它是否被误提进池，再继续。

4. **给关键行打锚点**
   - 完成标准: 关键行带 `//Base64Encrypt` 或等价标记，脚本只处理带标记的语句，处理完 `delete trailingComments`；产物里搜不到标记字符串。
   - 判停条件: 需要"自动判断哪行关键" → 不做，交回人工；这条是作者明确承认的自动化边界。

5. **按依赖顺序装配**
   - 完成标准: 标识符混淆 → 逐行加密 → 其它常量层；装配后 `generate`/`parse` 成功，关键函数可运行。
   - 判停条件: 顺序颠倒（先加密后改名）导致密文里含待改标识符、或改名改不动 → 回退重排，不要打补丁绕过。

6. **强度复核：按造价/拆价裁剪层数**
   - 完成标准: 逐项记录每层的造价与拆价；对核心几十行优先保留平坦化与标识符混淆，属性下标/hex 只作点缀。
   - 判停条件: 增加某层的唯一理由是"层数更多" → 不加；造贵拆廉的层堆多了只会拖慢自己。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目标是还原别人的混淆样本——那是 `obfuscation-fingerprint-triage` 与各还原 skill，本 skill 只负责"造"。
- 只是想压缩体积或格式化代码——那是 minifier/beautifier 的工作，不是混淆。
- 需要运行期反调试与 Hook 对抗（`toString` 检测、循环 `debugger`）——超出本 skill；书中该节还建立在 MV2 常驻后台假设上，现代 Chrome 已不适用。
- 关键行无法由人确定——本 skill 明确承认自动化做不到，先补业务输入而不是硬写规则。
- 目标环境依赖 wasm、瑞数类商业方案——书中零分析，本 skill 无对应约束可给。

### 作者在书中警告的失败模式

- 代码逐行加密的方案不建议大规模应用，会导致标志太明显；应只隐藏其中几句代码或某些变量的关键赋值位置（第9章 PAGE 188）。
- 自动化处理过程中无法知道一段代码是否为关键代码，除非用户在代码中加入标记（第9章 PAGE 188）。
- 引导代码（乱序还原函数自身）用到的字符串若进了池，会变成"解密前先解密"，脚本启动即崩（第6章 PAGE 104–105）；造侧只能 hex 编码、保留可执行性（第8章 PAGE 181）。
- 逐行加密会把代码中的标识符一起加密，所以必须放在标识符混淆之后（第9章 PAGE 206）。
- 点号访问的属性名是标识符，必须明确出现在代码中，不能加密和拼接（第6章 PAGE 97）。

### 作者的盲点 / 时代局限

- 样本量 = 1：第9章的混淆器是作者自写玩具（PAGE 190–197），靶站大概率按同一模板生成；"用自己的混淆器喂自己的还原器"是循环论证，不能证明方法通用（BOOK_OVERVIEW 批判节）。
- 2021 环境快照：未覆盖 wasm、瑞数（全书仅 PAGE 82 点名）、MV3；现代站点的 SRI/CSP 会让"替换回站"这一验收档大面积不可达。
- 只站混淆器作者视角，没有回答"我怎么检测别人在还原我"；检测正则给了，哪些写法会命中没给（BOOK_OVERVIEW）。
- 合规与伦理零覆盖：未讨论 robots、ToS、数据性质；第10章还给出 cookie 全量劫持（PAGE 216），与"保护自有代码"的正当用途不是一回事。
- 强度只用"造价/拆价对称"这一条启发式，无实测数据；"堆层不是线性增益"没有量化，也没有对照实验。

### 容易混淆的邻近方法论

- minifier（如 terser）的 mangle：也会改名，但目标是体积与执行速度；本 skill 的目标是延迟阅读，且额外要求引导代码白名单与关键行锚点。
- 商用混淆器（如 javascript-obfuscator）：提供控制流平坦化、字符串数组、死代码注入等现成开关；本 skill 给的是"选哪几项 + 顺序 + 保护面"，不是工具参数手册。
- 代码水印/指纹：在代码里埋可识别标记以便追溯；与"行尾注释锚点"形似但目的相反——锚点必须抹掉，水印必须保留。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。混淆只应用于保护自有代码或已获授权的交付物，不得用于规避平台规则、隐藏恶意载荷或对抗安全审计。
