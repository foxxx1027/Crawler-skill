# 混淆指纹判别与投入估算：先判层，再决定投不投

## R — 原文 (Reading)

> 常规的混淆方法都是有迹可循的，主要有数组混淆、数组乱序、字符串混淆和switch流程控制平坦化等。
>
> — 李岳阳、卓斌, 第5章「常规的混淆方法」, PAGE 86

---

## I — 方法论骨架 (Interpretation)

这一步发生在动手之前，产出不是代码，而是判断。

混淆手法是有限且可枚举的，所以先用结构证据把"用了哪几层"列清楚，再决定投入——而不是看到乱码就从第一行啃。

七条可验指纹：①文件头部一个几百项的大数组，紧邻一个自执行函数；②引用处形如 _0xabcd('0x1f')，靠索引取明文；③顶部有 '1|2|4|7|5|3|8|0|6' 这类字符串被 split 成分发器；④while(!![])+switch 的控制流；⑤RegExp.test(fn.toString()) 的自检；⑥push(Math.random()) 这类内存爆破；⑦二级对象间接，对象套对象逐层取值。

命中哪条，就对应哪类还原动作；没命中，就对应"这一步可以整步跳过"。指纹的缺席本身是信息，它决定跳过什么，而不只决定做什么。

强度按造/拆对称性估，而不是按层数：属性下标、hex、逗号这类"造贵拆廉"，还原代价低；平坦化与标识符混淆接近对称，最贵；堆更多层不是线性增益。

先判"是加密还是混淆"：还原后若只有 substr/concat 与常量、没有密码学运算，且服务端只按位置或长度校验，就把"解密"降级为"拼接"。

最后只交三件事：层清单、可跳过步骤、投入量级。

## A1 — 书中的应用 (Past Application)

### 案例 1：验证码站样本——看结构，先分类再验证
- **问题**: 打开样本只看到一坨不可读代码，不知道从哪下手。
- **方法论的使用**: 先看结构不看内容：首行是长度 353 的字符串数组，判为数组混淆；紧跟的函数体里有 push 与 shift，判为带乱序还原；再往后的函数体调用 atob，判为字符串 base64 加密。
- **结论**: 这份文件至少三层——数组混淆、数组乱序、字符串加密，第一动作是解字符串池，不是读业务。
- **结果**: 在还原函数后断点，对比运行前后数组顺序，顺序变化证实乱序函数；atob 作为固定锚点可直接拿明文（第5章 PAGE 86–87）。作者同时点明：只抽数组不打乱时 arr[0] 就是固定映射，混淆归零（PAGE 86）——有指纹不等于有效。

### 案例 2：format 函数逐级改造——同一函数上的四层强度阶梯
- **问题**: 同一段 Date.prototype.format 被反复改造，怎么判断它改造到第几层。
- **方法论的使用**: 按层识别：层 1 只动常量（属性变字符串下标、hex/unicode、数值异或）；层 2 动结构（抽大数组、乱序还原、花指令）；层 3 动流程（switch 平坦化、逗号表达式）；层 4 加执行期对抗（eval 加密、内存爆破、格式化检测）。
- **结论**: 层越高越需要 AST 自动化；层 1–2 手工还能应付，层 3 起手工成本陡增。
- **结果**: 用同一函数逐级改造，验证四层可叠加且每层语义等价（第6章 PAGE 103–118）。

### 案例 3：真实靶站——按七条指纹排手段清单，并把"解密"降级为"拼接"
- **问题**: 靶站 lebo.yzm.pc.min.js 体积大、手段混杂，怎么排还原顺序；data 是长随机串，拿不准要不要按密码学去逆。
- **方法论的使用**: 按七条指纹逐条核对，先列出"有哪些手段"再决定顺序，未命中的指纹对应步骤直接跳过；对 data 再用"还原后有无密码学运算"判据检查。
- **结论**: data 还原后只有 substr/concat 与常量，服务端靠 $strlen 定位真实索引，属混淆而非加密。
- **结果**: 把"解密"降级为"拼接"，省掉整段算法逆向（第11章 PAGE 224–231、PAGE 249）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 打开样本，第一行就是几百项字符串数组，后面全是 _0x1234(0x1f)。
2. 代码里有 while(!![]) + switch，case 里一堆 continue，看不出真实执行顺序。
3. 文件里出现 function(){...}.toString() 与正则比对，或有不断 push 的死循环。
4. 某个参数是长随机串，拿不准是加密还是编码或混淆，犹豫要不要上算法分析。
5. 需要回答"这套混淆大概要几天能还原"，要给量级而不是拍脑袋。

### 语言信号 (用户的话里出现这些就应激活)

- "混淆 / obfuscated / deobfuscate"
- "一坨乱码 / 完全看不懂 / unreadable"
- "用了哪几种混淆 / which obfuscation techniques"
- "大数组 / string array / 字符串池"
- "_0x / 变量名都是下划线"
- "分发器 / dispatcher / split('|')"
- "平坦化 / control flow flattening / while(!![])"
- "还原成本 / 值不值得逆 / how long to reverse"
- "加密还是混淆 / encryption or obfuscation"
- "toString 检测 / 内存爆破 / OOM"

### 与相邻 skill 的区分

- 与 `data-path-cost-ladder` 的区别: 后者按取数路径（打印版、接口、浏览器）降成本；本 skill 按混淆层与造拆对称性估逆向成本。
- 与 `ast-restore-pipeline-acceptance` 的区别: 后者管"按什么顺序还原、怎么验收"；本 skill 只做判层与取舍，输出清单交给它。
- 与 `sign-reproduce-acceptance` 的区别: 后者验单参数复现值；本 skill 不进入复现环节。
- 与 `fetch-tier-triage` 的区别: 后者选请求档位（请求库、浏览器、隐身浏览器）；本 skill 选还原档位（不还原、局部还原、全量还原）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先排除"这不是混淆"**
   - 完成标准: 能明确指认是压缩（minified）、编码（base64/hex/unicode），还是确有密码学运算。
   - 判停条件: 若只是编码，直接解码即可，不进入还原流程。

2. **取样本头部与 50–100 行，逐条对七指纹**
   - 完成标准: 每条指纹标记"命中（附证据行）/ 未命中 / 待确认"，不允许写"可能"。

3. **把命中项映射成层与动作**
   - 完成标准: 产出一份层清单与对应动作清单（数组→解池、乱序→还原函数、分发器→重排、自检→先摘检测）。

4. **生成"可跳过步骤"清单**
   - 完成标准: 每个未命中指纹都对应一条跳过理由。
   - 判停条件: 若只有层 1 指纹，不做 AST 流水线，直接本地求值或复现。

5. **估投入并给出取舍**
   - 完成标准: 按造拆对称性排序（平坦化 ≫ 属性下标 > 编码），给出"放弃 / 只还原关键函数 / 全量还原"三选一，并写理由。

6. **输出交接口**
   - 完成标准: 一张"指纹 → 层 → 动作 → 成本 → 跳过理由"表，可直接交给还原流水线或复现验收。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 脚本还没拿到、抓不到包，或页面数据其实在接口里而不在脚本里——先解决通道与取数路径。
- 需要跑出真实结果、要执行或 Hook 运行时——那是动态调试，不是静态判层。
- 目标每次访问下发不同脚本（瑞数类动态混淆），静态指纹只能判"这一份样本"，不能当站点结论。
- 只想验某个参数的复现值对不对——不涉及判层。

### 作者在书中警告的失败模式

- 只抽数组不打乱：arr[0] 就是第一个元素，下标与值一一对应，缺少乱序即混淆归零（PAGE 86）。
- 逐行加密全量铺开：文件里全是同构的 eval 与长串调用，标志太明显，解密脚本一写就全解（PAGE 188）。
- 在 DevTools 里格式化不会触发格式化检测，只有把格式化结果落盘再加载才触发，并被导向内存爆破（PAGE 118）。
- 把"层数多"当强度：作者的成本观是"原本一小时变几天"，堆层不是线性增益（PAGE 119、PAGE 206）。

### 作者的盲点 / 时代局限

- 七条指纹来自同一靶站与作者自造的混淆器（样本量 = 1），是"这本教材用过的形"，不是穷举清单；未见指纹不等于没混淆（BOOK_OVERVIEW 批判节）。
- 未覆盖瑞数类动态混淆、wasm/Rust 编译型加密与商业壳的分层加载（PAGE 82 仅点名）；这些目标上静态指纹会大面积失效。
- 2021 年快照（Babel parser 7.9.4、Chrome 79）：现代打包器会做字符串数组加密与分片加载，简单 grep 式判层已不够。
- 书中未说"哪些写法会命中检测正则"，因此"有指纹 = 能还原"这一步并未被证明（BOOK_OVERVIEW 批判节）。

### 容易混淆的邻近方法论

- `data-path-cost-ladder`——取数路径成本，不是逆向成本。
- `fetch-tier-triage`——请求档位，不是还原档位。
- `ast-restore-pipeline-acceptance`——层清单的消费者，负责顺序与验收。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
