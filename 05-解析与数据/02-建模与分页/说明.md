# 02 建模与分页

## 解决什么

两件容易被低估的事：**表结构**（要回答什么问题、什么唯一标识对象，怎么让接第 N 个站不用改表）与**翻页验收**（日志翻了几十页、库里只有一页的量，怎么定位）。

## 触发信号（用户原话）

- "该抓哪些字段 / 表怎么建"
- "每接一个站就要改表"
- "翻页脚本跑完了，数据只有一页"
- "不知道分页有没有真的推进"
- "去重之后条数对不上"

## 包含的 skill

| skill | 作用 | 来源 | 何时调用 |
|---|---|---|---|
| `requirements-first-data-model` | 四道闸（项目要回答什么、什么唯一标识对象）→ 把"怎么抓"（每站一条配置）与"抓到什么"（统一内容对象）分离；稀疏属性进 attributes 表；主键用自增 id | 权威指南 2e | 写爬虫前、或要扩到几十个站 |
| `pagination-acceptance` | 三件套验收：最终 URL 含偏移（提成断言）、条数对账（页数×每页 = 去重后条数，±1 页）、去重键确认；按故障签名分诊 | Python项目案例 | 翻页跑完但量不对 |

## 类内先后

建模在前（决定字段与唯一键），分页验收在后（用唯一键对账）。顺序反了会出现"翻页对不上，但其实是去重键选错"的误诊。

## 故障签名（`pagination-acceptance` 的核心）

| 现象 | 根因 |
|---|---|
| 每页条数与内容都相同 | 请求没变（偏移没带上） |
| URL 在变，条数不符 | 游标没回填，或去重键错 |
| 日志页数正常、库里少 | 去重键把不同对象合并了 |

## 内容速览

- "统一内容对象 + 每站一条配置"是多站扩展的唯一可持续结构；每站一张表必然越改越乱。
- 翻页验收的锚是**唯一键**，不是总条数。
- ±1 页是正常边界（末页可能不满），超过就是逻辑问题。

## 使用示例

### 示例 1：接 30 个电商站，每接一个就改表
**用户说**：「我要比价 30 个电商站，现在每接一个站就得改一次表结构。」

**路由**：`requirements-first-data-model`。

**执行**：
1. 四道闸：这个项目要回答什么问题（实时比价？历史价格？）；什么唯一标识一个商品（站点 + 站内商品 id）。
2. 拆分：**怎么抓**写成"每站一条配置"（入口 URL、字段映射）；**抓到什么**统一成一张内容对象表。
3. 稀疏属性（只有某站有的字段）进 `attributes` 表，不往主表加列。
4. 主键用自增 id，站点内 id 作为业务唯一键。

**产出**：一张统一 items 表 + 30 行站点配置；第 31 个站接入时只加配置、不改表。

### 示例 2：翻了 40 页，库里 20 条
**用户说**：「日志显示翻了 40 页，数据库里只有 20 条。」

**路由**：`pagination-acceptance` —— 用故障签名分诊，不要先怀疑网络。

**执行**：① 看最终 URL 是否真的带上了偏移（提成断言）；② 抽查两页内容是否完全相同（相同 = 请求没变）；③ 若 URL 在变但条数不符 → 游标没回填或去重键选错；④ 对账：页数 × 每页 ≈ 去重后条数（允许 ±1 页）。

**产出**：一条明确的根因 + 修好的分页参数或去重键。
