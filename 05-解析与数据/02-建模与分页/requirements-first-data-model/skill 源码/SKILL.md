# 数据模型需求先行

## R — 原文 (Reading)

> • 这个信息可以帮助项目实现目标吗？如果我不包括该信息，是否会造成阻碍？还是说该信息有了固然好，但是并不会影响任何结果？
> • 如果该信息将来可能有帮助，但是我并不确定，那么晚些时候再抓取会有多大的困难？
> • 这个数据对于我已经抓取的信息来说是否冗余？
> • 将数据存储在这个对象中是否符合逻辑？
>
> — 瑞安·米切尔，《Python网络爬虫权威指南（第2版）》第4章 4.2，p.43

> 注意，这里Website 类并不存储任何从页面本身抓取的信息，而是存储关于如何抓取数据的指令。…… 这就是这个类被命名为Website（它包含适用于整个网站的信息）而不是Content（它包含来自单个网页的信息）的原因。
>
> — 瑞安·米切尔，《Python网络爬虫权威指南（第2版）》第4章 4.3，p.47

## I — 方法论骨架 (Interpretation)

绝大多数人是"打开网站，看看有哪些字段，然后建表"。作者要求反过来: 先把网站忘掉，问"这个项目要回答什么问题"。

第一步是字段取舍，每个候选字段过四道闸: 缺了它能否达成目标；如果现在不抓、晚点再抓有多难；它对我已抓到的信息是否冗余；把它放在这个对象里是否合逻辑。四道闸的作用是把"我想要"和"我必要"分开，而不是把所有看得见的字段都搬进库。

第二步是判稀疏: 只有少数记录才有的属性（面料、颜色、签证、远程、股权）不进主表，统一放进一张 key-value 的稀疏表或字典；每个站点都有的字段才进主表。

第三步是把两张表分开: 一张描述"怎么抓"（起始 URL、列表/详情选择器、URL 正则、是否绝对 URL、字段映射），一张描述"抓到什么"（统一的 Content/Product 对象）。前者的值是指令（字符串 `h1`），后者的值才是数据。这样新增一个站点 = 加一条配置 + 一段映射，而不是写一个新解析函数；配置甚至能交给非程序员填。

第四步是落库纪律: 每张表都加自增 id 主键（你并不知道哪些字段唯一）；只为会被频繁查询的字段建索引；把重复出现的值（同一条 URL、同一个词组）抽成独立表 + 关系表，而不是每发现一次就插一行。

整个方法论的评价指标只有一个: 新增一个数据源的边际成本。不是"这一站能不能抓"，而是"第 51 个站要改几行代码"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 商品字段的取舍
- **问题**: 跨站点抓商品，页面上可见字段很多（描述、评分、价格、颜色、材质），不知道哪些该进统一对象。
- **方法论的使用**: 对每个候选字段过四道闸: 缺了能否达成目标、晚点抓有多难、是否冗余、放在 Product 对象里是否合逻辑（p.43）。
- **结论**: 产品名称/制造商/ID 等跨店通用且能标识对象；评论、评分、价格是"特定商店的特定产品"；颜色、材质是"特定于产品但稀疏"。
- **结果**: 通用字段进主对象，商店相关字段单独保存，稀疏属性另用容器承载，避免了"每个站一套字段"。

### 案例 2: Website 与 Content 的职责分离
- **问题**: 每接一个新站点就要写一套新的抓取函数，代码越堆越多。
- **方法论的使用**: 明确 Website 只存"怎么抓"的指令（它存的是字符串 `h1`，不是标题本身），Content 只存"抓到什么"（p.47）。
- **结论**: 抓取指令被数据化之后，新增站点从"写函数"变成"加配置"。
- **结果**: 作者用同一套 Crawler 抓不同站点，只换 Website 实例，验证了"配置驱动"的可行性。

### 案例 3: 存储按查询设计
- **问题**: 词频项目要存"每条记录里的每个词"，直接存会导致大量重复与查询缓慢。
- **方法论的使用**: 先问"哪些值会重复、将来怎么查"，再把数据拆成 phrases / urls / foundInstances 三张表；每张表加自增 id 主键，只为高频查询字段建索引（p.84–85）。
- **结论**: 建索引会占空间、拖慢插入，所以索引要按查询方式建，而不是"能建就建"。
- **结果**: 数据库体积与查询时间都落在可控范围；同一纪律后来又被用于"页面 + 链接"的关系建模（pages / links(fromPageId, toPageId)，p.86）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 刚开始一个抓取项目，正准备"先看看网站有什么字段再建表"。
2. 要一次覆盖几十个同类站点（招聘、电商、房产），担心每接一个站就要改表。
3. 发现某些字段只有少数记录才有（签证、远程、股权、面料），不知道放主表还是另存。
4. 表已经建了，但每加一个新源就要 ALTER TABLE 或复制一份解析函数。
5. 在纠结"这个字段现在不抓，以后还来得及吗"。

### 语言信号 (用户的话里出现这些就应激活)

- "字段怎么选 / 哪些字段要存"
- "表结构怎么设计 / schema"
- "50 个站点，怎么设计才能每个新站只加配置"
- "这个字段只有部分商品有，放哪"
- "data model / sparse attributes / ETL schema / 边际成本"

### 与相邻 skill 的区分

- 与 `semantic-selector-robustness` 的区别: 那个解决"字段怎么稳定地取出来"；本 skill 解决"到底要取哪些字段、取出来放哪"。先定模型，再写选择器。
- 与 `page-owned-api-recon` 的区别: 那个解决"数据从哪条通道取"；本 skill 解决"取到的数据用什么结构承载"。
- 与 `crawl-scope-and-halt` 的区别: 那个管"抓多大范围、什么时候停"；本 skill 管"抓到的内容怎么建模"，两者常在同一项目里前后使用。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行:

1. **写出项目要回答的问题**
   - 完成标准: 用 1–3 句话说明"这批数据要支持什么判断/分析"，并能据此判断某个字段是否必要。

2. **过四道闸筛字段**
   - 完成标准: 每个候选字段标注"必要/可延后/冗余/不该放这里"，并写明理由；没有未分类字段。
   - 判停条件: 若某个字段"晚点抓代价很高"，标记为必须现在抓。

3. **拆分主对象与稀疏属性**
   - 完成标准: 给出主表字段清单（所有源通用、能标识对象）与 attributes 稀疏表结构（objectId, key, value），并说明哪些查询需要 pivot。

4. **分离"怎么抓"与"抓到什么"**
   - 完成标准: 产出两套结构: 站点配置（起始 URL、列表/详情选择器、URL 正则、字段映射、绝对 URL 标志）与统一内容对象；新增一个源只需加配置。

5. **定落库纪律**
   - 完成标准: 每表有自增 id 主键；索引清单与查询语句一一对应；重复值已抽表或已论证不需要。

6. **用"第 51 个源"做验收**
   - 完成标准: 假设新增一个同类型站点，写出需要改动的文件与行数；若超过"一条配置 + 一段映射"，回到步骤 3 重新拆分。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 只有一次性的几十条数据、不打算复用: 直接抓成 CSV，不必设计 schema。
- schema 已经确定，只差把字段取出来: 转 `semantic-selector-robustness`，再讨论模型是返工。
- 数据来源只有一个、字段永远不变: 过度抽象（稀疏表 + 配置层）会增加无谓复杂度。

### 作者在书中警告的失败模式

- "先看网站有什么字段再建表": 会让模型跟着某个站点长，新增站点时被迫改表（p.42–43）。
- 把抓取指令和抓取结果混在一个类里: 换站就得改代码，而不是加配置（p.47）。
- 给每个字段都建索引: 索引占空间、拖慢插入，应按查询建（p.84）。

### 作者的盲点 / 时代局限

- 本书成书于 2017–2018，代码用的是 Scrapy 1.x 的 `scrapy.contrib.*` 导入路径（已废弃），具体实现需按现代 Scrapy 改写；Website/Content 分离、稀疏属性表、自增 id、按查询建索引这些结构判断不受版本影响。
- 书中没有涉及 JSON Schema / Pydantic 之类的运行时校验，也没有增量更新、数据版本与去重合并；现代项目应补上"入库前校验 + 版本字段"。
- 作者的建模示例以电商与词频为主，未覆盖多租户、权限字段、审计字段等企业级需求；把这些直接套到含个人信息的模型上，会踩合规问题（见 `scraping-compliance-layering`）。
- "新增一个源的边际成本"这一指标在书中只是主张，没有给出可量化的验收方法；本 skill 用"第 51 个源改几行"把它变成可执行检查。

### 容易混淆的邻近方法论

- "规范化"与"先建模型"不是同一件事: 规范化是存储层的纪律，需求先行是字段层的取舍，两者要分开做。
- "字段越多越好"与"只抓必要字段"是两种默认；本方法论明确站在后者。
