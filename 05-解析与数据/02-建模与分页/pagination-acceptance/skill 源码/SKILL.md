# 分页验收与条数对账

## R — 原文 (Reading)

> if pageNum>0:
>  start=(pageNum-1) *20
> else:
>  return False
> requrl='https://movie.douban.com/subject/' + movieId + '/comments'
>
> — 郑秋生、夏敏捷, 第20章 20.4 完整程序, PAGE 408

---

## I — 方法论骨架 (Interpretation)

1. **分页最常见的失败不是报错，而是"每页都返回同一页"**：代码不抛异常、日志有 N 行、正文写着"爬了 N 页"，而库里只有一页的量。所以分页必须被验收，不能被相信。
2. **为什么不能凭"数据看起来少"判断**：没有对账就没有可观测差异。书里正是凭感觉写下"比较有参考价值"（PAGE 407），而没有数过实际条数。
3. **三件套之一：最终 URL 必须含偏移**。把它提成断言（`assert 'start=' in url`）或每轮打印完整 URL。变量名对、赋值对，都不等于进了请求串——这是本书 bug 的全部内容。
4. **三件套之二：条数对账**。页数 × 每页条数 = 去重后条数，允许 ±1 页容差（末页不足、解析失败被跳过的条目会正常造成少量偏差）。对不上就把"每页条数"和"唯一键"分别打印。
5. **三件套之三：去重键**。键选错（拿标题、时间、正文前 N 字当键）会把不同页的条目合并，制造"只有一页"的假象；键选得太细又会把同一页的重复条目当成新数据。
6. **故障签名固定，按三条依次反查**：每页条数相同且首条 id 相同 → 请求没变（偏移算了没拼、或没回填）；URL 每轮在变但条数对不上 → 游标没回填，或把页序号当成了偏移；URL 与返回都在变、去重后仍少 → 真只有这么多条，或"循环跑了 N 次"被当成"抓了 N 页"。
7. **口径要写清**：`start` 是记录下标（默认 0），`page` 是页码；两者混用会跳页、重叠或永远停在第 1 页。
8. **上限必须本地化**：服务端返回的 `has_more`/`next` 不能替代本地上限——服务端异常时 `has_more` 会永远为真。本地上限 + 当前游标要显式成变量。
9. **验收通过才谈数据质量**：条数对不上时，后面的清洗、分词、词云全部无意义；对上了再交给下游评估。

## A1 — 书中的应用 (Past Application)

### 案例 1: 豆瓣评论——算了 start 却没拼进 URL
- **问题**: 作者要抓 10 页豆瓣短评做词云，但第 1 页只有 20 条，需要翻页。
- **方法论的使用**: 按三件套回查——① 打印每轮最终 URL，发现停在 `/comments`，没有任何 `?start=`；② 每轮条数都是 20、首条评论 id 相同；③ 对账 10 × 20 = 200，实际参与词频的约 20 条。
- **结论**: 命中死变量签名"每页条数相同且内容相同 = 请求没变"。`start` 算出来了，但 `requrl` 没有接上它；运行不报错，日志也不打印 URL 差异，所以错误只表现为"数据少"。
- **结果**: `for i in range(10)` 的十次请求全部命中第 1 页；正文却写"由于前面只是爬取了第1页的评论，所以数据有点少，在最后给出的完整代码中爬取了10页的评论，所得数据比较有参考价值。"（PAGE 407）修法是把 `start` 拼进 `requrl`、加 `assert 'start=' in url`，再用条数对账复核。

### 案例 2: 百度图片递归翻页——上限与游标显式化
- **问题**: 顺着"下一页"递归抓图，担心停不下来，也担心漏页。
- **方法论的使用**: 用两个全局量把终止显式化——`MaxSearchPage=20` 是上限、`CurrentPage` 是当前游标（每下一页 +1，超上限不再递归）；另有 `nextSource(content)` 判断是否还有下一页。
- **结论**: 上限与游标必须独立于"有没有下一页"这个隐式条件；站点异常时它可能永远有下一页。原文："MaxSearchPage=20 / #搜索页数 / CurrentPage=0 / #当前正在搜索的页数"（PAGE 149）
- **结果**: 递归被限制在 20 页内，不会跑飞。缺的一半是验收：作者没有把"页数 × 每页 = 实际落盘条数"写进流程，所以漏抓与翻页失效都无法被发现（PAGE 146–151）。

### 案例 3: start 是记录下标，不是页码
- **问题**: 评论接口默认只返回 20 条，想要更多。
- **方法论的使用**: 改 `start` 参数：`start=40&limit=20` 表示从第 40 条开始取 20 条，步长等于每页条数，而不是页码 +1。
- **结论**: `start` 是偏移量（默认 0），`page` 是页码；把页码当 `start` 会跳页、重叠，或永远停在第 1 页。
- **结果**: 原文明确了用法："这样仅仅获取了20个影评，可以指定开始号 start 来获取更多影评"（PAGE 397）；但同一章的完整程序没有把这个结论落进请求串（PAGE 408），讲解与实现自相矛盾。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 循环翻页脚本跑完，日志写"共 40 页"，库里只有几百条且 id 看起来是同一批。
2. 不确定分页参数到底有没有生效：代码里算了偏移，但从没打印过最终请求 URL。
3. 服务端返回 `has_more`/`next` 游标，不知道该不该信、怎么回填给下一轮。
4. 抓到的条数比预期少，分不清是"站点只有这么多"还是"翻页没推进"。
5. `start`/`page`/`offset` 混用，出现跳页、重叠或分页循环不终止。

### 语言信号 (用户的话里出现这些就应激活)

- "跑了十页，数据只有一页的量"
- "每页返回的内容好像都一样"
- "start 算了，但不知道有没有用上"
- "has_more 一直是 true，停不下来"
- "抓到的条数和页数对不上"
- "all pages return the same items"
- "pagination is not advancing"
- "the start offset seems ignored"
- "has_more is always true"
- "page count vs row count mismatch"

### 与相邻 skill 的区分

- 与 `crawl-scope-and-halt` 的区别: 后者管"抓多大范围、跟不跟外链、什么时候停"；本 skill 只管"每一页是否真的推进"，用故障签名与条数对账定位静默故障，不管范围裁剪。
- 与 `requirements-first-data-model` 的区别: 后者先定"抓哪些字段、唯一键是什么、表怎么建"；本 skill 借用去重键做验收，但不设计数据模型。
- 与 `semantic-selector-robustness` 的区别: 后者解决"页内节点解析对不对"；本 skill 解决"页与页之间有没有换"。选择器全对，也可能十页都是同一页。
- 与 `form-hidden-state-and-readback` 的区别: 两者共享"写后回读断言"的精神，但那个回读的是表单提交后的页面状态；本 skill 回读的是请求串（URL 含偏移）与返回条数。
- 与 `http-request-replication` 的区别: 后者解决单条请求重放不出来（头/体/会话/编码）；本 skill 假设单条已通，只在多轮之间查偏移有没有真的进 URL。
- 与 `page-owned-api-recon` 的区别: 后者负责找到页面自用的接口并把五要素归档；本 skill 在接口已找到之后验收"每一页是否真的换了"，不重复做定位。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先让每轮请求可观测**
   - 完成标准: 每轮日志包含完整请求 URL（含 query）、本轮条数、本轮首条与末条的唯一键值。
   - 判停条件: 若现有脚本没有这些日志，先加日志再判断；不得凭"数据看起来少"下结论。

2. **断言偏移出现在最终 URL 里**
   - 完成标准: 每轮 URL 都含偏移参数，且数值随轮次按步长变化；断言写成代码（`assert` 或运行期检查），不是注释。
   - 判停条件: URL 不变 → 修拼接/回填（变量赋值后是否真的被引用），修完回到步骤 1 重跑；修不了则本页无法翻动，停。

3. **逐轮比对返回，命中故障签名**
   - 完成标准: 对相邻两轮给出明确结论——条数是否相同、首条唯一键是否相同、响应结构是否相同。
   - 判停条件: URL 在变但返回同批 → 查游标回填（上一轮返回值是否喂给下一轮）与页码/偏移口径；URL 不变且返回同批 → 回到步骤 2。

4. **做条数对账**
   - 完成标准: 算出"页数 × 每页条数"与"去重后条数"，差值在 ±1 页容差内；把每页条数与唯一键同时打印。
   - 判停条件: 超差且唯一键可疑（如用标题/时间当键）→ 换键复算；换键仍对不上 → 回到步骤 2 检查偏移是否真的生效。

5. **校准口径与上限**
   - 完成标准: 明确 `start`/`offset` 是记录下标还是页码、步长是多少；本地上限与当前游标是独立变量，不依赖服务端 `has_more`/`next`。
   - 判停条件: 服务端游标异常（永远 true、或返回空 next）→ 以本地上限停止，并记录"服务端游标不可信"这一结论。

6. **固化验收结论并交接**
   - 完成标准: 输出一行可复核的结论（页数 N × 每页 M = 去重 K，±1 容差），写进脚本或运行报告；异常轮次的 URL 与原因留档。
   - 判停条件: 验收未过不得交给下游清洗/评估；通过后才转 `small-sample-eval` 或数据模型设计。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没确定要抓多大范围、要不要跟外链、何时整体停止: 用 `crawl-scope-and-halt`，本 skill 只验收"单条翻页链有没有推进"。
- 字段与唯一键还没定: 先走 `requirements-first-data-model`，否则"去重键"无从选，对账也算不准。
- 单条请求本身重放不通（401/403/结构不符）: 先用 `http-request-replication` 把一条请求调通，再谈翻页。

### 作者在书中警告的失败模式

- 分页参数算了却没拼进 URL：十次请求全部命中第 1 页，正文却宣称"爬取了10页的评论"，词云实际只基于约 20 条（PAGE 407–408）。
- 把"没有下一页"当唯一终止条件：站点异常时它永远有下一页，递归会跑飞；作者用 `MaxSearchPage` 显式上限来防（PAGE 149）。
- 凭感觉判断数据量：不数条数、不对账，只用"比较有参考价值"这类主观表述收尾（PAGE 407）。
- 讲解与实现脱节：同一章先讲清 `start` 是偏移（PAGE 397），完整程序却没把它落进请求串（PAGE 408）——文档与代码分头维护，读者无法判断哪份是真的。

### 作者的盲点与时代局限

- 无并发、无限速：第20章是串行 `for i in range(10)`（PAGE 408），既慢也无法在并发下暴露"请求相同"的问题；全书无线程池、限速器。
- 异常被吞、无日志：`try/except: continue` 遍布（PAGE 122、131、142、150），没有失败计数与失败队列，"漏抓多少"永远未知，验收因此缺少输入。
- 无验收机制：全书无断言、无对账、无测试；唯一的质量判断是运行截图。
- 样本量极小：声称 10 页、实际约 20 条（PAGE 407–409），结论强度被高估。
- 平台与接口无可用性承诺：第三方接口随对方改版失效（PAGE 143–149），分页参数口径也可能随之改变，本书没有版本/口径记录。

### 容易混淆的邻近方法论

- "检查一下分页参数"不等于验收；本 skill 要求把偏移写进断言、把条数写成等式。
- `has_more`/`next` 是服务端游标，不是本地上限；把终止权交给服务端，异常时就停不下来。
- "`start` = 页码"是常见误用；偏移与页码是两种口径，混用会产生跳页与重叠。

### 合规红线

- 仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
- 不对目标站做高频试探：验收用的重放应控制在个位数请求，发现服务端游标异常时以本地上限停止，而不是加大请求量。
