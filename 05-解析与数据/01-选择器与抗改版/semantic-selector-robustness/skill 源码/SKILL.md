# 语义选择器稳健性与抽取方法选型

## R — 原文 (Reading)

> 以上的代码是不安全的，它依赖于网站的结构永远不变。
>
> — 瑞安·米切尔，《Python网络爬虫权威指南（第2版）》，第2章，p.13–14

> 如果对你来说速度不是问题，并且更希望只使用pip 安装库的话，那么使用较慢的方法（如Beautiful Soup）也不成问题。如果只需抓取少量数据，并且想要避免额外依赖的话，那么正则表达式可能更加适合。不过，通常情况下，lxml 是抓取数据的最佳选择，这是因为该方法既快速又健壮……
>
> — 凯瑟琳·雅姆尔、理查德·劳森，《用Python写网络爬虫（第2版）》，第2章，p.51

## I — 方法论骨架 (Interpretation)

解析器会不会"活下来"，取决于两件事，顺序不能颠倒。

**先选工具，再选锚点。** 工具层看三个量：这个解析器要跑几次、一次要取多少字段、能不能接受多一个第三方依赖。只跑一次、字段少、想避免装库，用正则就够了；量小、想快速看懂结构，用 BeautifulSoup；要长期跑、字段多，用 lxml（CSS 选择器或 XPath）。速度差来自实现语言（lxml 与正则是 C，BeautifulSoup 是纯 Python），但网络才是真正的瓶颈，别为微秒级差异牺牲可读性。

**锚点层看的是"绑定了什么"。** 优先级从高到低：id/class/语义属性 → 父子与兄弟关系 → 标签名 → 第几个元素。位置索引（`find_all('table')[4].find_all('tr')[2]`）编码的是当前这张页面快照的编号，页面加一列或加个 div 就全部错位，甚至直接抛出 AttributeError。

**过滤层要反过来归纳。** 不要枚举"什么不是目标"（那会长成上百行的特例判断），而是先看一批正样本，找出它们共同的二三条特征，压成一条规则。

**写之前先在浏览器里验一次。** jQuery/CSS 用 `$()`，XPath 用 `$x()`，在控制台里改到"返回数量和预期一致"再落进 Python，把调试成本从"跑一遍爬虫"降到"敲一行选择器"。

**最后留一道校验。** 元素数为 0 或关键字段为空时必须显式失败或记异常日志，否则改版后程序会静默返回错行——这比崩溃更难查。

## A1 — 书中的应用 (Past Application)

### 案例 1: 深链位置选择器——能跑，但一次改版就死
- **问题**: 作者要说明"不经考虑就写选择器"的代价，举了一个能从深层标签里取到目标的行。
- **方法论的使用**: 把 `bs.find_all('table')[4].find_all('tr')[2].find('td').find_all('div')[1].find('a')` 作为反例，逐项指出它依赖了表格序号、行序号、div 序号。
- **结论**: 这样的代码"依赖于网站的结构永远不变"；管理员加一张表、加一列、或在顶部加几个 div，它就会失效，甚至毁掉整个爬虫。
- **结果**: 作者先给出四条替代路径（打印版/移动版、JS 文件里的内嵌数据、从 URL slug 取、换数据源），并声明只有这些都走不通时才进入解析章节。

### 案例 2: 只有一张表也要写 id
- **问题**: 抓取示例站的礼物表格，直接 `bs.table.tr` 或 `bs.tr` 也能拿到正确的第一行。
- **方法论的使用**: 作者仍然写成 `bs.find('table', {'id':'giftList'}).tr`，并解释为什么宁可写长一点。
- **结论**: "即使页面上只有一个表格（或其他目标标签），只用标签也很容易丢失细节"；页面布局会变，某个标签今天是第一行，明天可能就在第三行。
- **结果**: 形成一条可复用的规则——"如果想让你的爬虫更稳定，最好还是让标签的选择更加具体。如果有属性，就利用标签的属性。"

### 案例 3: 朋友写了 100 多行过滤函数，作者用三条共同点压成一条正则
- **问题**: 判断维基百科内链是不是词条页链接；朋友的做法是写一个超过 100 行的过滤函数，逐个排除。
- **方法论的使用**: 作者改为观察一批"词条链接"样本，归纳出三个共同点：都在 `id=bodyContent` 的 div 里、URL 不含冒号、URL 以 `/wiki/` 开头。
- **结论**: 三条共同点足以把"词条链接"和"分类页/讨论页/页脚链接"分开，写成 `^(/wiki/)((?!:).)*$`。
- **结果**: 一条正则替代上百行枚举，且新增页面类型时不必再补特例。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **选型阶段**：手里有一个页面要取字段，在正则、BeautifulSoup、lxml/XPath 之间犹豫，或问"哪个快/哪个稳/要不要装 lxml"。
2. **改版失效**：昨天还能抓，今天抓空、抓到别的行、报 `AttributeError: 'NoneType' object has no attribute ...`。
3. **写过滤条件**：要判断"这条链接/这段文字算不算目标"，第一反应是写一长串 if/else 或黑名单。
4. **前端混淆**：目标站的 class 是 `css-1a2b3c` 这类构建哈希，或结构由框架动态生成，找不到稳定锚点。
5. **复用与交接**：解析代码要交给别人维护，或要接第二个同类站点，需要判断当前写法能不能撑住。

### 语言信号 (用户的话里出现这些就应激活)

- "这个选择器怎么写才不容易坏" / "改版之后抓不到了" / "抓到的是错的行"
- "用正则还是 BeautifulSoup" / "lxml 和 bs4 选哪个" / "XPath 还是 CSS selector"
- "class 是随机哈希" / "nth-child 能不能用" / "只有一张表要不要写 id"
- "regex or BeautifulSoup" / "selector keeps breaking" / "site redesign broke my scraper" / "which parser is more robust"

### 与相邻 skill 的区分

- 与 `data-path-cost-ladder` 的区别: 那个 skill 在**写解析器之前**回答"要不要解析 HTML"（换页面版本、找 JS 内嵌数据、调内部接口、上浏览器）；本 skill 只在"已经确定要解析 HTML"之后回答"怎么绑锚点、用哪个库"。若三类锚点都不稳，应退回那个阶梯，而不是继续加固选择器。
- 与 `page-owned-api-recon` 的区别: 那个 skill 解决"数据其实来自 XHR/内嵌 JSON，怎么把那条通道找出来"；本 skill 处理的是服务器已经把数据渲染进 HTML 的情形。
- 与 `requirements-first-data-model` 的区别: 那个管"取哪些字段、怎么建表"；本 skill 管"每个字段在这张页面上怎么定位"。

## E — 可执行步骤 (Execution)

1. **定工具：先回答三个量**
   - 问清"这个解析器跑几次、一次取几个字段、能否新增依赖"。
   - 完成标准: 能写出一句选型理由（如"长期跑 + 14 个字段 + 可装库 → lxml/XPath"），而不是"顺手用哪个"。
   - 判停条件: 若发现数据其实不在 HTML 里（关掉 JS 后目标消失），停止本流程，转 `data-path-cost-ladder`。

2. **采样本：至少 3–5 个同类页面，含 1 个异类**
   - 覆盖同类页面的不同版式（列表页/详情页/空结果页），记录每个页面里目标元素的 id/class/语义属性/父子兄弟关系。
   - 完成标准: 得到一张锚点清单，且已显式剔除"构建哈希 class"和"第 N 个元素"这两类伪锚点。

3. **定锚点链：按优先级拼，不跳级**
   - 顺序为 语义属性（id/class/aria-*/data-*/role）→ 稳定父容器 + 关系（第几个同类兄弟、相邻标题）→ 标签名 → 位置索引。
   - 完成标准: 选择器里最多只有一处位置索引，且该处有注释说明为何无法避免。
   - 判停条件: 若找不到任何稳定锚点（全是哈希 class + 动态 DOM），跳到步骤 6。

4. **控制台预验证**
   - CSS/jQuery 用 `$('...')`，XPath 用 `$x('...')`，在真实页面上跑，比对返回元素数量与预期。
   - 完成标准: 控制台返回数量与手工点数一致，且抽 1 个元素核对文本内容无误。

5. **写过滤规则：先找模式，再写正则**
   - 从正样本里提炼 2–3 条共同特征，压成一条规则；若规则里出现"或"串联的多个特例，回到样本重新归纳。
   - 完成标准: 一条规则能同时命中全部正样本、且不命中已知反例（如分类页/页脚链接）。
   - 判停条件: 若正样本本身没有共同点（说明"目标"定义不清），先回去和用户确认字段定义。

6. **加校验与失败面**
   - 取数后断言元素数量、关键字段非空；异常时记录 URL + 选择器 + 期望/实际数量。
   - 完成标准: 人为删掉目标元素后，程序报错或写日志，而不是静默返回空/错行。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **数据不在 HTML 里**: 关掉 JS 后目标消失、页面只有模板壳，说明要的是 `page-owned-api-recon` 或 `data-path-cost-ladder`，加固选择器无效。
- **只取一次、量极小**: 手动复制或用一次性的 `Ctrl+F` 就够了，写解析器是过度工程。
- **已有官方结构化出口**: 站点提供 API/CSV/RSS/sitemap 时，直接读结构化数据，别解析渲染后的 HTML。
- **需要跨站点统一模型**: 那是 `requirements-first-data-model` 的职责，本 skill 只解决单页定位。

### 作者在书中警告的失败模式

- 用位置索引链（`find_all('table')[4].find_all('tr')[2]`）——"依赖于网站的结构永远不变"（p.14）。
- 只用标签名、不写属性——"即使页面上只有一个表格，只用标签也很容易丢失细节"（p.21）。
- 混淆子标签与后代标签——`find_all` 默认抓所有后代，取表格行要用 `.children` / `.next_siblings`，否则会把嵌套表格的行一起抓进来（p.20–21）。
- 用一个 `try` 包住多行解析——首行异常会吞掉后续所有字段，"你无法识别出究竟是哪行代码抛出了异常"（p.35）。
- 逐个枚举"什么不是目标"——朋友那 100 多行的过滤函数就是反例（p.29–30）。

### 作者的盲点 / 时代局限

- **只假设"改版"，没假设"对抗"**: 书中把解析风险归为布局变化，未讨论动态混淆 class 名、随机化 DOM、按 UA 返回不同内容——这些会让"稳定锚点"本身被主动破坏。
- **CSS-in-JS / Shadow DOM / 框架渲染未覆盖**: 哈希 class、Web Component 封闭树在成书时尚未普遍；本 skill 的"剔除哈希 class、找语义属性"是对原原则的现代外推。
- **库与语法已变**: `findAll` 驼峰写法、`scrapy.contrib.*`、Selenium `find_element_by_*` 均已废弃；原则（绑语义、控制台预验证）不受影响，代码需按现代 API 改写。
- **性能结论有前提**: "lxml 最快最稳"是在单页多字段、可装 C 依赖的前提下成立；纯 Python 环境或只需一个字段时，结论要重算。
- **全书层面的时代局限**: 重型渲染方案默认 PhantomJS（2018 年 3 月已停止维护）；反爬认知只到 UA/限速/换 IP，未涉及 TLS 指纹与 JS challenge；合规讨论是纯美国法框架（DMCA/CFAA），不覆盖 GDPR 与中国的《网络安全法》《数据安全法》《个人信息保护法》。

### 容易混淆的邻近方法论

- **XPath vs CSS 选择器**: 不是"哪个更高级"，而是"这个页面哪种表达更短、更稳"；lxml 内部会把 CSS 转成 XPath，二者能力接近。
- **"语义选择器" vs "数据模型"**: 前者是定位手段，后者是字段定义；字段没定清就写选择器，会反复返工。
- **"先找模式" vs "写黑名单"**: 前者是提取不变量，后者是排除特例；黑名单会随反例增长而无上限。
