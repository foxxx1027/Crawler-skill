# 自适应选择器维护闭环

## R — 原文 (Reading)

> 自适应抓取（Adaptive 以前称为自动匹配）是抓取最强大的功能之一。通过记录元素身份特征（标签、属性、结构、内容等），网站改版后自动重定位元素，大幅降低维护成本。
>
> — 《爬虫-Scrapling》中文文档汇编, p52「自适应抓取」

> 自适应准确率：常规 CSS 改版准确率≥90%，页面大规模重构时准确率下降，关键任务建议人工校验。
>
> — 同上, p7「常见问题」

---

## I — 方法论骨架 (Interpretation)

它不是一个“改版后自动帮我修好”的按钮，而是一套**两段式**机制：先存档，后重定位。

第一段在建站/上线时：抓到目标元素时顺手把它的“身份特征”（标签、属性、结构位置、内容）写进本地存档。这一步是入口，没有存档，后面的一切都不会发生——所以“改版之后才想起开自适应”在机制上是空转。

第二段在改版之后：把存档拿来与当前 DOM 做相似度匹配，返回“最像的那个元素”。注意措辞：**最像**，不是“对的那个”，也不是“找不到就报错”。相似度算法没有失败语义，找不到时也会给出一个答案，于是**失败会伪装成成功**——返回空、返回错元素、返回数量骤减，都可能是“正常返回值”。

由此得到本方法论的重心：**重定位只能当召回器，不能当答案**。跑一遍拿到候选集，但不上线；用一套与相似度无关的验收去判它到底对不对。验收对象必须是**可验算的值**——带量纲、可交叉比对的字段（价格、库存、评分、条数、分布），而不是“有没有抓到东西”。因为“抓到了”恰恰是这个机制最容易假装做到的事。

验收不过，就回退到手工选择器，并**重建存档**（用回退后的选择器重新 auto_save）；而不是继续调阈值、放宽相似度把结果凑出来。阈值越低只会让“最像”更不像。

文档给了一个可信区间：常规 CSS 改版可用，大规模重构会掉。这决定了**先分类改版类型、再决定信不信自适应**的顺序——分类在前，工具在后。

## A1 — 书中的应用 (Past Application)

> 说明：本书无真实项目复盘。下列是文档内的调用示例，均跑在练习站/虚构靶场，属**文档示例，非真实项目结果**，未验证真实改版与反爬条件下的表现。

### 案例 1: 两段式调用的最小示例（p53）
- **问题**: 文档要演示“改版前后怎么用”这一机制。
- **方法论的使用**: 第一次抓取 `page.css(".product", auto_save=True)` 存特征；结构变化后 `page.css(".product", adaptive=True)` 重定位。前置还给了两种全局开关（`Selector(html_doc, adaptive=True)`、`Fetcher.adaptive = True`）。
- **结论**: 机制是“先存后用”的配对调用，auto_save 是入口而非可选优化。
- **结果**: 文档止于调用形式，未给命中率、未给失败样例、未说明返回“最像元素”时的判别方式。

### 案例 2: 相似度定位的扩样演示（p117–119）
- **问题**: 如何从“一个已知卡片”扩展到整组同构元素。
- **方法论的使用**: p117 先用 `find_by_text('Add to Cart')` 找到锚点，`find_ancestor(lambda e: e.has_class('product-card'))` 升到容器，再 `find_similar()` 扩样，最后从每个卡片取 name / price / stock / rating；p118、p119 给出表格行、表单字段容器的同类套路。
- **结论**: 相似度扩样的可用前提是“同构”——同一容器结构重复出现。
- **结果**: 示例站为虚构靶场（example.com / example.com 系），未验证改版能力；`find_similar` 的结果直接进入抽取列表，没有验收环节——这正是本 skill 要补的那一环。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 目标站改版后，原选择器返回空、条数骤减或字段错位，用户想“一次修好并防止再犯”。
2. 用户手里有改版前的抓取基线，问“能不能开 adaptive 直接顶上，还是得先做什么”。
3. 用户已经开了自适应，但发现“跑得通、数据不对”（价格串了、库存全 False、评分缺失），怀疑重定位到了错元素。
4. 站点换了前端框架：类名哈希化、卡片外多包一层 wrapper、同一组件多实例，用户仍想沿用旧存档。
5. 关键任务（价格监控、库存告警）上线前，需要判断“这套定位逻辑值不值得托付”。

### 语言信号 (用户的话里出现这些就应激活)

- “网站改版了，选择器全失效 / selector broke / 抓不到数据了”
- “要不要开 adaptive / auto_save 怎么用 / 重定位准不准”
- “开了自适应但数据不对 / 抓到的是别的元素 / 条数变少了”
- “类名变成哈希了 / 外面多套了一层 div / 页面整个重构了”
- “≥90% 这个数能信吗 / 关键任务敢不敢用”

### 与相邻 skill 的区分

- 与 `anti-bot-triage-and-human-parity` 的区别：本 skill 处理“页面结构变了、元素定位失效”，前提是**已经能正常拿到 HTML**；后者处理“请求被拦截、拿到的是挑战页/空壳”。若拿到的响应本身就不对，先走后者。
- 与 `data-path-cost-ladder` 的区别：本 skill 处在“数据已能取到、定位逻辑需要长期维护”这一层；取数路径与成本的取舍由后者决定。
- 与“选择器写法速查”（本书判定不足以独立成 skill 的部分）的区别：本 skill 不教 CSS/XPath 语法，只管道定位的存档、验收与回退流程。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **先分类改版类型，再决定信不信自适应**
   - 动作: 对照改版前后的 DOM，判断属于“常规 CSS 改动”（局部类名/层级微调）还是“大规模重构”（类名哈希化、组件多实例、Shadow DOM、整体换框架）。
   - 完成标准: 产出一句分类结论 + 两条以上证据（例如类名是否仍语义化、容器层级是否改变、同类结构是否仍重复出现）。
   - 判停条件: 若判为大规模重构 → 直接跳到步骤 5（回退手工选择器 + 重建存档），不要先试自适应再判断。

2. **确认存档存在且与本次基线对应**
   - 动作: 检查是否有改版前 `auto_save=True` 留下的特征存档，且存档对应的选择器就是失效的那一个。
   - 完成标准: 明确回答“有对应存档 / 无存档”。无存档则自适应不可用——此时不得“事后补开”，直接进步骤 5。

3. **把重定位当召回跑一遍（不上线）**
   - 动作: 用 `adaptive=True` 跑一次，只收集候选集，不写入生产数据。
   - 完成标准: 记录三个数：命中条数、与改版前基线条数的比值、命中元素的结构摘要（标签/关键属性）抽样若干。

4. **独立验收：用可验算字段核对，而不是“有没有抓到”**
   - 动作: 从存档/基线中取带量纲、可交叉比对的字段（价格、库存布尔、评分、时间、条数分布）抽样核对；同时检查条数与分布是否突变（例如突然只剩首屏 10 条、或翻倍出现重复）。
   - 完成标准: 给出逐项核对表（字段 / 抽样值 / 是否合理 / 异常原因），并明确“通过 / 不通过”。
   - 判停条件: 任一可验算字段系统性错误、或条数与分布突变且无法解释 → 判为不通过，进步骤 5；通过则进步骤 6。

5. **回退手工选择器并重建存档（不要靠调阈值凑结果）**
   - 动作: 用当前 DOM 手工写出新选择器，验证其稳定取到目标元素后，以 `auto_save=True` 重新存档；记录本次回退原因（哪类改版、哪个字段先坏）。
   - 完成标准: 新选择器在多次抓取中稳定返回预期条数与字段；新存档已落盘并与新选择器绑定。

6. **上线并留下回归信号**
   - 动作: 生产启用新逻辑，同时设置最小回归检查：条数阈值、关键字段非空率、抽样值与人工基线比对。
   - 完成标准: 回归检查可被下一次改版直接触发，输出“哪一项先越界”，使下一轮能直接进入步骤 1 而不是重新摸底。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 拿到的响应本身就不对（拦截页、空壳、登录墙）——那是取数/反爬问题，先走 `anti-bot-triage-and-human-parity`，不是选择器问题。
- 目标站属企业级反爬（Akamai、DataDome 一类）——本工具对这类拦截方无原生绕过方案，维护闭环不能建立在“绕过拦截”之上，先解决能否稳定取到页面。
- 没有改版前存档却想“事后开启自适应”——机制上无效（p52–53 的入口是 auto_save），只能手工重写并重建存档。
- 想用它“预判”改版、免掉验收——相似度没有失败语义，跳过验收等于让错误静默进入数据。
- 未授权目标——本 skill **仅限自有系统、已授权目标或公开测试环境**。

### 作者在书中警告的失败模式

- **把 ≥90% 当阈值契约**：p7 的“常规 CSS 改版准确率≥90%”无样本量、无站点类型分布、无误报后果，且同一句就写了“大规模重构时准确率下降”；它是厂商自述的一个锚点，不是可依赖的 SLA。把它当承诺，就会在重构场景下无声地吃到错误数据。
- **把“重定位成功”当“定位正确”**：p117–119 的 `find_similar()` 扩样示例直接进入抽取列表，没有独立验收；书里没有“重定位到错元素”的检测动作，这一环必须自建。
- **把扩样当前置步骤**：`find_similar` 依赖“同构”，同构被破坏时它会返回“最像”的一批，而不是报错。

### 作者的盲点 / 时代局限

- **结构同构前提在组件化前端下被削弱**：类名哈希化、同一组件多实例、Shadow DOM 已普遍，文档完全未讨论；这类站点应默认按“大规模重构”处理。
- **p121–141 教程章的 API 与正文冲突**（`Fetcher.fetch()` / `.browse()` 被当成动态方案、`.text()` 被当方法、`find_all('article.news-item')` 传 CSS 字符串、`fetcher.session()`）——该段是外部/生成内容，未经与正文核对。凡引用该段代码，照抄即踩坑，必须回正文（p8–13 / p47 / p54）二次校验；本 skill 的示例一律取自正文，不取教程段。
- **全书无失效检测设计**：没有“何时判定自适应失效、如何回滚”的章节，也没有成本/误报分析；步骤 4、6 的验收与回归是 skill 自建，不得声称来自文档。
- **合规被降格为开关**：robots.txt 只是可选标志，文档未讨论 ToS、数据留存与站点负载。

### 容易混淆的邻近方法论

- 与 `anti-bot-triage-and-human-parity`：本 skill 是“结构变了”的维护闭环；后者是“被拦了”的分诊。
- 与 `data-path-cost-ladder`：本 skill 在“已能取到页面”之后做定位维护；后者做取数路径取舍。
- 与“相似元素扩样套路”（本书判定不足以独立成 skill 的部分）：扩样只是本闭环里的一次召回动作，不构成方法论主体。
