# 01 锚点定位

## 解决什么

不知道目标函数在哪，但手上有一个"已知锚点"。锚点四类：**文件格式/协议关键字或错误文本**（搜字符串）、**公开符号表或类方法名**（搜函数名）、**崩溃或报错里出现的消息**（搜引用文本）、**格式规范里的字段语义**（把数字标注成字段）。命中锚点后用交叉引用直接落到函数入口，跳过逐层回溯。

## 触发信号

- "不知道 sign 在哪个函数算的"
- "没有符号表，怎么找那个校验函数"
- "字符串搜到了，但不知道谁调用它"
- "这个常量 0x5f3759df 是什么意思"

## 包含的 skill

| skill | 作用 |
|---|---|
| `locate-by-known-anchor` | 按锚点类型选检索方式（strings / 符号 / 交叉引用 / 格式字段），一步落到目标函数 |

## 与相邻子类的分工

| 情况 | 去哪 |
|---|---|
| 有锚点，要直达 | 本子类 |
| 没有任何锚点，只能从行为/崩溃逆推 | `03-反爬对抗与逆向/01-通道与封禁` 先造锚点 |
| 有锚点但函数体看不懂 | `02-静态审计` |

## 内容速览

- 先找"人写的字符串"，再找"机器生成的常量"。人写的字符串（报错、header 名、参数名）命中率最高。
- 交叉引用（xref）是核心动作：字符串 → 引用它的代码 → 调用它的函数 → 参数来源。
- 一个锚点命中多个候选时，用"调用栈深度 + 参数形态"筛，别逐个读。

## 使用示例

**用户说**：「页面请求带 `sign=` 参数，我在 JS 里搜 `sign` 出来 300 个结果。」

**执行**：换成更独特的锚点——搜 header 名、搜 `invalid sign` / `签名错误` 这类报错文本、搜 appKey 常量 → 交叉引用到调用点 → 观察调用点的入参是不是 `(token, t, data)` 三元组 → 命中生成函数。

**产出**：生成函数地址/文件位置 + 入参来源清单（哪个变量来自 cookie，哪个来自时间戳）。
