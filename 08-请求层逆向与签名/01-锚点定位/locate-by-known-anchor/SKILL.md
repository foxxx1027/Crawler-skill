# 用已知锚点跳步定位

## R — 原文 (Reading)

> "用 IDA 反汇编 CoolType.dll 库，查看字符串可发现"SING"字体，因为该字符串是漏洞解析出错的地方，直接定位进去即可查看该库对 sing 表格的解析方式。"
>
> — 林桠泉，《漏洞战争：软件漏洞分析精要》第 2 章 2.3.4

配套引文（符号不可用时的替代锚点，第 5 章 5.4.2）：

> "通常情况下，输出文本消息的函数往往就是导致格式化字符串的漏洞函数。"

## I — 方法论骨架 (Interpretation)

定位不一定要"顺着调用链一步步走"。只要手上有一个**能把地址锚定下来的已知量**，就可以跳步直达目标函数，再由动态验证确认。作者用了一整本书的量在运用这个思路，锚点可分四类：

1. **字符串 / 特征码 / 指令序列（不依赖符号）**
   - 解析型漏洞先搜格式关键字：TTF 的 `"SING"` 表名、协议关键字、错误提示文本。
   - 栈已破坏、页堆也定位不了时，抓"崩溃时程序输出的那条文本"，搜它的引用处（"所有参考文本字串"），落回打印/格式化函数——**格式化字符串漏洞必然发生在输出处**。
   - 定位成功后，把该函数的**机器码特征**（如 `89 58 10 89 5F 1C`）记录下来，形成后续可复用的锚点。
   - 补丁比较全失配时，改搜"漏洞指令序列"（如 `8B 04 81`）并利用"同版本各函数地址波动多在 0xFFF 内"在邻近地址搜索。

2. **符号表与类/方法命名（依赖符号，最精准）**
   - 加载厂商符号表后，`sub_XXXX` 会还原为有意义的函数名（`midiOutPlayNextPolyEvent`），IDA 与 WinDbg 都适用。
   - 微软命名法本身是一张免费索引：类方法名为 `C<Class>::put_<Prop>` / `get_<Prop>`。在 IDA Functions Window（`Alt+T`）搜属性名或类名片段（`runtimestyle`、`cachesize`、`dashstyle`+`put`）往往能唯一定位到处理该属性的类方法。
   - **前提**是知道目标函数属于哪个 DLL——这可以靠公开的类/属性/方法列表站点 + `site:` 语法检索确定候选，再逐个下断点验证谁被命中。

3. **文件格式规范（把数字翻译成语义）**
   - 输入数据里的 `0x68` 是长度、计数还是坐标，**看汇编永远看不出来**。必须先取格式规范（如 Cinepak/CVID stream format），按 Frame Header / 编码条 / Chunk 的字段定义把 PoC 字节逐字段标注，再与调试中读到的寄存器/栈值一一对应。
   - 有了字段语义，才能看懂代码里每一次 `cmp/jb` 在检查什么，进而判断哪一处检查缺失导致越界。
   - 特殊情形：RTF 中以内嵌文本形式存放的 OLE 数据不被解析器识别时，把从 OLE 签名（`D0CF11E0`）起到结尾的数据按十六进制另存为 `.doc`，即可被 OffVis 正常解析。

4. **派生锚点：结构体偏移（在无符号时）**
   - 用读写断点记录某偏移被写入/读取的时机，结合旧版本公开源码（如 IE5 的类定义）交叉验证，逐步为该偏移赋语义。

**共同纪律**：锚点法给出的是**候选**，必须用"下断点看谁被命中"来收口；不要因为"名字像"就直接认定。

## A1 — 书中的应用 (Past Application)

### 案例 1: CVE-2010-2883（Adobe Reader TTF SING 表栈溢出）
- **问题**: 拿到 PDF 样本，不知道 CoolType.dll 里哪段代码解析出问题。
- **方法论的使用**: 在 IDA 里搜字符串 `"SING"`（漏洞解析出错处的表名），顺交叉引用跳到 sing 表解析代码。
- **结论**: 该处用 `strcat` 拼接时未做长度限制。
- **结果**: 一次搜索即锁定解析函数，避免通读整个字体库。

### 案例 2: CVE-2012-0809（Sudo 格式化字符串）/ CVE-2012-3569（VMware OVF Tool）
- **问题**: 崩溃时栈空间已被破坏，栈回溯失效，开页堆也定位不了（格式化字符串漏洞的特征）。
- **方法论的使用**: 抓崩溃前程序输出的文本作为锚点，在调试器中搜索该字符串的引用，定位到引用它的函数，再单步跟到真正的打印函数。
- **结论**: 输出文本的函数即漏洞函数（可控格式化串被当作格式串）。
- **结果**: 在两条常规路径都失效时仍完成定位。

### 案例 3: CVE-2013-2551（IE VML）— 按类函数名直落 put_length
- **问题**: 需要找到 JS 属性 `dashstyle` 内部对应的 IE 类方法。
- **方法论的使用**: 在 IDA Functions Window 用 `Alt+T` 搜 `runtimestyle` 得到唯一命中 `COARuntimeStyle`；再按属性名与 `put`/`get` 命名法定位到 `COALineDashStyleArray::put_length`。
- **结论**: 真正写入异常值的是 `put_length`（长度被设为 -1），而非崩溃处的 `get_item`。
- **结果**: 跳步直达真正的漏洞函数。

### 案例 4: CVE-2010-2553（Cinepak）— 格式规范把 0x68 变成"编码条数量"
- **问题**: PoC 里的 `0x68` 无法判断语义。
- **方法论的使用**: 查 AVI/Cinepak 的 CVID stream format 规范，按字段定义标注 PoC 字节，再与调试中读到的值对应。
- **结论**: `0x68` 是编码条数量；代码对该数量缺少上限校验。
- **结果**: 补丁（强制 ≤3）与根因形成闭环。

### 案例 5: CVE-2011-2110（Flash 数组越界）— 指令序列 + 邻近地址
- **问题**: 补丁把整个漏洞函数删除/重排，BinDiff 找不到匹配函数。
- **方法论的使用**: 搜漏洞指令序列 `8B 04 81` 是否仍存在；因版本相近、函数地址波动多在 `0xFFF` 内，优先在原地址附近搜索。
- **结论**: 找到后被加了"索引不得大于数组元素个数"的判断，该处即修复代码。
- **结果**: 在函数匹配完全失效时仍定位到修复点。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 崩溃时栈不可信 / 栈已破坏，但程序**打印了某条文本或错误码**。
2. 有符号表或可在线获取类/属性/方法列表，想把"JS 属性用法"直接对到"二进制实现函数"。
3. 分析文件解析类漏洞，但不知道输入里的某个数字是长度、计数还是坐标。
4. 之前费力定位到某函数，想把它固化成以后能直接搜的锚点。
5. 补丁比较工具匹配失败，需要靠指令序列 + 邻近地址找修复点。

### 语言信号 (用户的话里出现这些就应激活)

- "怎么从 PoC 里的这个值找到解析函数"
- "没有符号表怎么办 / 怎么看到函数名"
- "按名字搜函数 / 搜字符串定位"
- "这个字段到底是什么意思 / 格式字段对不上"
- "栈回溯不可用，还有别的切入点吗"
- "find the function by string / symbol name / IDA search"

### 与相邻 skill 的区分

- 与 `crash-to-root-cause` 的区别: 后者从崩溃**逐层回溯**；本 skill 靠**锚点跳步**。选择依据是"手上有没有已知量"。
- 与 `heap-vulnerability-locating` 的区别: 涉及 gflags/页堆/分配记录 → 后者；涉及字符串/符号/格式规范 → 本 skill。
- 与 `patch-diff-and-source-analysis` 的区别: 本 skill 的"搜指令序列"是补丁比较**失败时**的退路；若补丁比较工具可用，走后者。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **清点可用锚点（按可靠性排序）**
   - 完成标准: 列出至少一个可用锚点并标注其类型与可靠性：符号名（高）> 类/方法命名（高）> 格式规范字段（高）> 特殊字符串/错误文本（中）> 指令序列（中）。

2. **锚点定位（按类型取路）**
   - 字符串类: 在反汇编器中搜字符串 → 看 Xrefs → 跳到解析/输出代码。
   - 符号类: 先确定目标属于哪个 DLL（可用 `site:` 语法查公开类列表）→ 加载符号表 → `Alt+T` 搜业务关键字 → 得到候选函数列表。
   - 格式类: 取格式规范 → 把样本字节逐字段标注 → 与调试中的寄存器/栈值对齐。
   - 完成标准: 得到 1–3 个**候选函数**，而不是"整段代码"。

3. **动态收口（必须做，不可省）**
   - 方法: 对候选函数逐个下断点（注意用"符号+偏移"，不要用绝对地址），执行 PoC，看谁被命中且参数与输入相关。
   - 完成标准: 命中唯一目标函数，且能说明其参数如何来自 PoC。
   - 判停条件: 若全部候选都未命中 → 回步骤 1 换锚点类型（例如从符号转向字符串/指令序列）。

4. **确认根因位置（区分"触发"与"写入"）**
   - 方法: 若命中函数表现为"读越界/触发异常"，继续向上找"写入该异常值的函数"（如从 `get_*` 找 `put_*`）。
   - 完成标准: 明确哪一处是"写入异常值"的真正漏洞点。

5. **固化锚点（可复用资产）**
   - 完成标准: 记录该函数的机器码特征片段或稳定字符串引用，写入分析笔记，供下次直接搜索。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **没有任何已知锚点**（无字符串、无符号、无格式资料、无输出文本）→ 走 `crash-to-root-cause`。
- **目标已剥离符号且字符串被加密/混淆**（常见于加壳样本）→ 先脱壳/解密，再回到本 skill。
- **无法获取格式规范且样本为私有格式** → 格式类锚点不成立，需改用对照实验（改样本字段观察行为变化）。

### 作者在书中警告的失败模式

- 特征微弱的函数难以靠直接搜机器码定位（g07-ce02）。
- 目标无符号表时，直接在调试器中定位内存结构极其复杂（g07-ce05）。
- 盲信 IDA F5 反编译结果——偏移显示可能是错的（g08a-ce02）。
- 直接对含无关内容的 PDF 对象执行解码会失败（g07-ce01）。
- 补丁把函数删除/重排后，BinDiff 匹配失效（g04-ce03）。

### 作者的盲点 / 时代局限

- **锚点体系强依赖"符号/字符串可见"**：作者的时代（2010–2015）商业软件大量带符号、样本未强混淆。当代环境中符号广泛剥离、字符串普遍加密、符号服务器访问受限，本 skill 的第 2 类锚点可靠性显著下降。
- **未涉及自动化工具链**：今天可用 Ghidra/IDA 的签名库、BinDiff 的下一代替代（如 Diaphora）、以及 LLM 辅助的函数命名，作者均未讨论。
- **"格式规范"假设可得**：私有格式或被裁剪的格式规范会让该类锚点直接失效。
- **完全缺席 fuzzing**：本 skill 的定位发生在"已有样本"之后；在现代流程中它通常服务于"fuzzer 产出崩溃 → 快速圈定函数"这一步。

### 容易混淆的邻近方法论

- "搜索"≠本方法：差异在于**先按可靠性对锚点排序、并用动态命中收口**，而不是随便搜到就当真。
