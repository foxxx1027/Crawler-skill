# 03 数据流与污点

## 解决什么

一个值在代码里传了七八手：从一个 cookie 读出来，经过拼接、编码、截断、再加盐，最后进了签名。这一子类建立**数据流图 / 污点传播**，回答两个问题：这个值从哪来、它到哪去。

## 触发信号

- "token 到底是从 cookie 读的还是接口返回的"
- "这个参数看着是常量，其实每次都在变"
- "扫描器报了一个污点流，是不是误报"
- "改了某个字段签名就不对了，是哪个环节用到它"

## 包含的 skill

| skill | 作用 |
|---|---|
| `dataflow-analysis-and-code-modeling` | 基本块 / CFG / SSA / 调用图 / PDG，数据流方程迭代到不动点，函数摘要 |
| `taint-analysis` | 定义污点源（source）、传播规则、汇聚点（sink）与净化函数，判可达性 |

## 方法

1. 定 source：cookie / localStorage / 接口字段 / 用户输入。
2. 定 sink：签名函数、加密函数、请求参数拼装点。
3. 传播：赋值、拼接、编码（base64/hex/urlencode）、切片、哈希。
4. 净化（sanitizer）：真正把污点清掉的函数——通常不存在，只是变形。
5. 判可达：从 source 到 sink 有没有一条不断的路。

## 与相邻子类的分工

| 情况 | 去哪 |

| 要直接命中函数 | `01-锚点定位` |

## 内容速览

- 编码不是净化：base64/hex 只是把污点换了形态，仍然是污点。
- 签名函数几乎必然是 sink：找到它，反推 source 是最快路径。
- 只看静态容易漏"运行时注入的常量"（时间戳、随机数），这类必须在动态里采。

## 使用示例

**用户说**：「请求里的 `t` 和 `sign` 每次都不一样，不知道谁生成的。」

**执行**：以 `sign` 为 sink 反向切片 → 追到 `md5(a + "&" + b + "&" + c + "&" + d)` → 逐个 source 回溯源：`a` 来自 `_m_h5_tk` cookie，`b` 是毫秒时间戳，`c` 是固定 appKey，`d` 是请求体 JSON 串 → 四个 source 全部落地即可复现。

**产出**：source→sink 路径表（四行），每行标注来源与变换链。
