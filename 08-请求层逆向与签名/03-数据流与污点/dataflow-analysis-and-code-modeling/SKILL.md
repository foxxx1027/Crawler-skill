# 数据流分析与代码建模

## R — 原文 (Reading)

> 数据流分析是一种用来获取特定数据沿着程序执行路径流动的信息分析技术，其目的是获取程序执行路径上的数据流动过程和数据的可能取值。漏洞分析通常需要确定数据的流动过程和数据的性质，如SQL注入漏洞分析中，需要确定某个变量的取值是否源自非可信数据源；
>
> — 魏强、武泽慧，《逆向与漏洞分析》第4章 4.1.1 基本概念

---

## I — 方法论骨架 (Interpretation)

1. 先把线性指令变成可推理的图：按入口语句（首句、跳转目标、条件跳转后继）切出极大基本块，再按跳转关系连边得到 CFG。
2. 在 CFG 上按需升级代码模型：SSA 用重命名与 φ 函数让每个使用点只对应一个定值；调用图描述函数间可能调用；PDG 同时承载数据依赖与控制依赖。
3. 为要回答的问题写数据流方程，四要素固定为：分析方向（正向/逆向）、值的格与汇合算子、每个基本块的 Gen/Kill、传递函数 Out=f(In)。
4. 先问结论要多强：Must（所有路径成立）在汇合处取交集，May（至少一条路径成立）取并集；量词选错，方程就会写反。
5. 给每个基本块的 In/Out 一个初值，沿 CFG 反复迭代到所有值不再变化，即不动点；循环是必须处理的核心障碍。
6. 函数内先算局部 Gen/Kill，再做全局遍历；重复进入同一基本块时，前置条件相同就复用已有结果。
7. 函数间用摘要复用：为库函数或已分析函数记录前置/后置条件，调用点匹配前置条件后直接用后置条件续推，避免重扫函数体。
8. 上下文敏感会提高精度，但递归与深层调用必须用 k-CFA、折叠递归环或调用深度上限控制状态爆炸。
9. 漏洞规则有两条落法：变量状态类漏洞写成有限状态自动机（危险状态为接受态），取值类漏洞写成程序点上的取值约束（如目的缓冲区长度 ≥ 源串长度）。
10. 分析结果始终是上近似：它回答“可能发生什么”，不自动证明“真实可达”；报告必须与路径可行性、动态证据或样本核对。

## A1 — 书中的应用 (Past Application)

### 案例 1: 阶乘圆周长程序的基本块划分与 CFG 构造
- **问题**: 一段用三地址码表示、计算以 16 的阶乘为半径的圆周长的程序，需要先变成可做流敏感分析的图结构。
- **方法论的使用**: 按入口语句规则找出 (1)、(5)、(6)、(9)：首句、跳转目标、条件跳转后的相邻语句；再从每个入口切到下一入口、跳转语句或终止语句之前，得到 BB1–BB4。
- **结论**: BB1 为 (1)–(4)，BB2 为 (5)，BB3 为 (6)–(8)，BB4 为 (9)–(11)；以基本块为节点、跳转为边，得到唯一首节点、可覆盖全部节点的 CFG。
- **结果**: 书中据此构造出边集 {BB1→BB2, BB2→BB3, BB2→BB4, BB3→BB2}，作为后续数据流分析的代码模型；未纳入任何基本块的语句被视为不可达。

### 案例 2: 变量集 {a,b,c,d} 的活跃变量分析
- **问题**: 给定含 8 个基本块的控制流图，要判断各程序点上哪些变量将来还会被使用，并找出可删除的死代码。
- **方法论的使用**: 为每个基本块计算 Gen/Kill 与 In/Out，采用逆向分析，按 `In = (Out - Kill) ∪ Gen`、`Out = ∪ In(后继)` 反复遍历 CFG。
- **结论**: 第一次迭代到第二次迭代的数据流值不再变化，判定达到不动点；变量 d 在任何程序点都不活跃。
- **结果**: 可安全删除 d 的所有赋值；分析同时给出活跃变量 c 经过的路径（如 (n5,n7,n8)），并可用于寄存器分配与死代码消除。

### 案例 3: 用状态自动机与数据流分析定位 Double Free
- **问题**: 一个 `malloc(10)` 得到的指针经 `testfunc`、`FREE_MEM` 释放后，又在 `main` 中再次释放，需要静态判断是否存在指针重复释放。
- **方法论的使用**: 先把代码转成三地址码，分别构造 `FREE_MEM`、`testfunc`、`main` 的 CFG 和调用图；再按 `start → free → DoubleFree`（free 后被使用则 `UseAfterFree`）的状态规则，做带函数前置/后置条件的深度优先分析。
- **结论**: 第二次调用 `FREE_MEM(p)` 时 p 已处于 free 状态，再次释放转入 DoubleFree；第 18 行与第 10 行可能出现指针误用。
- **结果**: 分析定位到这两处 Double Free 风险，说明状态自动机可以把“指针生命周期”转成可判定的数据流事实。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿到源码或中间表示，问“这个变量是从哪来的、在哪些程序点被赋值/释放”，需要到达定值或 use-def/def-use 链。
2. 扫描器报了大量漏洞，用户想判断哪些是误报、误报是否来自流不敏感或不可行路径。
3. 需要证明某条危险路径“到底走不走得到”，或想知道分析结论为什么只是“可能”。
4. 要把 UAF、Double Free、未初始化变量、数组越界等规则落到代码上，需要状态自动机或取值约束。
5. 漏洞数据跨函数传播，用户问库函数、递归、函数指针/虚调用该怎么建模，摘要和上下文敏感如何取舍。

### 语言信号 (用户的话里出现这些就应激活)

- “这个变量是从哪来的 / 在哪被赋值的”“这条路径到底可不可达”“扫描器误报太多，怎么排除”
- “UAF / Double Free 的规则怎么落到代码里”“函数之间怎么传播”“活跃变量 / 到达定值 / 可用表达式怎么算”
- “控制流图 / 基本块 / SSA / 调用图 / 程序依赖图怎么建”“为什么循环分析不终止”
- “where does this value come from”“is this path actually reachable”“too many false positives”
- “dataflow analysis / control-flow graph / reaching definitions / liveness / fixed point / function summary”

### 与相邻 skill 的区分

- 与 `taint-analysis` 的区别: 污点分析是数据流分析的特化，只跟踪被 source 标记的不可信数据是否到达 sink；本 skill 不预设 source/sink，讲通用的 CFG/SSA/方程/不动点建模，以及任意格上事实的求解。
- 与 `symbolic-execution` 的区别: 符号执行沿路径收集条件并交给约束求解器，回答“哪条具体输入能到达”；本 skill 用 May/Must 做上近似，通常不判定路径可行性，也不能直接生成触发输入。
- 与 `crash-to-root-cause` 的区别: 后者从动态崩溃现场回溯根因，依赖样本、栈与内存证据；本 skill 是静态建模，不需要崩溃样本，但可能漏掉异常路径、并发交错和真实可达性。

## E — 可执行步骤 (Execution)

1. **明确要回答的问题与分析预算**
   - 完成标准: 写出一句可判定问题（如“p 在哪些路径上被释放两次”“c 是否活跃”），并选定流不敏感/流敏感/路径敏感、函数内/函数间。
   - 判停条件: 若只需语法级模式匹配（如查找 `strcpy` 调用点），跳到步骤 7，不必构建完整方程。

2. **构建基本块与 CFG**
   - 完成标准: 列出全部入口语句，切出极大基本块，按跳转关系连边；确认首节点唯一、目标节点可达，并标注不可达语句。
   - 判停条件: 若无中间表示、无法反汇编或无法插桩，停止并改用动态/黑盒方法。

3. **选择代码模型与精度**
   - 完成标准: 明确是否使用 SSA（含 φ 位置）、调用图（函数指针/虚调用的可能目标）、PDG（数据依赖 + 控制依赖）；记录别名、异常与外部调用的建模假设。

4. **写数据流方程与传递函数**
   - 完成标准: 四个要素齐全——方向（正向/逆向）、格与初值、汇合算子（∪ 或 ∩）、每块 Gen/Kill 与 Out=f(In)；并用 Must/May 说明为何选交集或并集。

5. **迭代求不动点**
   - 完成标准: 每块保存 In/Out，反复遍历直到值不再变化；记录迭代轮数与收敛依据，循环回边被显式处理。
   - 判停条件: 若不收敛（格无限高或循环无法收敛），限制迭代次数并降级为流不敏感/有界分析，在报告中标注精度损失。

6. **处理函数间传播**
   - 完成标准: 为库函数/已分析函数建立前置/后置摘要；调用点匹配前置条件后用后置条件续推；递归与深层调用设置 k-CFA 或深度上限。

7. **把漏洞规则写成可判定条件**
   - 完成标准: 状态类漏洞给出状态集合、转移触发语句、接受态；取值类漏洞给出程序点、变量约束与安全边界（如目的缓冲区长度 ≥ 源串长度），并说明规则来源。

8. **核对误报与漏报**
   - 完成标准: 对每条报告给出触发路径或状态序列；检查是否混入互斥分支、不可行路径、未建模的异常边/调用边；必要时用符号执行、动态调试或样本验证，并记录置信度与遗漏面。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **需要真实可达性或触发输入**: 静态数据流给出的是上近似，无法证明路径可执行；应改用 `symbolic-execution`、concolic 或模糊测试。
- **并发/多线程/异步回调程序**: 传统数据流假设单一控制流历史，线程交错与共享内存竞争不在 CFG 中；应使用竞态检测、线程模块化分析或动态工具。
- **JIT、自修改代码、加壳或动态生成代码**: 没有稳定 CFG/IR，静态模型会漏掉运行时生成的路径；应使用动态插桩、trace 或脱壳后再建模。
- **无中间表示且无法插桩的目标**: 反汇编失败、严重混淆或只有二进制片段时，先解决表示问题，不要直接套方程。
- **只需语法级规则匹配**: 若规则只依赖调用名/常量，模式匹配成本更低，数据流建模是过度工程。

### 作者在书中警告的失败模式

- **ce-B01 用流不敏感分析做漏洞判定**: 把互斥分支的定值混在一起，输出不可能同时成立的变量状态；警告信号是同一变量同时具有互斥分支的多个取值。
- **ce-B02 把流敏感分析的可能路径当成真实可达路径**: 流敏感不计算分支谓词，汇合点合并的是上近似；警告信号是报告路径要求 `x>0` 与 `x<0` 同时成立。
- **ce-B03 把 CFG 当作完整执行模型，忽略异常路径**: 解引用、类型转换、除零、longjmp 等隐式控制转移不在普通 CFG 中；警告信号是动态能到异常处理代码、静态图却无对应路径。
- **ce-B04 把静态调用图的所有边当作真实调用关系**: 函数指针、虚调用、回调使静态调用图必然包含永不发生的边；警告信号是调用图规模远大于运行 trace 的函数集合。
- **ce-B05 对带循环的 CFG 无不动点、无上限地遍历**: 循环使同一基本块反复更新，缺少不动点判定或迭代上限会导致不终止或随意截断；警告信号是分析进程长时间不结束、结果随遍历顺序变化。
- **ce-B06 把顺序程序的数据流方法直接用于并发程序**: 竞态窗口不在单线程 CFG 中，分析会漏掉线程交错导致的漏洞；警告信号是目标含线程、锁或异步回调而工具只支持单线程。

### 作者的盲点 / 时代局限

- **教材示例规模小**: 基本块、SSA、活跃变量、Double Free 都以可手算的小程序演示；真实代码中的宏、模板、内联、异常表与编译器优化被大幅简化。
- **理论到工程成本被低估**: IR 提升、别名分析、摘要生成、规则维护与误报 triage 的工作量远大于方程本身；书中对可扩展性和误报率讨论不足。
- **平台与工具偏旧**: 示例以 32 位 x86 为主，现代 64 位/ARM64 的调用约定、优化模式和工具链需另行补课。
- **静态分析乐观**: 假设能获得可用中间表示或插桩能力；对加壳、反调试、JIT、动态生成代码等前提不成立的情形覆盖有限。
- **顺序程序假设**: 作者自己也指出并发程序的数据流分析工作很少；不能把书中的方程直接外推到多线程目标。

### 容易混淆的邻近方法论

- `taint-analysis`: 只追不可信数据从 source 到 sink，关注“污点是否到达”；本 skill 关注通用事实的建模与求解。
- `symbolic-execution`: 用路径条件与约束求解回答“哪条输入可达”；本 skill 用 May/Must 上近似回答“可能是什么”。
- `crash-to-root-cause`: 从动态崩溃现场反推根因；本 skill 从静态代码模型正向/逆向推导事实。
- `program-analysis-technique-selection`: 决定数据流、污点、符号执行、模糊测试之间如何分配预算；本 skill 只负责其中数据流这一路的落地。
