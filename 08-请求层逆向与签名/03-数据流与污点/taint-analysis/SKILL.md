# 污点分析

## R — 原文 (Reading)

> (1)污点引入。识别污点信息在程序中的产生点并对污点信息进行标记。
> (2)污点跟踪。利用特定的规则跟踪分析污点信息在程序中的传播过程。
> (3）污点检查。在一些关键的程序点检查关键的操作是否会受到污点信息的影响。
>
> — 魏强、武泽慧，《逆向与漏洞分析》第5章 5.1.1 基本概念

---

## I — 方法论骨架 (Interpretation)

1. **三要素**：污点分析把“不可信输入是否到达危险操作”化简为信息流可达性问题——source 标记污点从哪来，传播规则描述污点怎样扩散，sink 定义在哪个敏感操作上检查。
2. **两条通道**：沿赋值与运算的数据依赖传播的是显式信息流；沿分支、循环条件等控制依赖传播的是隐式信息流。完整分析必须同时覆盖两者。
3. **欠污染与过污染**：该标而未标（如只看显式流、库调用断裂）会漏报；不该标而标（无净化规则、标签粒度过粗）会让 sink 全线告警。取舍要按误报成本与漏报成本分别估。
4. **静态污点**：先建模（中间表示、CFG、调用图、PDG），再按规则传播。它覆盖全部代码、平台依赖低，但不可达路径与近似建模会带来误报，报告必须人工复查。
5. **动态污点**：在真实执行中给寄存器/内存打标，误报低、路径真实，但单次输入只覆盖部分代码，漏报高，且依赖插桩平台与指令覆盖范围。
6. **正向与反向**：正向从 source 顺着执行顺序问“它会流到哪”；反向先把 sink 及其控制依赖标脏，再沿 PDG 回溯是否依赖 source。大程序应按需构建依赖、只切片与 source/sink 相关的代码。
7. **污点生命周期**：污点创建于外部数据写入寄存器/内存，传播于复制与运算，删除于常量覆盖、非污点覆盖或 `xor reg,reg` 这类清零指令。只创建不删除，已净化的数据会继续被标脏。
8. **净化函数**：加密、转义、白名单、参数化查询、严格校验等必须在规则里显式清除标记——判据是“结果是否仍受不可信输入控制”，而不是“看起来处理过了”。
9. **核心判据**：一条污点报告只有在 source 可控、传播链完整、sink 参数确实敏感、路径可达且未被净化时，才值得升级为漏洞结论。

## A1 — 书中的应用 (Past Application)

### 案例 1: scanf 输入到 while 循环的源码级传播（c-B06）
- **问题**: 需要说明 `scanf("%d",&a)` 读入的 `a` 如何影响 `b` 与 `while(i<b)`，以及 `a=10` 之后污点是否还在。
- **方法论的使用**: 把 `scanf` 所在点定为 source 并标记 `a`；按“二元运算任一操作数被污染则结果被污染”推出 `b=a+6` 被污染；按“赋常量清除污点”在 `a=10` 后清掉 `a` 的标记；把 `while(i<b)` 定为 sink，检查循环上界是否受输入控制。
- **结论**: `a` 的污点经显式赋值传给 `b`；`a=10` 使 `a` 恢复为未污染；`b` 仍带污点，因此 sink 处的循环次数可能被输入控制。
- **结果**: 演示了 source 标记、数据依赖传播、常量净化和 sink 检查的完整链条。

### 案例 2: 从 SQL 执行点反向切片定位依赖（c-B09）
- **问题**: SQL 拼接代码中，要判断 `Stam.executeQuery(sql)` 是否依赖 `getInput()` 的返回值。
- **方法论的使用**: 从 sink 语句 `executeQuery(sql)` 出发，在同时包含数据依赖边与控制依赖边的程序依赖图上做逆向切片；只保留与 `sql` 来源相关的语句，并按需构建依赖，避免一次性计算全程序 PDG。
- **结论**: 可沿依赖边回溯到 `str=getInput()` 等 source 相关语句；`if(a>0)` 对 `sql=prefix+str` 的控制依赖也在切片内，不能只看赋值。
- **结果**: 书中说明可从 sink 逆向提取相关语句、检查敏感操作是否依赖 source；未给出完整切片集合，后续仍需核验路径可达性与净化。

### 案例 3: Pin 插桩检测释放后使用（c-B10）
- **问题**: 程序 `malloc(32)` 后读 `buf[0]`、`free(buf)`、再次读 `buf[0]`、再 `malloc(32)`，需要检测 UAF。
- **方法论的使用**: 用 Pin 在 `malloc`/`free` 的入口与返回处插桩，记录分配基址、大小和 allocate/free 状态；在每次 load/store 时查表，若访问地址已处于 free 状态则报告 UAF。
- **结论**: 第二次读 `buf[0]` 落在已释放区间，构成 UAF；之后新的 `malloc(32)` 复用同一地址，不改变此前访问的违规性质。
- **结果**: 插桩程序输出多次 `[UAF in 618010]` 并给出对应指令地址，随后才出现新的 `malloc(32)=618010`。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 代码审计中看到用户输入经过若干函数后进入 SQL 拼接、命令执行、`strcpy`/`printf` 或网络发送，需要判断是否真的能从 source 到达 sink。
2. 拿到 CodeQL、Fortify、Joern 等扫描器的污点报告，需要判断这条 taint flow 是否路径可行、是否经过净化、是不是误报。
3. 动态污点插桩后 sink 没有告警，或污点在某条指令后突然消失，怀疑指令未覆盖、库调用断裂或内核态未跟踪。
4. 污点只用在 `if`/`while` 条件里，分支内产生的变量却没有被标脏，怀疑隐式信息流漏报。
5. 需要给 `encrypt`、转义、参数化查询、白名单等净化函数建模，确定它到底应不应该清除污点。

### 语言信号 (用户的话里出现这些就应激活)

- “这个参数能不能流到危险函数 / 用户输入能不能到达 sink”
- “污点从哪来、在哪被清掉 / 污点分析规则怎么定”
- “扫描器报的污点流是真的吗 / 这条 taint flow 可不可达”
- “动态污点没跑出来 / 污点跟丢了 / Pin 插桩没有结果”
- “隐式流、控制依赖算不算污点 / 净化函数算不算清污”
- 英文: "taint analysis", "taint propagation", "source to sink", "sanitizer clears taint", "taint false positive / false negative"

### 与相邻 skill 的区分

- 与 `dataflow-analysis-and-code-modeling` 的区别: 后者求一般的数据依赖、到达定值与活跃变量，回答“这个值可能从哪来”；本 skill 只追被标记的不可信 source，回答“它是否到达特定 sink”。
- 与 `non-memory-vulnerability-analysis` 的区别: 后者判定具体注入漏洞的构成与利用条件；本 skill 负责配置 source/sink/传播规则并解读分析结果，不替代具体漏洞的定性。
- 与 `crash-to-root-cause` 的区别: 后者从已有崩溃点回溯根因；本 skill 不依赖崩溃，先问污点可达性，可用于崩溃发生前的可疑点筛选。

## E — 可执行步骤 (Execution)

1. **确定 source**
   - 完成标准: 列出 source 清单（网络 `recv`、文件 `fscanf`/`NtReadFile`、输入设备、`getParameter` 等），标明参数、返回值或字段中哪一部分被标污，并区分“外部不可信数据”与“仅为分析需要而标污的内部数据”。
   - 判停条件: 若列不出任何外部可控入口，停止本流程——这不是污点分析问题，改用一般代码审计或数据流分析。

2. **确定 sink**
   - 完成标准: 按漏洞类型列出 sink 及具体敏感参数（如 `strcpy` 的 `src`、`printf` 的格式串、`executeQuery` 的 SQL、`send` 的 `buf`），而不是只写函数名。
   - 判停条件: 若 sink 无法对应到具体参数或危险语义，回到步骤 1 重新确认攻击面与检查目标。

3. **确定传播规则**
   - 完成标准: 写出赋值、二元运算、数组/字段访问、函数调用/摘要、常量赋值和清零指令的处理规则；明确标签粒度（布尔、字节、字段）与 May/Must 量化。
   - 判停条件: 若关键库函数既无源码也无摘要，先补摘要或将该调用标为“传播未知”，不得默认它清污。

4. **选择静态或动态**
   - 完成标准: 给出选择理由——要全代码覆盖、平台无关、可离线，选静态；要低误报、真实路径、可插桩，选动态；需要互补时说明先用哪一个缩小范围。
   - 判停条件: 若目标强对抗、反插桩、加壳或 JIT 且无法先处理，停止动态路线，转静态或先做保护识别与脱壳。

5. **运行分析**
   - 完成标准: 静态产出 source→sink 路径及支撑它的数据/控制依赖边；动态产出实际执行路径、代码覆盖率、污点丢失点和 sink 命中记录。

6. **处理净化与隐式流**
   - 完成标准: 每个净化点都给出“清污/不清污”的依据（加密、转义、白名单、参数化、类型转换、长度校验）；对分支与循环检查控制依赖是否应传播，并记录本次过污染/欠污染的取舍。
   - 判停条件: 若污点在某个未建模的库调用或特殊指令后消失，先补规则或换工具，不得把“污点消失”当作“已被净化”。

7. **人工核验**
   - 完成标准: 对每条报告核对路径可行性、别名与调用图建模、净化是否真正切断可控性；能构造输入则动态复现，不能构造则标注不确定性。
   - 判停条件: 若路径不可达且无法构造触发输入，降级为“疑似”或排除，不得直接定性为漏洞。

8. **给出结论**
   - 完成标准: 输出 source、sink、传播链、净化点、证据（地址/行号/输入）、结论等级（确认/疑似/排除）与未建模假设；明确“未发现污点流”不等于“程序无漏洞”。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **没有明确 source/sink 的泛泛代码审计**: 污点分析需要可判定的起点与终点；“帮我看看这个程序有没有漏洞”应先做威胁建模、攻击面梳理或漏洞机理识别。
- **需要证明“无漏洞”**: 静态分析是过近似，动态分析是欠覆盖，两者都只能给出“未发现”，不能证明不存在污点流。
- **强对抗、反插桩、加壳或 JIT 目标**: 观察与插桩前提可能不成立，污点链会断在未建模代码处；应先做保护识别、脱壳或改用其他证据来源。
- **并发、跨请求或状态机漏洞**: 污点分析跟踪单次执行中的数据流，难以表达线程交错、会话状态与跨请求污染，需配合状态建模或协议级分析。

### 作者在书中警告的失败模式

- **只追显式数据依赖（ce-B07）**: 忽略隐式控制依赖与复杂外部库调用，分支条件中的污点不会影响分支内变量，库调用边界处传播链断裂，造成欠污染和漏报。预警信号是“污点只用于 if/while 条件”或“sink 参数来自未标记的库函数返回值”。
- **不加区分地标污（ce-B08）**: 不识别净化、常量运算与无关字段，二进制标签只有污/不污两态，污点随无害运算扩散，导致 sink 全线告警、人工复查成本高于收益。预警信号是报告数量远超代码规模、大量路径经过 encrypt 或校验逻辑。
- **把静态报告直接当已确认漏洞（ce-B09）**: 跳过人工复查与动态验证，把不可达路径、不可利用数据流当成真实漏洞上报。预警信号是报告没有可复现输入、路径含不可行分支或未建模库调用。
- **用单次动态分析得出“无漏洞”（ce-B10）**: 单次输入只走一条路径，未覆盖代码中的污点流永远不会被检查；没有覆盖率记录就下结论，漏报率天然很高。
- **假设二进制污点工具覆盖全部指令（ce-B11）**: 浮点、SIMD、多媒体等特殊指令可能没有传播规则，污点会在该指令处丢失；只分析用户态、不处理内核层传播也会让结果不准确。预警信号是目标含 SSE/AVX 或加密指令，且污点在一条指令后突然消失。

### 作者的盲点 / 时代局限

- **工具覆盖不全**: 书中明确承认二进制污点工具通常只实现传输、算术、逻辑、比较等常见指令，浮点与多媒体指令、系统调用和内核层传播可能缺失。
- **动态分析覆盖率有限**: 单次执行只覆盖部分代码，需要多轮输入才能提高覆盖率；平台相关性强，换操作系统或固件就要换工具。
- **静态分析偏乐观**: 真实二进制上的别名、间接调用、C++ 虚分发与库摘要建模成本很高，书中案例规模较小，容易低估工程工作量。
- **示例以 32 位 x86 为主**: 64 位、ARM64、JIT 动态生成代码与强混淆目标需要另行补课；书中也默认分析者能获得中间表示或插桩能力。
- **单路径假设**: 真实漏洞常涉及多线程竞争、跨请求状态与环境组合，而污点分析倾向于用“一条数据流”解释问题。

### 容易混淆的邻近方法论

- `dataflow-analysis-and-code-modeling`: 一般数据依赖与不动点求解 vs 只追不可信 source 到 sink 的可达性。
- `non-memory-vulnerability-analysis`: 具体注入漏洞的判定与利用条件 vs 污点分析的规则配置与报告解读。
- `crash-to-root-cause`: 从崩溃回溯根因 vs 在崩溃前判断污点是否可达危险操作。
- `symbolic-execution`: 用路径条件与约束求解生成输入 vs 用污点标记判断数据流可达性。
- `fuzzing-strategy`: 用执行与覆盖率反馈找异常 vs 用污点分析筛出值得重点测试的 sink。
