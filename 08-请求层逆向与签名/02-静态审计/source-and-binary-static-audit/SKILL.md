# 源码审计与剥离二进制静态分析

## R — 原文 (Reading)

> "这里所讨论的静态（又称为被动）逆向工程技术，也就是尝试通过检查源代码或编译代码的方式来发现潜在的缺陷和漏洞。"
>
> "由于启动序列的最后一个操作是将控制转交给main函数，因此无论二进制代码是否已被剥离，都应该能够非常容易地定位main函数。"
>
> — Daniel Regalado 等, 第3章 3.0；第4章 4.1.1

---

## I — 方法论骨架 (Interpretation)

1. 静态审计的第一步不是打开工具，而是判断输入：能拿到源码就走源码路径；只能拿到可执行文件就走二进制路径。两条路径目标相同，都是把"可能有缺陷"收敛成"有证据的候选点"。
2. 源码路径的主线是：枚举所有输入源（argv、环境变量、文件、stdin、网络数据，以及 dup2 接到 stdin 的套接字）→ 追踪数据在函数与条件分支中的流向 → 确认它能否到达危险点 → 用路径约束判断可达性。
3. 源码路径上，扫描器（RATS、ITS4、Yasca 等）只负责生成候选点：告警要逐条人工确认，零告警也不等于安全；同时必须检查程序员手写的复制循环和协议解析，不能只搜危险函数名单。
4. 二进制路径的主线是：先判平台、链接方式与库版本 → 从 `_start` 启动序列定位 main → 用库签名剥离库代码 → 按调用次数排序收敛到应用核心 → 恢复结构体与 C++ 类。
5. 定位 main 的结构性锚点是：`_start` 的最后一个动作把 main 交给 `libc_start_main`，传给它的第一个参数就是 main。剥离只丢符号、不改这段行为；动态链接的导入/导出名仍保留。
6. 静态链接且剥离时，库函数与用户函数外观相同。必须用 FLIRT 签名识别已知库；识别不出的库用 FLAIR 自建签名（模式生成器 → `.pat` → `sigmake` → 处理 `.exc` → `.sig`），否则会把 C 标准库当成应用逻辑逆向。
7. 签名之后仍有大量 `sub_` 时，用 IDAPython 统计调用次数并降序，先命名和分析高频函数；再按"malloc/new 长度"与"最大偏移 + 访问宽度"两步互证恢复结构体，用 this 传递方式与 vtable 项对比恢复 C++ 类层次。
8. 两条路径的出口一致：每个候选点都要写清输入是否可控、路径是否可达、证据在哪。工具告警、反编译输出、签名命中都只是线索，不能升级为"安全"或"可利用"的结论。

## A1 — 书中的应用 (Past Application)

### 案例 1: find.c 的手工源码审计与工具复核

- **问题**: 面对一个基于 UDP 的文件定位服务 find.c，需要判断缓冲区溢出在哪、扫描器报出的点是否真的可利用。
- **方法论的使用**: 先从 `recvfrom` 入口枚举输入源，把 buf 一路追到 `manage_request`；发现 `envstrings` 只分配 16 个指针，而解析 environ 的 while 循环不检查下标 i。按每个元素 4 字节、到保存的帧指针/返回地址约 67600 字节计算，约 16900 个额外环境字符串即可覆盖。随后用 RATS/ITS4 复核，工具标出两处 `sprintf`、栈缓冲区与 `recvfrom`，作者逐条手工确认。
- **结论**: 第 172 行声明的缓冲区可被适当格式化的 UDP 报文溢出；循环不校验 `key=value`，仅用空白字符就能把环境字符串放进报文。
- **结果**: 书中确认该溢出并给出利用思路（细节留作练习）；同时明确工具只提供候选点，规模越大误报越多，未标记区域仍须人工审。

### 案例 2: 剥离 fetch 的启动序列定位 main

- **问题**: 同一个 fetch 程序被 strip，甚至静态链接后函数名全失，IDA 停在 `_start`；直接逐个逆向 `sub_`/`loc_` 不知道从哪开始，也不知道哪些是库代码。
- **方法论的使用**: 先用 `file` 与 `strings` 收窄平台和 libc 版本；把未剥离版作为参照，确认 `_start` 的最后一个动作是把 main 传给 `libc_start_main`，而剥离不改变这一行为。在剥离版中取传给 `libc_start_main` 的第一个参数（栈顶项），把 `loc_8046854` 重命名为 main；对静态链接剥离版，先按启动序列特征识别 `libc_start_main` 本身。
- **结论**: main 可以稳定定位，不必从 `_start` 开始逐条读 C 库初始化；但 `stderr`、`fwrite`、`exit`、`gethostbyname` 等也已变成 `sub_`/`loc_`，直接深入就是在逆向 C 标准库。
- **结果**: 作者用未剥离版与剥离版的对照证明"剥离只丢符号、不改行为"，并据此要求在分析前先做库签名。

### 案例 3: 为 FreeBSD libc.a 生成 FLAIR 签名时的冲突取舍

- **问题**: 为 FreeBSD 6.2 的静态 libc.a 建签名，`sigmake` 报告 924 个冲突并拒绝生成 `.sig`，只输出 `.exc` 排除文件。
- **方法论的使用**: 因库是 ELF 格式，选用 `pelf` 生成 `libc_FreeBSD62.pat`（skipped 0，total 988）；再用 `sigmake -n` 生成签名。查看 `.exc` 后发现 `ntohs` 与 `htons` 签名完全相同——在 x86 上二者都只是交换两字节短整型的高低字节。按规则删除分号注释行，在希望保留的函数行前加 `+`，以相同选项重跑。
- **结论**: 冲突来自真实的同码函数，工具无法替分析者决定命名归属；此外 FLAIR 版本必须与 IDA 版本匹配，否则签名无法生成或加载。
- **结果**: 重跑成功生成 `.sig`，复制到 IDA 的 sig 目录后，原本的 `sub_80593B0`、`sub_805939C`、`sub_8057850` 被识别为 `sys_getuid`、`sys_getgid`、`initgroups`。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿到一个源码仓库或单个 `.c` 文件，问"从哪开始审""扫描器报了一堆怎么确认""这个 recvfrom/sprintf 路径能不能到"。
2. 拿到固件或闭源程序，IDA 打开后停在 `_start`，函数全是 `sub_`/`loc_`，找不到 main，也不知道该不该继续往下读。
3. 面对静态链接且被剥离的二进制，分不清哪些是应用逻辑、哪些是 C 标准库或第三方库，想用 FLIRT/FLAIR 缩小范围。
4. 反汇编里看到 `malloc(0x60)` 和 `[esi+80]`、`[esi+88]`，或看到只读数据段里的指针表和 `ecx` 传参，想恢复结构体布局、vtable 与类继承关系。
5. 需要批量处理大量样本，想用 IDAPython 统计调用次数、重命名包装函数、批量解密字符串或跑 `-B/-S` 批处理。

### 语言信号 (用户的话里出现这些就应激活)

- "源码审计 / source audit / 静态审计 / 白盒审计"
- "IDA / stripped binary / 剥离二进制 / 没有符号 / 找不到 main"
- "FLIRT / FLAIR / sigmake / .exc / 静态库签名"
- "结构体恢复 / malloc 大小 / vtable / thiscall / IDAPython 批量"
- "这些 sub_ 是库函数还是业务代码"

### 与相邻 skill 的区分


- **composes-with** `fuzzing-engineering-peach`：本 skill 用静态收敛找可达危险点与结构；需要动态触发、种子与崩溃样本时交给它，二者互为输入。
- **composes-with** `patch-diff-1day-workflow`：本 skill 对单个版本做静态审计；有新旧版本或补丁差异时，由它从修复反推漏洞，本 skill 负责读懂被改函数。
- 与 `reverse-engineering-workflow` 的区别: 后者是通用逆向流程（样本分类、工具选择、动静结合、分析记录）；本 skill 只保留本书的增量——剥离二进制定位 main、FLIRT/FLAIR 库签名、结构体恢复、IDAPython 自动化，通用流程直接引用旧 skill，不重讲。
- 与 `cpp-semantic-recovery` 的区别: 后者处理反编译后的类型、表达式、有符号性与控制流语义修复；本 skill 在 IDA 数据库层恢复结构大小、字段偏移、vtable 与类层次，不负责把优化后的反编译代码还原成可读 C++。
- 与 `locate-by-known-anchor` 的区别: 后者用已知字符串、导入函数、错误信息等作为锚点；本 skill 的锚点是结构性的——`_start → libc_start_main → main` 的启动序列，以及库签名的字节模式。
- 与 `patch-diff-and-source-analysis` 的区别: 后者从补丁差异反推漏洞；本 skill 不做版本对比，只对一个目标做静态收敛。
- 与利用类 skill 的区别: 本 skill 的出口是"可达性 + 候选点 + 证据"，不构造 PoC、不绕过保护。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **授权与输入判定（共同起点）**
   - 完成标准: 已书面确认目标所有者授权与范围；已记录目标是否可取得源码、可否构建、文件格式与架构。

2. **源码分支 A1 — 枚举输入源**
   - 完成标准: 列出 argv、环境变量、输入文件、stdin、网络数据，以及 `dup2` 接到 stdin 的套接字等全部入口，并为每个入口标注数据类型与长度来源。
   - 判停条件: 若源码不可得或无法构建对应版本，转二进制分支 B1，并在报告中标注源码不可得。

3. **源码分支 A2 — 追数据流与路径约束**
   - 完成标准: 每个候选危险点都能给出"入口→函数→危险调用"的完整路径，并列出路径上所有条件测试及其约束。
   - 判停条件: 若数据在某个条件处被完全约束、无法到达危险点，标记为不可达，不投入利用分析。

4. **源码分支 A3 — 手工检查与工具复核**
   - 完成标准: 按"未检查错误条件、误解功能行为、协议设计拙劣、未测试边界"四类逐项过检查表；用 RATS/ITS4/Yasca 等扫描同一份代码，逐条核对告警与未告警区域。
   - 判停条件: 若工具零告警，不视为安全，继续手工检查关键输入路径；若告警过多，只把工具当候选点生成器，按可达性排序，不逐条追误报。

5. **源码分支 A4 — 形成候选点与修复建议**
   - 完成标准: 每个候选点写清输入可控性、可达条件、影响与证据（文件/行号/调用链）；修复建议包含输入长度验证，不只做 `strcpy→strncpy`。
   - 判停条件: 若结论只有"使用了危险函数"而无输入可达性，降级为线索，不得写成漏洞结论。

6. **二进制分支 B1 — 判定链接方式、平台与库版本**
   - 完成标准: 用 `file` 判定平台/文件格式，用 `strings` 搜索编译器、libc、第三方库版本线索；判定动态链接还是静态链接，并记录内部符号是否被剥离。
   - 判停条件: 若为动态链接且导入/导出名完整，直接用导入名恢复 API 语义，跳过 B3 的自建签名；若同一程序存在动态链接版本，优先分析该版本。

7. **二进制分支 B2 — 由启动序列定位 main**
   - 完成标准: 从 `_start` 跟到最后一个调用 `libc_start_main` 的位置，取传给它的第一个参数（栈顶项）作为 main 地址并重命名；说明剥离不改变 `_start` 行为。
   - 判停条件: 若静态链接剥离后连 `libc_start_main` 名称都消失，先按启动序列特征识别它本身，再取 main；若误把 main 当第一个执行函数，回到 `_start` 重新定位。

8. **二进制分支 B3 — 应用或生成库签名**
   - 完成标准: 先应用 IDA 自带 FLIRT 签名；识别不出的库按"收窄平台/版本→`pXXX` 生成 `.pat`→`sigmake`→编辑 `.exc`→复制 `.sig` 到 sig 目录"完成，并记录匹配率与仍呈库特征的可疑函数。
   - 判停条件: 若 `sigmake` 报 COLLISIONS 且 `.exc` 未处理，停在此步先明确同签名函数保留哪个名字；不得假设 FLIRT 覆盖所有静态库。

9. **二进制分支 B4 — 按调用次数排序并命名**
   - 完成标准: 用 IDAPython 枚举函数、以 `CodeRefsTo` 统计调用次数、过滤 `FUNC_LIB` 后降序，人工分析并命名前 N 个高频函数；只改 `sub_` 等哑元名。
   - 判停条件: 若 Functions 窗口数量明显偏少或出现大片红色普通代码，先按 P 手工识别函数边界再重跑；若脚本会覆盖已有名称，停止并修正过滤条件。

10. **二进制分支 B5 — 恢复结构体与 C++ 类**
    - 完成标准: 用 `malloc/new` 分配长度与"最大观察偏移 + 该处访问宽度"两种方法互证结构大小，按访问方式推断字段类型并在 Structures 窗口应用；C++ 用 this 传递方式（微软 thiscall 走 `ecx`，g++/Borland 走栈参数）与 vtable 项对比恢复类层次。
    - 判停条件: 若只有栈/全局变量的多个 `[ebp-xx]` 地址差，不得仅凭相差若干字节断定同一结构；若动态分配结构未呈现"基址+偏移"访问，回到分配点确认。

11. **二进制分支 B6 — 脚本化与批量处理**
    - 完成标准: 用 `-B` 建 IDB、`-S` 跑脚本，脚本末尾调用 `exit()`；确认 IDB 已落盘且重命名、注释可见；明确 Patch 只改 IDB、不改原始二进制。
    - 判停条件: 若脚本跑完进程不退出或重开 IDB 看不到改动，先修 `exit()`/保存流程，不继续批量；若需要真实修改样本做动态验证，另行走文件写入并记录哈希。

12. **共同出口 — 汇总可达性与候选点**
    - 完成标准: 输出"入口→路径→危险点→证据"的候选点清单，逐条标注可达性、影响、置信度与未覆盖区域，并说明源码/二进制两条路径各自的盲区。
    - 判停条件: 若没有任何可达性证据，只能作为线索移交；若需要证明可利用，转入利用开发 skill，不在本 skill 内下结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 未取得目标所有者授权，或目标范围不包含逆向/安全测试：静态分析同样受法律约束，应先回到授权与披露门禁。
- 需要实际运行样本、观察网络行为、抓内存或动态取证：静态分析只能给候选点，不能回答"运行时到底做了什么"，应转动态分析或恶意样本分析。
- 目标是大规模 fuzzing、覆盖率引导或崩溃 triage：本 skill 不提供种子、变异与执行闭环。
- 已经拿到补丁、只想做版本差异比较：应使用补丁比较工作流，本 skill 不做 BinDiff 分诊。
- 已经定位到具体漏洞、要构造 PoC 或绕过保护：应转入利用开发类 skill，本 skill 的终点是候选点与可达性。
- 目标是 Java/Python 等字节码：反编译成功率高、模型不同，套用 IDA/剥离二进制的流程收益很低。

### 作者在书中警告的失败模式

- ce20: 误以为 main 是第一个执行的函数，跳过 `_start` 与 C 库初始化，导致初始化行为判断错误。
- ce21: 在剥离的静态链接程序中直接逆向 `sub_`/`loc_`，结果把 C 标准库片段当成应用逻辑完整逆向。
- ce22: 仅凭残留符号名推断函数用途，不验证参数、返回值与调用上下文。
- ce23: 看到 `sigmake` 报冲突就认为签名库不可用，不编辑 `.exc` 便放弃。
- ce24: 自动重命名脚本不区分哑元名与已有名称，覆盖库函数名、导入名或人工命名。
- ce25: 批量脚本忘记调用 `exit()`，IDA 不退出，重命名/注释/补丁没有写入 IDB。
- ce26: 以为 FLIRT 覆盖所有静态库；内置签名匹配率低时，把剩余函数全当应用逻辑。
- ce27: 完全信任 IDA 的自动函数识别，漏掉显示为红色普通代码的真实函数，调用图不完整。
- ce13 / ce15: 只按危险函数名单审计，或把"使用了 `strcpy`"直接等同于"存在漏洞"，不确认输入可控性与可达性。
- ce18 / ce19: 用源码声明尺寸推算实际栈偏移，或期待反编译器还原原始源码；编译器会插入 padding、重排变量，优化还会改变控制流。

### 作者的盲点 / 时代局限

- 书中以 IDA 6.x 的界面、菜单与命令为例，且 FLAIR 发布版本通常不向后兼容旧版 IDA；今天使用 IDA 7/8/9 或其他工具时，菜单路径、脚本 API 与签名格式需按当前版本文档核对，不能照抄命令。
- FLIRT 签名与编译器、库版本、优化选项强绑定；静态链接二进制命中率低不代表样本异常，也可能是版本不匹配或库未被签名覆盖。
- 书中二进制审计以 32 位 x86 为主：C 调用约定从右向左压栈、微软 thiscall 用 `ecx` 传 this。x64 下前四个参数走寄存器（Windows 为 `rcx/rdx/r8/r9`），"从 call 向前读 push 还原参数"不能直接套用。
- 书中源码工具（RATS、ITS4、Yasca、Flawfinder 等）多为 2000 年代产物，部分已停止维护；现代可换用 Semgrep、CodeQL、Clang Static Analyzer，但"工具只生成候选点、必须人工确认"的方法不变。
- 剥离、静态链接在固件与闭源程序中仍常见，但 LTO、内联、PIE、CFG 等现代编译/加固选项会让函数边界更碎、签名更易失配；本 skill 的定位方法可迁移，具体匹配率不能保证。
- 该书默认单个研究者、商业 IDA 许可与可长期运行的隔离环境，未讨论团队协作、CI 集成与云端分析成本。

### 容易混淆的邻近方法论

- **反编译 = 源码恢复**: 反编译只生成近似代码，变量名、类型、注释已丢失，不能按源码审计的方式逐行信任（ce19）。
- **库签名识别 = 函数语义确认**: FLIRT 只给名字，函数实际参数、返回值和调用上下文仍要验证；符号名也可能误导（ce22、ce26）。
- **启动序列定位 vs 已知锚点定位**: 前者依赖 `_start → libc_start_main → main` 的结构不变量；后者依赖字符串、导入、错误信息等业务锚点，适用条件不同。
- **结构体恢复 vs 反编译语义修复**: 前者恢复内存布局与字段类型，后者修复表达式、有符号性与控制流；两者可互补但不能互相替代。
- **静态审计 vs 漏洞验证**: 静态审计回答"哪里可能有问题、是否可达"，不回答"能否利用"；零告警、签名全命中、反编译可读都不构成安全证明（ce12、ce17）。
