# 符号执行与约束求解

## R — 原文 (Reading)

> 在遇到程序分支时，通过符号执行搜索每个分支，将分支条件加入路径约束条件中；最后，通过约束求解器对约束条件进行求解，验证约束的可解性，以判断该路径是否可达。
>
> — 魏强、武泽慧，第6章 6.1.1 基本概念

---

## I — 方法论骨架 (Interpretation)

1. 符号执行把选定输入换成符号，程序状态从“变量=具体值”变成“变量→符号表达式”的映射；内存也要建模为地址到表达式或具体值的映射，遇到符号地址时用 ite 公式或按所有可能状态派生。
2. 沿一条路径推进时，每个分支的判定条件都并入路径条件（PC）；到达目标点时，PC 就是“能走到这里”的全部前提。
3. 判断漏洞是否真实，要把 PC 与“违反安全规则的条件”取合取——例如数组访问处的 `i<0 ∨ i≥len(a)`——再交给求解器。
4. 求解结果要分开处理：sat 给出具体输入；unsat 排除该路径；unknown 只能记为不确定，既不能当 sat，也不能当安全证明。
5. 正向从入口沿 CFG/调用图铺开，适合全面探索；逆向从目标点（assert、危险写、越界访问）回代约束，目标明确、搜索空间通常更小。
6. 动态符号执行（concolic）先用具体输入跑一条路径，插桩收集约束，取反其中一个分支条件并求解出新输入，迭代推进；它降低建模与内存压力，但覆盖受种子和取反策略限制。
7. 混合符号执行在在线式（多 executor、速度快、吃内存）与离线式（单路径、省内存）之间切换；选择性符号执行只符号化关心区域，其余具体执行，并在边界做具体值↔符号值转换。
8. 路径爆炸来自分支与循环，路径数近指数增长；缓解手段包括每个分支先求解剪枝、状态合并、函数摘要/欠约束、切片与污点缩小范围、与 fuzz 混合、限定时间与内存。
9. 循环不要盲目展开：次数已知时取退出前一次（如 `i=99`），次数未知时取终值（如 `i=k-1`），只分析一次循环体。
10. 外部函数必须显式建模：追踪进去会让约束急速膨胀，直接跳过又会切断跨库数据流，通常用函数摘要或环境模型在调用边界截断。
11. 求解失败的处理有方向差异：正向遇到不可解常保守继续（降低漏报但可能产生假阳）；逆向一旦确认约束不可解就停止该路径，因为再添加上游约束仍然不可解。
12. 报告纪律：必须区分“已求得可满足输入”和“无法证明不可行”。后者只是疑似，需具体执行或其它手段复核，不能直接当成已确认漏洞。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三重 if 程序求永真路径的输入

- **问题**: 一段含三个嵌套 `if` 的程序有 8 条路径，需要求出能让三个条件都为真的具体输入。
- **方法论的使用**: 把接收输入的 `a、b、c` 符号化，遇到分支就选择 true 分支，并把条件逐条并入路径约束；三个条件累积为 `a>2 ∧ a+b>5 ∧ b+c>3`，再交给约束求解器判断可满足性并求值。
- **结论**: 路径条件可满足，求解器给出一组解 `a=3、b=3、c=3`。
- **结果**: 用这组输入执行程序，三个条件均为真，验证了“一次符号执行代表一类输入”。

### 案例 2: 数组越界漏洞的正向与逆向分析

- **问题**: 全局 `int array[10]`，`get_item(index)` 在 `index<0` 时返回 NULL，`rand_print()` 用 `i=rand()%20` 调用它；需要判断 `array[index]` 的访问是否可能越界。
- **方法论的使用**: 正向采用自底向上的调用图分析，先为 `get_item` 归纳摘要（`0≤index<10` 安全、`index<0` 返回 NULL），再把 `rand_print` 中 `i` 的 0–19 范围与摘要结合，求解 `i>9`；逆向则从第 10 行数组访问出发，把越界条件 `index<0 ∨ index>len(array)` 作为初始约束，沿分支回代并传播到调用者 `rand_print`。
- **结论**: 正向求解得到 `i=10` 满足越界约束；逆向在同一调用点也得到可满足约束，两种方向都判定存在越界。
- **结果**: 说明正向适合系统性归纳、逆向适合从已知危险点收敛，两者可互相印证。

### 案例 3: 动态符号执行对 foo 程序做约束取反

- **问题**: `foo(a,b)` 含两个 `if` 和 `assert(z-x<0)`，共有 4 条路径；需要覆盖不同路径并触发断言失败。
- **方法论的使用**: 以 `a=b=1` 具体执行，收集当前路径约束 `(a=0)∧(b≠0)`；按策略取反其中一个分支条件，得到新约束并求解出下一轮输入，重复“执行—收集—取反—求解”。
- **结论**: 求解 `(a≠0)∧(b=0)` 得到 `a=1、b=0`，执行后 `x=4、z=8、z-x=4>0`。
- **结果**: 断言失败，错误路径被成功触发；说明 concolic 用具体执行驱动探索，能逐步覆盖路径。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 已知某个分支、危险函数、`assert` 或数组访问点，想生成**确实能到达它**的输入，而不是靠猜。
2. 覆盖率引导 fuzz 跑了很久覆盖率不涨，卡在某个比较、校验和或长度检查上，想对该分支做定向求解。
3. 需要判断一个数组越界、整数溢出或空指针解引用**是否真的可达**，要的是约束证据而不是“看起来可能”。
4. 需要证明某条路径不可行，排除静态分析或 fuzz 报出的误报。
5. 符号执行工具已经跑起来，但超时、内存爆炸或求解器返回 unknown，需要判断是目标不适合、建模不完整，还是参数/区域需要收缩。

### 语言信号 (用户的话里出现这些就应激活)

- “帮我生成能走到这个分支/这一行的输入”“怎么让程序执行到危险函数”
- “fuzz 跑了两天覆盖率不涨”“卡在这个比较/校验上”“想定向求解这个分支”
- “这个越界到底可不可达”“能不能证明这条路径走不到”“约束是不是无解”
- “符号执行路径爆炸/状态太多”“solver 返回 unknown/timeout”
- “symbolic execution”“path condition”“concolic”“constraint solving”“path explosion”
- “generate an input that reaches this branch”“prove this path is infeasible”

### 与相邻 skill 的区分

- 与 `coverage-guided-fuzzing` 的区别: 对方靠**真实执行 + 覆盖率反馈**做广撒网式发现，不求解路径约束；本 skill 靠**路径条件 + 约束求解**合成定向输入，能证明某路径可满足或不可满足，但需要建模且受求解能力限制。两者可组合成 concolic：fuzz 负责探索，符号执行负责攻破卡住的分支。
- 与 `dataflow-analysis-and-code-modeling` 的区别: 对方做 CFG/SSA/到达定值/活跃变量等**静态依赖近似**，回答“数据可能从哪来到哪去”，不生成具体输入；本 skill 是**路径敏感**的，收集路径条件并求解出可执行输入或不可行证明。
- 与 `program-analysis-technique-selection` 的区别: 对方决定“在数据流、污点、符号执行、fuzz 之间如何分配预算”；本 skill 是在已经选定符号执行后，执行其内部流程并处理路径爆炸与求解失败。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **定目标点与违反条件**
   - 完成标准: 写出具体程序点（地址/行号/函数）和该点的违反谓词，例如 `a[i]` 处的 `i<0 ∨ i≥len(a)`；若目标是“全面看看有没有漏洞”，先说明本 skill 只做定向判定。
   - 判停条件: 若没有可指认的目标点、只需要大范围发现崩溃，转到 `coverage-guided-fuzzing`。
2. **选符号化范围与方向**
   - 完成标准: 列出哪些输入/变量符号化（argv、文件字节、`scanf` 变量、网络字段）、哪些保持具体、分析区域是全程序还是选择性区域；明确正向还是逆向及理由。
   - 判停条件: 若目标无法获得 IR/插桩能力且二进制提升不可行，停止并改用动态分析或定向 fuzz。
3. **建模外部调用与环境**
   - 完成标准: 每个库函数、系统调用、第三方 DLL 都有处理方式（摘要、桩、具体执行边界或环境模型），并记录其假设与副作用；不能既不建模又声称覆盖。
   - 判停条件: 若外部调用无法建模且追踪会导致状态爆炸，收缩符号化区域或改用选择性符号执行。
4. **收集路径条件**
   - 完成标准: 在目标点得到完整 PC，包含分支条件、数组/分配大小约束、指针与别名关系；若走逆向，赋值语句按变量关系回代，无关赋值可忽略，别名不确定时先做别名/指向分析。
   - 判停条件: 若 PC 中大量符号地址/别名无法确定，先补建模，不要直接求解。
5. **求解“路径条件 ∧ 违反条件”**
   - 完成标准: 求解器返回 sat（附具体模型）、unsat（附可信建模依据）或 unknown（附原因：非线性、浮点、符号作分母、超时）。
   - 判停条件: 若 unsat 且建模可信，判定该路径不可行并记录；若 unknown，不得当作 sat；若约束不可解且无法放宽模型，停止该路径并记录，不得继续据此报漏洞。
   - 判停条件: 若 unsat 来自建模不完整（外部函数跳过、别名缺失），只能记为“不确定”，不能当作安全证明。
6. **把模型转成真实输入**
   - 完成标准: 解出的值能落成合法输入（长度、格式、校验和、编码都满足），并保存为可复现的文件/参数/报文。
   - 判停条件: 若模型含无法表达的符号指针或无约束字节，回到步骤 3/4 调整建模，而不是硬凑输入。
7. **具体执行验证**
   - 完成标准: 在插桩或调试环境中运行该输入，实际轨迹命中目标分支/触发崩溃或断言；记录命中地址与调用栈。
   - 判停条件: 若实际轨迹与预测不符，判定为建模偏差，带着差异回到步骤 3/4，不把求解结果当结论。
8. **处理路径爆炸与失败并收敛报告**
   - 完成标准: 明确记录所用缓解手段（分支剪枝、状态合并、循环取一次/终值、函数摘要/欠约束、选择性符号化、与 fuzz 混合）以及时间/内存/路径数上限；报告区分“已用输入证实”“仅约束 sat”“unknown/未覆盖”。
   - 判停条件: 若达到时间、内存或路径数上限，停止探索，报告已覆盖路径与残余未证区域，并建议切换到 fuzz、污点或人工分析。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **大型闭源且无法插桩、无 IR、无调试信息**: 符号执行依赖中间表示或插桩；纯黑盒目标应先走定向/内存 fuzz 或动态分析，否则只能得到失真的提升结果。
- **强浮点、指针、加密/压缩/外部库密集**: 现有求解器对浮点和指针没有可靠理论，符号地址与库调用会让约束迅速膨胀；建模成本常高于收益。
- **路径爆炸不可控且没有明确目标点**: 输入相关的深循环、递归、状态数指数增长时，全路径探索跑不完；应收缩区域、加目标点或改用 fuzz。
- **需要覆盖全程序或证明“没有漏洞”**: 符号执行是有界的，unsat 只对当前路径与当前模型成立，不能外推为整个程序安全。
- **多线程/并发/时序竞争是主要问题**: 单路径模型难以表达线程交错与共享内存竞争，应改用动态竞态检测或定向 fuzz。
- **只需要快速发现大量崩溃、没有特定目标**: 覆盖率引导 fuzz 的单位成本更低，符号执行应作为卡住分支的补充。

### 作者在书中警告的失败模式

- **把理论路径完备性当成工程可用性**（ce-B12）: 每个分支复制状态，路径数近指数增长，循环会让分支数趋于无限；表现为 executor/状态数暴涨、超时、内存耗尽，覆盖率却停在浅层。正确做法是先设时间/内存/路径上限并配合剪枝、合并与选择性符号化。
- **把“不可解/unknown”当成“路径可行”继续分析**（ce-B13）: 正向符号执行对不可解约束常保守放行，求解器对非线性、浮点、符号作分母本就可能返回 unknown；把 unknown 当 sat 会产出无法复现的假阳，把建模不完整的 unsat 当安全证明则会漏报。必须记录求解状态与建模假设。
- **逆向到达入口仍无法断定时直接判漏洞**（ce-B14）: “无法证明安全”不等于“已证明存在漏洞”；没有 sat 模型、只有 unknown 时，应报“疑似/未证实”，并用具体执行或其它工具复核。
- **对外部函数不做环境建模**（ce-B15）: 追踪进库函数会让路径与约束急速增加，直接跳过又会切断跨库数据流、漏掉库内 sink；两种极端都失真，应使用摘要、环境模型或选择性具体执行。

### 作者的盲点 / 时代局限

- 成书于 2022 年，工具示例以 BAP、KLEE、EXE、SART/SMART、S2E、Mayhem、angr 等为主；具体版本、脚本、参数与工程流水线很快过时，**概念可迁移，命令不能照抄**。
- 案例多为 32 位 x86 上的小型 C 程序，真实软件中的宏、模板、内联、异常表、编译器优化、JIT、加壳与反调试会显著改变建模难度；书中的“可分析”前提在真实目标上经常不成立。
- 理论完备不等于工程可用: 路径爆炸、约束求解（尤其浮点/指针/非线性/符号分母）、外部环境建模仍是硬瓶颈，书中也承认这些方法无法从根本上消除路径爆炸。
- 假设分析者能获得可靠 IR 或插桩能力，并假设约束求解器能处理路径条件；对二进制提升的语义失真、多线程交错、跨请求状态机讨论不足。
- 书中明确提到 Mayhem 无法处理多线程交互；把符号执行用于并发程序时，需要额外的方法而不是直接套用本章流程。

### 容易混淆的邻近方法论

- `coverage-guided-fuzzing`: 真实执行与覆盖率反馈 vs 路径约束求解；前者广、后者准，concolic 是两者结合。
- `dataflow-analysis-and-code-modeling`: 静态依赖与 May/Must 近似 vs 路径敏感的条件收集与求解；前者不生成输入，后者能给出可执行证据。
- `taint-analysis`: 回答“不可信输入是否到达 sink”，不回答“这条路径是否可行”；常用污点先找候选 sink，再用符号执行证明可达。
- `directed-memory-kernel-fuzzing`: 用距离/目标导向的 fuzz 逼近目标点，不依赖求解器；适合内核、闭源或无文件输入的目标。
- `program-analysis-technique-selection`: 决定预算与技术组合；本 skill 只负责符号执行这一条路线内部怎么做。
