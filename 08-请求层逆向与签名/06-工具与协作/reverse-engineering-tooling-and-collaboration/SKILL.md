# 逆向工程工具化与协作

## R — 原文 (Reading)

> “在对复杂的恶意软件样本或软件进行逆向工程时经常出现的一种情况是，有多个人在做同样的事情。而最基本的协作方式便是分享IDB文件。”
>
> “Yara签名是一种记录恶意软件分析并建立个人签名库的好方式。”
>
> — 第23章 23.1.3、23.1.1

---

## I — 方法论骨架 (Interpretation)

1. 工具化的起点不是“装插件”，而是先量化当前流程的痛点：哪一步最耗时、最重复、最容易因人工遗漏而返工；方案按耗时与工作量评价，而不是按“高级/正统”评价。
2. 单样本冷启动的第一道工序是函数恢复：IDA 未识别的代码会让交叉引用、反编译和后续标注全部失真，必须先修复函数边界。
3. 恢复用保守两阶段：先只把带标准函数开场白的代码转成函数，再把其余指令转成函数；宁可少转，避免假函数污染后续分析。
4. 在完整函数表上做低成本标注：只调用另一个函数的薄封装按 WrappingApiName+_w 命名；再按 API 语义组（Crypt、File、Reg、Proc、Str、Net 等）给函数加组名前缀。
5. 语义着色把“读代码找行为”变成“看颜色找区域”：基本块按所调 API 组着色，函数调用概况图同样适用；颜色只是线索，结论仍要读指令确认。
6. 密码逻辑识别走双路径：先匹配标准密码常数（S 盒、初始向量、魔数），再用循环启发式（算术指令占比、基本块大小、API 调用次数）发现自定义算法；阈值必须按样本迭代调优。
7. 长会话用 Global Marks 与 History 记录“看到哪、为什么来、下一步去哪”；用探路器回答“危险函数从入口是否可达”。探路器给出的是一条选定路径，不是全部可达路径。
8. 团队协作先统一命名与标注约定，再谈同步：没有命名规范，共享 IDB 只会放大冲突；拷贝 IDB 文件本身不是版本控制。
9. 协作工具按同步对象分三类：同一 IDB 的活动式同步、跨样本的标注数据库、标注与文件推送；选型同时看维护状态、开放性、服务依赖与 EULA。
10. 知识沉淀用 YARA：每次分析后把关键字符串、配置标记或代码特征写成规则，纳入个人/团队签名库；命中后必须回到匹配地址核验假阳性。
11. 沙箱/蜜罐在链路中的位置是“第一轮回答做了什么”：先在受控网络捕获并执行，采集网络、文件、配置取证数据，再决定静态深入哪里；它不替代逆向，也不能保证样本在观察窗内触发。
12. 所有手段共享同一条评价标准：是否减少了完成同一任务的时间与人工工作量，而不是是否显得专业。

## A1 — 书中的应用 (Past Application)

### 案例 1: IDAscope 的新样本分析四步工作流
- **问题**: 新样本载入 IDA 后，大量数据和代码没有被识别为函数，函数表里全是 sub_xxxx，交叉引用和反编译都不可靠，分析者无从下手。
- **方法论的使用**: 按固定顺序做四件事：先用两阶段启发式修复未知代码（先只认标准开场白，再把其余指令转为函数）；再重命名只调用另一个函数的包装器；然后按函数调用的 API 组拼出组名前缀；最后开启语义着色。配合 23.1.2 的 Global Marks、History 树和探路器记录分析路径与可达性。
- **结论**: 四步顺序不可颠倒，重命名与着色都以第一阶段恢复出的函数边界和 API 标签为前提；颜色和标记只用于导航，最终结论仍要回到指令与基本块核对。
- **结果**: 该书以此描述 IDAscope 的典型工作流。该开源插件由 Daniel Plohmann 与 Alexander Hanel 开发，在 2012 年度 Hex-Rays 插件大赛中获得亚军，结构可扩展。

### 案例 2: 用 YARA 规则识别 Tidserv 并核验假阳性
- **问题**: 第 22 章分析过的样本（MD5 为 0E288102B9F6C7892F5C3AA3EB7A1B52）需要判断是否属于 Tidserv 家族，仅靠人工找字符串既慢又难关联变种。
- **方法论的使用**: 在 IDAscope 的 YARA Scanner 中加载来自两个文件的 7 条规则，对样本扫描；结果表给出规则名、匹配字符串数、匹配百分比、是否命中以及具体匹配地址。Tidserv_generic 与 Tidserv_cmd32 两条规则的全部字符串均匹配。
- **结论**: 规则命中不能直接当作家族确认，必须回到匹配地址逐条检查是否存在假阳性；地址级复核通过后，才能把命中用于家族归属与变种关联。
- **结果**: 两条规则均被确认命中，样本可用于 Tidserv 家族归因；作者同时保留了“按匹配地址核验假阳性”这一必要步骤。

### 案例 3: 协作插件谱系与 TrapX/MalwareTrap 的工具选型
- **问题**: 多人分析同一样本时重复劳动、标注互相覆盖；同时拿到未知样本后，又需要决定先做动态取证还是直接静态逆向。
- **方法论的使用**: 按同步对象梳理插件谱系：IDASync 用客户端-服务器即时同步 IDB 改动，但更新停在 2012 年；CollabREate 增加多客户端操作监视与类似版本控制的上下载，被作者评为最好的活动式协作插件且持续更新；BinCrowd 转向跨样本标注数据库，用模糊匹配找相似函数，但服务器代码从未公布且已停止开发；IDAToolbag 只提供有限的队列式协作；CrowdRE 是闭源的 BinCrowd 重生版，与 CrowdStrike 服务捆绑，使用前应读 EULA。样本入口侧，TrapX ThreatInspector 把内存转储放入文件库、逐个分析后写入数据库再由界面呈现；MalwareTrap 用虚拟蜜罐感应敌意扫描、动态创建定向诱捕器，再把样本引入沙箱观察 C&C 回连。
- **结论**: 协作工具选型由维护状态、开放程度与服务依赖决定，而不是功能列表；同一 IDB 同步与跨样本标注复用是两种不同协作模式。动态/内存取证先行可以缩小静态逆向范围，但 TrapX/MalwareTrap 部分属于产品能力介绍，书中没有给出独立验证。
- **结果**: CollabREate 被视为最佳活动式方案；IDASync 停更、BinCrowd 服务器未公布且停更、CrowdRE 闭源并依赖厂商服务。TrapX/MalwareTrap 被定位为分析链路中的捕获与初筛环节，而非可复现的方法论。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队多人分析同一批样本，出现同一函数被重复分析、不同 IDB 里函数名不一致、标注无法合并或交接。
2. IDA 载入新样本后函数边界残缺、满屏 sub_xxxx，需要一套可重复的冷启动流程而不是逐个手工重命名。
3. 要在样本里找加密/解密逻辑，但找不到标准 S 盒或魔数，需要判断是否存在自定义循环。
4. 分析完成后想把结论变成可复用资产：写 YARA 规则、建立签名库、做家族归因与变种关联。
5. 需要在沙箱/蜜罐与静态逆向之间安排顺序，或要在多个协作插件之间做选型与治理。

### 与相邻 skill 的区分


- **composes-with** `android-malware-triage`：本 skill 提供工具化与协作基础设施；APK 分诊的具体证据链由它完成。
- **composes-with** `x64-malware-cc-decoding`：本 skill 让函数边界、命名与标注可读并可共享；C&C 配置解码的 ABI 校准与分层剥离由它完成。
- 与第 3 本 `reverse-engineering-workflow` 的区别：后者回答“为什么逆、交付物是什么、分析到哪一层算够”，负责通用逆向流程与目标框定；本 skill 假定目标与深度已经确定，只回答“用哪些工具、怎样标注、怎样分工协作、怎样把结论沉淀成签名库”，不重讲反汇编入门、中间表示或语义还原。

- 与本书 `source-and-binary-static-audit` 的区别：后者面向源码/二进制的漏洞审计与检查表；本 skill 面向分析过程的工具化、团队协作与知识沉淀，不产出漏洞结论。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **量化当前分析痛点并选工具**
   - 完成标准: 列出最耗时或最重复的 1–3 个环节（函数恢复、命名、找加密、标注交接等），并为每个环节给出候选工具与“预计节省的时间/人工量”。
   - 判停条件: 若只是一次性小样本、人工通读即可完成，停止本流程，直接分析。

2. **确认分析前提**
   - 完成标准: 样本已可被 IDA 稳定反汇编，函数表可生成；若加壳、反调试或反汇编错位，先转 `anti-debugging-and-unpacking` 恢复可分析代码。
   - 判停条件: 若静态结果整体不可信，不要在此阶段做命名和着色，先解决保护问题。

3. **修复未知代码**
   - 完成标准: 先用标准函数开场白（如 push ebp; mov ebp, esp / 558BEC）保守转函数，再把其余指令转函数；抽查新增函数，确认没有把数据或跳转表批量误判为函数。

4. **统一命名与标注**
   - 完成标准: 只调用另一个函数的薄封装按 `WrappingApiName_w` 命名；其余函数按所调 API 组拼组名前缀（如 `Crypt_File_Reg_sub_10002630`）；把命名约定写成一页团队规范。

5. **语义着色、标记与探路**
   - 完成标准: 关键基本块按 API 组着色；用 Global Marks 记录关注点并填写分组与描述；用 History 树记录“父函数—子函数”的分析路径；对关键起点/终点生成路径图并双击核对反汇编。
   - 判停条件: 颜色或路径只作为线索，若尚未读指令确认，不得写入结论。

6. **选择协作模式并治理插件**
   - 完成标准: 明确采用同一 IDB 活动式同步、跨样本标注数据库还是标注/文件推送；核对其维护状态、是否开源、是否依赖第三方服务器、EULA 是否允许上传样本或 IDB。
   - 判停条件: 若为单机分析，跳过协作步骤直接进入第 7 步。
   - 判停条件: 若插件已停更或服务器不可用，改用导出脚本/IDB 注释 + 版本控制保存标注，不把流程绑死在插件上。

7. **沉淀 YARA 签名**
   - 完成标准: 至少产出一条规则，写明关键字符串/配置标记/代码特征；在已知正样本上命中、在至少一个负样本上不命中；命中后逐条检查匹配地址，区分真命中与假阳性。

8. **安排沙箱/蜜罐初筛**
   - 完成标准: 在受控网络与隔离环境中运行样本，记录网络连接、落地文件、注册表/配置变更等取证数据；用这些“做了什么”的结果决定静态深入范围。
   - 判停条件: 若样本在观察窗内不触发或识别虚拟环境，记录为“未知/未触发”，转静态分析，不把无流量当成无行为。

9. **交付与复盘**
   - 完成标准: 交付 IDB、标注/命名约定、YARA 规则和一份可复现的分析记录；记录本次各环节实际耗时，与第 1 步的预估对比，决定保留、替换或淘汰工具。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **一次性小样本**：样本很小、读几个函数就能回答问题时，函数恢复、着色、协作和签名库的建设成本高于收益，直接分析即可。
- **闭源插件存在数据合规风险**：需要把样本、IDB 或标注上传到厂商服务器，而目标范围、保密义务或 EULA 不允许时，不要使用；数据外泄的代价远大于效率收益。
- **团队尚无统一 IDB 与命名规范**：此时上同步工具只会把冲突放大；应先停下协作工具选型，先把命名、标注和文件管理约定定下来。
- **只有通用逆向流程问题**：不知道该不该逆、交付物是什么、分析到哪一层，应先走 `reverse-engineering-workflow`，而不是用工具堆砌代替目标框定。

### 作者在书中警告的失败模式

- **ce153 把共享 IDB 文件当作团队协作的全部**：各自拷贝 IDB、各自重命名和写注释，最后无法合并；同一函数被多人重复分析，冲突标注被覆盖，产生多个不一致版本。共享文件不是版本控制，缺少操作监视、冲突解决与增量合并。
- **ce154 依赖服务器闭源且已停更的协作插件**：客户端开源但函数匹配依赖未公布的服务器，开发停止后协作与跨样本标注复用同时中断，已有标注也难以迁移；核心能力在服务端且闭源，形成单点依赖与供应商锁定。
- **ce155 把基于签名的检测当作完整防线**：签名必须依赖已知样本，面对新变种或零日，在首个样本被捕获、签名编写并下发之前攻击不可见；YARA 签名库是分析沉淀，不是完整检测体系。

### 作者的盲点 / 时代局限

- **IDA 6.x 插件生态**：书中 IDAscope、IDAToolbag、IDASync、CollabREate、BinCrowd/CrowdRE 均以 2012–2015 年的 IDA 6.x 插件接口为背景；今天 IDA 版本、插件 API、Python 环境与社区服务器均已变化，许多插件停更或闭源，菜单、快捷键和兼容性不能照搬。
- **TrapX 产品信息**：23.2 的 TrapX ThreatInspector 与 MalwareTrap 基本是产品能力介绍，缺少可复现实验与独立验证，更接近白皮书；产品名称、功能与部署方式可能已变化，只能当作“沙箱/蜜罐在分析链路中的位置”参考。
- **商业工具与单机假设**：书中默认分析者拥有商业 IDA Pro 许可、可长期运行样本、能从公开渠道取样本，较少讨论团队合规、云端协作与插件供应链风险。
- **签名与沙箱的时效性**：YARA 语法与规则生态、沙箱反虚拟化对抗都在演进；书中的具体规则、样本哈希与工具输出只能作为方法示例，不能作为今日可直接复用的检测资产。

### 容易混淆的邻近方法论

- **工具链 ≠ 逆向流程**：装插件、上着色不回答“为什么逆、交付什么”；流程框定仍归 `reverse-engineering-workflow`。
- **共享 IDB ≠ 协作**：文件拷贝没有版本控制、冲突解决和操作归属；协作需要约定、同步机制与可追溯的标注。
- **YARA 命中 ≠ 家族确认**：匹配字符串只说明特征存在，必须回到地址核验假阳性，并区分“字符串存在”与“行为成立”。
- **沙箱跑通 ≠ 行为完整**：反虚拟化、时间条件与观察窗都会让样本不触发；动态结果必须与静态分析互证。
- **语义着色 ≠ 语义结论**：颜色只表示该基本块调用了某组 API，不代表它实现了目标加密或网络行为。
