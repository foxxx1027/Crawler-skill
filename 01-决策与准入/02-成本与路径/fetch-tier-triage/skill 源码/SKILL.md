# 抓取档位分档决策与能力边界体检

## R — 原文 (Reading)

> 纯 HTML 解析需求：无需网络请求时，可仅使用scrapling.parser模块，减少依赖体积；
> 企业级反爬对抗：对 Akamai、DataDome 等无原生绕过方案，需集成第三方服务；
> 底层 HTTP 精细控制：自定义 DNS、HTTP/2 帧、TLS 套件等场景，推荐使用 httpx/curl_cffi。
>
> — 《爬虫-Scrapling》中文文档汇编, p1「特性 / 适用边界」

> DynamicFetcher 类别提供灵活的浏览器自动化，包含多种配置选项，且在底层隐形技术上几乎没有改进。
>
> — 同上, p8「如何获取页面内容？/ 抓取器类」

---

## I — 方法论骨架 (Interpretation)

这套判断的核心，是把“抓取档位”从一条速度阶梯拆成两条互不替代的判据。

第一条：**这一页的数据是不是非 JS 渲染就拿不到**。若否，请求库档就够，上浏览器纯属浪费。
第二条：**目标站是否已经在拦你**。这一步与渲染无关——两个浏览器档都能渲染，差别只在反检测强度；因此“能渲染却仍被拦”时继续往上升档，问题不会消失。

把两轴跑一遍，只会落进三种格子：静态可解、必须渲染、渲染且被拦。前两格可以照着档位表往下走；第三格必须立刻切到第二张表——**能力边界表**，逐条问“本工具在这个拦截方上有没有原生手段”。边界表命中“无原生方案”时，正确动作是判停：外接第三方求解服务，或降低频率、换数据源，而不是加开关、加代理、加重试、再升一档。

所以顺序是反直觉的：**先做边界体检，再试档位**。而不是“跑到失败为止，然后逐级升档”。同一套逻辑还管另一件事：目标是整站还是单页——单页请求与整站爬取是两种工具形态，前者不具备跟踪链接、深度、去重、断点续爬，硬撑会在规模上先崩，与反爬无关。

## A1 — 书中的应用 (Past Application)

> 说明：本书没有真实项目复盘，下列均为文档内可核实的示例与对照表，属**文档示例，非真实项目结果**；示例站是 quotes.toscrape.com / example.com 一类练习站，本身无反爬、无改版压力。

### 案例 1: 三档定义与“升级不解决检测”（p8、p25）
- **问题**: 文档要回答“面对不同页面该选哪个抓取器”。
- **方法论的使用**: p8 给出三档说明，并明写 DynamicFetcher 在底层隐形技术上“几乎没有改进”；p25 的对照表把两档差异列在“主要目的（反检测 / 动态内容交互）、灵活性、网络拦截、多页面管理”，而**不列在“能否渲染”**。
- **结论**: 两档的差别是反检测强度与灵活度，不是渲染能力。
- **结果**: 文档层面给出的是判据，不是实测数据；读者据此可推出“能渲染却仍被拦时升档无效”。

### 案例 2: 能力边界与规模边界（p1、p113）
- **问题**: 哪些场景本工具明确不该接。
- **方法论的使用**: p1 列三条边界（只要解析、企业级反爬、精细 HTTP 控制）；p113 把 Fetcher / StealthyFetcher 与整站爬取形态对比，自动跟踪链接、深度控制、规则、去重、并发、断点续爬一栏前者全为 ❌。
- **结论**: 能力边界与规模边界是两类独立的“判停”理由，任一命中都该换形态或换工具。
- **结果**: 属文档自述的适用性说明，未附失败案例或对照实验。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新任务刚拿到目标站，还没决定用 `requests`/`httpx` 还是上浏览器，问“这个站要 headless 吗”。
2. 已用请求库跑通一部分页面，但某些字段只有 JS 渲染后才出现，纠结“是否整体升到浏览器档”。
3. 已经上了隐身浏览器仍被拦（返回 403/挑战页/空壳），第一反应是“再升一档、换代理、加 `real_chrome`”。
4. 上线前做风险评估：这个拦截方本工具到底有没有原生方案，还是必须外接服务。
5. 目标从单页扩到整站，发现单页 API 撑不起来（无去重、无深度、无断点续爬）。

### 语言信号 (用户的话里出现这些就应激活)

- “这个站要不要上浏览器 / 要 headless 吗 / 静态还是动态”
- “已经用 Stealthy 了还是被 blocked / 403 / 一直过不去”
- “Akamai、DataDome、Cloudflare 这种能不能直接过”
- “加个代理 / 加重试 / 开 real_chrome 是不是就好了”
- “fetcher tier / which fetcher / headless or not / still blocked”

### 与相邻 skill 的区分

- 与 `anti-bot-triage-and-human-parity` 的区别：本 skill 是**选档位 + 判能力边界**，在“还没被拦”或“刚开始评估”时用；后者是**已经被拦截之后**按响应信号做分诊与人类行为一致性排查。若用户已在讨论“拦截页长什么样、返回码/挑战类型”，走后者。
- 与 `data-path-cost-ladder` 的区别：本 skill 处在“已决定要用哪类取数方式（请求库 / 浏览器）”之后，回答**具体用哪一档、本工具能否闭环**；成本/数据路径的先后取舍由后者决定。
- 与“整站爬取框架选型”类问题的区别：本 skill 只用规模对照表做一次判停（单页形态 vs 整站形态），不做 Spider 内部设计。

## E — 可执行步骤 (Execution)

1. **拆两轴，先写判据**
   - 动作: 分别回答“数据是否必须 JS 渲染才能拿到”（看禁用 JS 后的响应体）与“当前是否已被检测”（看状态码、响应体是否为挑战页、字段是否为空壳）。
   - 完成标准: 两轴的答案都落到二值（是/否），并写出各自证据（哪一页、哪个响应特征）。

2. **按两轴落格定档**
   - 完成标准: 明确落到“静态可解 / 必须渲染 / 渲染且被拦”之一，并给出对应档位（请求库 / 渲染档 / 隐身档）。
   - 判停条件: 若两轴均为“否”，直接用请求库档，跳到步骤 6；不要因为“以后可能需要”就上浏览器。

3. **能力边界体检（命中即判停）**
   - 动作: 对拦截方与需求逐条对照三项边界：①是否只要解析不要请求；②拦截方是否属“无原生绕过方案”的企业级反爬；③是否需要自定义 DNS、HTTP/2 帧、TLS 套件等精细控制。
   - 完成标准: 三条各自给出“命中/未命中”，命中项写明替代路径（parser 模块 / 第三方求解服务或换源降频 / httpx、curl_cffi）。
   - 判停条件: 任一命中 → 停止升档尝试，输出“本工具无法闭环 + 替代路径”，跳到步骤 6。

4. **仅在“必须渲染但未被拦”时选渲染档**
   - 完成标准: 说明选渲染档的理由是“需要渲染/交互”，而不是“想更隐蔽”；若需要隐蔽则直接进隐身档并在步骤 3 已确认拦截方有原生手段。

5. **规模体检**
   - 动作: 判断任务是单页还是整站（是否需要跟踪链接、深度、去重、断点续爬、并发）。
   - 完成标准: 单页形态 → 用单页档；整站 → 换整站框架形态。
   - 判停条件: 若任务需要整站能力而当前形态不支持，判停并换形态，不要靠外层脚本硬凑。

6. **给出结论与停止条件**
   - 完成标准: 输出三段——选定的档位及理由、被排除的档位及理由、明确的停止条件（何种现象出现即判定失败并转替代路径，而不是继续升档/加重试）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目标只要解析 HTML（已有响应体/本地文件），不需要发请求——直接用解析模块，本 skill 的档位讨论无意义。
- 需要精细 HTTP 控制（自定义 DNS、HTTP/2 帧、TLS 套件）——这类需求本就该用 httpx / curl_cffi，不是档位选择问题。
- 还没有任何目标站信息（不知道是否 JS 渲染、不知道是否被拦）——先做一次探测拿到两轴证据，否则会退化成猜档位。
- 用户问的是“拦截之后怎么排查信号/行为一致性”——那是 `anti-bot-triage-and-human-parity` 的战场。

### 作者在书中警告的失败模式

- 把档位当速度阶梯：文档自述渲染档“在底层隐形技术上几乎没有改进”（p8），两档差异在反检测与灵活性（p25）——因此“被拦就升一档”是无效动作。
- 把厂商自述当承诺：p7 的“确认开启solve_cloudflare=True，非 Cloudflare 防护站点无原生绕过能力”与 p2 的“轻松绕过Cloudflare所有类型的Turnstile/Interstital”口径冲突，后者会快速过期；判断时以限制条款为准。
- 用整站工具形态反推单页档位的“能力更强”：p113 的 ❌ 列（跟踪、深度、规则、去重、并发、断点续爬）说明两者是不同形态，不能互替。

### 作者的盲点 / 时代局限

- **全书无成本量化**：内存、耗时、失败率一概没有，p123 只有“速度 ⭐⭐⭐ / ⭐⭐ / ⭐”一栏；不得替文档编造成本模型或 SLA。隐身档“每请求一个浏览器实例量级”的开销是常识推断，不是文档结论。
- **无失效检测与降级机制**：文档没有“何时判定隐身失效、如何回归”的内容；本 skill 步骤 6 的停止条件必须自建，不能声称来自文档。
- **反爬是军备竞赛**：p2 的“绕过 Cloudflare 所有类型”在 2026 年已高度可疑，主流厂商转向行为指纹与设备证明；任何“原生可过”的结论都应带时效标注。
- **合规被降格为开关**：robots.txt 被写成可选标志。本 skill **仅限自有系统、已授权目标或公开测试环境**；不用于绕过目标站 ToS、不用于未授权抓取。

### 容易混淆的邻近方法论

- 与 `anti-bot-triage-and-human-parity`：本 skill 判“该用哪档、能否闭环”；后者做“被拦后的信号分诊”。
- 与 `data-path-cost-ladder`：本 skill 在“取数方式已定”之后做档位细化；后者做更上游的成本路径取舍。
- 与“反爬升级路径”（本书不足以支撑的独立方法论）：文档在该处只有开关名与两个经验并发数字（单 IP ≤10、代理池 50–100），只能作参数附录，不能据此拼出升级路线。
