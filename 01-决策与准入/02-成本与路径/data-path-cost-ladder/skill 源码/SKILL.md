# 取数路径成本阶梯

## R — 原文 (Reading)

> 尤其是在面对埋藏很深或格式不友好的数据时，千万不要不经思考就写代码，一定要三思而后行。如果你确定自己不能另辟蹊径，那么本章其余的内容就是为你准备的。
>
> — 瑞安·米切尔，《Python网络爬虫权威指南（第2版）》第2章 2.1，p.14

> 该AJAX 爬虫提供的抽取国家（或地区）信息的方法，比第2 章中介绍的传统的逐页抓取方式更简单。这其实是一个日常经验：依赖于AJAX 的网站虽然乍看起来更加复杂，但是其结构促使数据和表现层分离，因此我们在抽取数据时会更加容易。如果你发现一个网站拥有类似该示例站点的开放应用程序接口（API），那么你就可以只抓取其API，而无须再使用CSS 选择器和XPath 加载HTML 中的数据了。

## I — 方法论骨架 (Interpretation)

拿到一个"要抓这个站"的需求时，先不要问"选择器怎么写"，而要问"这条数据还有没有更便宜的入口"。

这条阶梯按"自己承担的成本"从低到高排：最便宜的是让别人替你换一份页面（打印版、移动版）；其次是数据根本不在 DOM 里而在 JS 文件或内嵌变量里，直接读源码；再其次是信息已经在 URL 里（slug、查询参数），解析路径比抓正文更短；再往下才是换一个数据源；然后是承认页面有多个版本，改请求头让服务器主动返回更易抓的那一份；再往后是页面自己正在调用的那条 JSON 接口——它不需要文档，按请求记录就能重放；最贵的是启动真实浏览器执行 JS，它会把跟踪、广告、字体全部加载一遍。

关键不是记住七级，而是记住两条判据：一是"页面能显示数据，就一定有一条它自己用的数据通道，先找那条通道"；二是"用了 JS 不等于传统工具失效"——JS 只做两件事，生成 HTML 或发出 HTTP 请求，产物仍然可以被静态解析。

只有在阶梯全部走完仍不可行时，才回到写解析器或上浏览器；这时候你已经知道自己在为什么付钱。

## A1 — 书中的应用 (Past Application)

### 案例 1: 地址藏在谷歌地图的 JS 里
- **问题**: 作者要把网站上的街道地址整理成格式整洁的数组，但地址以经纬度形式出现在内嵌的谷歌地图里，页面结构里不好取。
- **方法论的使用**: 按阶梯先看"数据是不是根本不在渲染后的 DOM 里"，转而打开网页加载的 JavaScript 文件，发现里面有每个地址的标记点（p.14）。
- **结论**: 直接读 JS 源文件比解析 DOM 省事，属于阶梯的低成本一格。
- **结果**: 成功把坐标整理成数组，没有动用浏览器自动化。

### 案例 2: 《纽约时报》搜索结果的内部接口
- **问题**: 用 urllib 或 requests 抓 NYT 搜索页，页面里没有任何搜索结果——结果由一次独立的 API 调用加载。
- **方法论的使用**: 识别出页面自用的 JSON 端点后，直接请求该 API，而不是渲染整页。
- **结论**: Selenium 加载同一页面要发起 100 次请求、每次搜索传输 600~700KB；直接调 API 只发 1 次请求、约 60KB 格式良好的数据（p.159）。
- **结果**: 用一次请求拿到了同样的结果，成本差两个数量级；这也成了全书"浏览器兜底"的核心证据。

### 案例 3: 用请求头让对方给你一份更好抓的页面
- **问题**: 同一份内容，站点按语言或设备返回不同版本，默认版本广告与脚本多、结构复杂。
- **方法论的使用**: 把"请求头"当成内容开关而不是伪装手段：改 Accept-Language 拿到另一语言版本，改移动端 User-Agent 拿到无广告、无 Flash 的简化版（p.188–189）。
- **结论**: 服务器愿意主动给你一份更易解析的 HTML，成本远低于解析复杂版。
- **结果**: 作者用 iPhone 的 UA 抓到了"更容易抓取的网站"，并把这条写进了请求头一节。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新接一个站点，准备直接写 `find_all`/XPath，或已经打开 Selenium，但还没确认有没有更轻的入口。
2. 抓到的页面是空白、缺字段、或和浏览器里看到的不一样，怀疑"是不是要执行 JS"。
3. 页面能正常显示数据，但 Network 面板里请求很多，不知道哪一条才是数据源。
4. 官方 API 有配额限制，网页端却有全量列表，需要在几条路径之间分工。
5. 同一页面有语言版/移动版/打印版，纠结该抓哪一份、要不要为此改请求头。

### 语言信号 (用户的话里出现这些就应激活)

- "这个站要不要上 Selenium / 无头浏览器？"
- "页面能打开，但 requests 抓下来是空的"
- "有没有 API 可以直接调？/ 内部接口在哪？"
- "View Source 里没有数据，是不是必须渲染？"
- "dynamic content / API first / cheapest path / do I need a headless browser"

### 与相邻 skill 的区分

- 与 `scrape-preflight-and-entry-ladder`（《用 Python 写网络爬虫》）的区别: 那个是动手前的尽调与合规闸门，输出 go/no-go；本 skill 是"已经决定要抓"之后的路径排序，输出选哪条路。
- 与 `page-owned-api-recon` 的区别: 那个专做"页面自用接口"的侦察与五要素归档；本 skill 负责在阶梯上决定"要不要走到那一级"，以及走到那一级之前先试哪些更便宜的。
- 与 `semantic-selector-robustness` 的区别: 那个解决"已经确定要解析 HTML，选择器怎么写才不脆"；本 skill 解决"要不要解析 HTML"。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行:

1. **先问这条数据的"另一份"是否存在**
   - 完成标准: 已明确检查打印版/移动版/语言版、URL slug、站点是否另有列表页或 RSS/sitemap。
   - 判停条件: 若存在明显更易抓的版本，直接采用并跳到步骤 6 记录。

2. **判断数据是否真的在 DOM 里**
   - 完成标准: 用"关掉 JS 再看一次"或对比 View Source 与渲染后 DOM，给出结论：静态 HTML / 内嵌 script 变量 / XHR / 其他通道。
   - 判停条件: 若数据在静态 HTML 里，直接进入步骤 6；若在内嵌 JSON（如 `window.__INITIAL_STATE__`、JSON-LD、`data-*`），静态解析后进入步骤 6。

3. **在 Network 面板筛出页面自用的那条数据请求**
   - 完成标准: 找到并记录方法、路径与参数、请求头、cookie、响应字段五要素，能在命令行里独立重放一次并拿到同结构数据。
   - 判停条件: 若能重放且无签名/鉴权门槛，采用该接口并跳到步骤 6；若带 sign/timestamp/nonce 或响应加密，记下缺口后进入步骤 4/5。

4. **评估换源与请求头降级**
   - 完成标准: 写出两条备选——"换一个数据源"与"改 Accept-Language/移动端 UA 拿简化版"，各标注预期收益与风险（是否属于规避行为）。

5. **最后才评估浏览器执行**
   - 完成标准: 明确说清"为什么前四级都不可行"，并给出浏览器方案的请求量/流量估算（对照"1 次请求 60KB vs 100 次请求 600–700KB"这一量级）。
   - 判停条件: 若浏览器方案的成本高于缩小抓取范围或直接放弃，应停止并把结论交回需求方。

6. **固化结论**
   - 完成标准: 输出一张路径表：主路径、备用路径、每级的触发条件与失败信号，供后续 skill 直接接手。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目标数据必须登录、必须绕过密码/验证码/技术措施才能看到: 这不是路径选择问题，而是授权问题，应转 `scraping-compliance-layering`。
- 路径已定、只差选择器或 XPath 写法: 直接用 `semantic-selector-robustness`，再走阶梯只会拖慢。
- 已经被封禁或返回 403，需要判断是渲染、参数、会话还是身份问题: 转 `anti-bot-triage-and-human-parity`。

### 作者在书中警告的失败模式

- 不经思考直接写 `find_all('table')[4].find_all('tr')[2]...` 这类位置链: 网站稍作修改就失效，甚至毁掉整个爬虫（p.13–14）。
- 把浏览器当第一选择: 作者明确说 Selenium 是"利器但不是首选"，因为资源加载与流量成本高出一个数量级以上（p.158–159）。
- 把"请求头降级"当成无风险的便利: 作者自己也只把它写成"更容易抓取"，未讨论这在现代风控下是否已属于规避行为。

### 作者的盲点 / 时代局限

- 本书成书于 2017–2018（英文原版 2018，中文版 2019）。浏览器兜底默认写的是 PhantomJS，而 PhantomJS 已于 2018 年 3 月停止维护；今天应改用 Playwright/Puppeteer/CDP，并把"无头检测"计入成本。
- "内部无文档 API 裸奔可长期调用"的假设已过期: 现代接口普遍带 sign/timestamp/nonce、CSRF token、响应加密与 TLS 指纹风控；阶梯的排序仍成立，但每一级的"可行性判断"必须按现代加固重估。
- "改 UA 拿简化版"在指纹层风控下不再稳定，且书中把它当"便利"，未把它当作伦理/合规问题处理（BOOK_OVERVIEW 批判段已指出这一点）。
- 书中没有覆盖 WebSocket、GraphQL、移动端 App 接口等现代取数通道；遇到这些，"页面自用通道"的判断逻辑可迁移，但具体做法需另行补课。

### 容易混淆的邻近方法论

- "有 API 就用 API"是口号，不是本方法论；本方法论的价值在于**排序**与**每级的降级动作**。
- "动态页面就上 Selenium"是常识版本，本方法论恰恰要先用静态手段把动态页面拆掉。
