# 逆向投入的成本阶梯与换载体

## R — 原文 (Reading)

> 这里毕竟是爬虫开发，以模拟和分析加密参数为主，完成数据采集即可。因为在大多数时候为了一个参数分析so 文件实在不划算，不如直接通过hook 工具进行调用。
>
> — 李玺, 第6章「Android 逆向」章首, PAGE 185

---

## I — 方法论骨架 (Interpretation)

逆向不是一条"越深越好"的路，它有终点：参数能在本地稳定重算，数据能持续拿到。终点是工程指标，不是"读懂算法"。

于是每一级手段都要同时配两样东西：一个成本，一个退出条件。

**换载体最便宜。** 同一份数据往往 H5、小程序、App 三端都有；小程序是 JS，能读代码就能复写签名。App 打不动时转小程序，作者把它写成正式策略，不是妥协。

**拦截次之。** 用自动化触发请求 + 代理正则取参，不需要理解算法。

**RPC 再次。** 把目标方法暴露成本地接口，不追代码逻辑、不补浏览器环境也能调用；代价是要有常驻的设备或浏览器进程。

**复写/补环境再次。** 能跑原码就不手抄算法；跑不起来的成本在环境，不在算法。

**脱壳/Unidbg 最贵。** 它解决的是"代码看不见"，不是"参数算不出"；能读到关键代码就不脱壳，能 Unidbg 就不装 App，能 Hook 就不逆 so。

真正要回答的不是"我会不会"，而是"这一级要花几天、失败了退到哪一级"。

## A1 — 书中的应用 (Past Application)

### 案例 1：微博登录——六个参数，改用 RPC 一次拿全（案例已过期，仅演示流程）
- **问题**: 登录接口有 pcid、su、rsakv、sp 等加密参数，按正常流程要逐个分析逆向，"比较浪费时间和精力"。
- **方法论的使用**: 先搜 rsakv 定位到代码，确认 sp 是对密码加密的结果；但不再继续啃 sp 的算法，改为在 JS 里注入 WebSocket 客户端、本地起服务接收参数。
- **结论**: 不理解 sp，也能拿到 su、rsakv、sp 全部参数——RPC 是这条阶梯上更便宜的一级。
- **结果**: 本地服务收到完整表单数据（第3章 3.9.1，PAGE 93–98）。

### 案例 2：脱壳"够用即止"（案例已过期，仅演示流程）
- **问题**: App 有加固，是否要追求完整脱壳与修复。
- **方法论的使用**: 先明确需求是"分析源码中的加密参数"，因此只有当反编译工具拿不到关键代码时才需要脱壳。
- **结论**: "脱壳后只要能获取关键的Dex 文件即可，不需要完美的脱壳和修复"——把目标从"可回编译工程"降到"能读到关键代码"。
- **结果**: 大量本可跳过的脱壳修复工作被砍掉（第6章 6.6，PAGE 251）。

### 案例 3：先拿数据，再研究加密（案例已过期，仅演示流程）
- **问题**: 刚入门时面对加密参数容易卡死，迟迟没有产出。
- **方法论的使用**: 把"数据到手"排在"理解加密"之前。
- **结论**: "所有的采集任务终究是为了得到数据，可以先完成任务，再花时间来研究那些需要耗时费力的加密参数及请求协议。"
- **结果**: 自动化工具被定位为"退而求其次"但不失败的方案，先出量再优化（第4章章首，PAGE 127）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 预算明确（几天、一个人），要决定投哪条路，而不是"能做就做"。
2. 同一份数据在 H5 / 小程序 / App 三端都有，App 还有加固。
3. 已经在某一级卡了几个小时，不知道该继续还是退。
4. 团队要评估"值不值得做这套逆向"，需要给出一条有退出条件的路线。
5. 有人在问 RPC、Unidbg、脱壳三者先上哪个。

### 语言信号 (用户的话里出现这些就应激活)

- "要不要脱壳 / should I unpack / 值得脱壳吗"
- "值不值得逆 / worth reversing / 投入产出"
- "先上线还是先逆 / ship first or reverse first"
- "有没有更快的办法 / cheaper path / cheaper route"
- "RPC 还是 Unidbg / Frida 还是 Unidbg"
- "换小程序 / switch to the mini program / 三端都有"

### 与相邻 skill 的区分

- 与 `js-param-locate-ladder` 的区别: 后者回答"下一步试哪种定位手段"；本 skill 回答"要不要在这条路上继续花时间"。
- 与 `native-hook-or-unidbg` 的区别: 本 skill 决定"要不要走到 native 层"；后者是走到 native 层之后的二选一。
- 与 `android-unpack-gate` 的区别: 后者是"怎么脱、脱到什么程度"；本 skill 是"要不要脱"。
- 与 `captcha-cost-routing` 的区别: 同一个成本公式，但对象是人机验证，不是加密参数。

## E — 可执行步骤 (Execution)

1. **写下终点，而不是手段**
   - 完成标准: 一句话说明"参数可本地重算 + 日均可采 N 条 + 允许的失败率"，不写"读懂算法/还原 so"。

2. **盘载体**
   - 完成标准: 列出 H5 / 小程序 / App / 开放接口 / 第三方数据源，逐项标注"是否同源同接口"。
   - 判停条件: 任一低门槛载体同源 → 直接在该载体上做，停，不再往下排。

3. **盘数据量与调用形态**
   - 完成标准: 估算日请求量，判定是"少量调用"（RPC 够用）还是"高频批量"（必须本地重算）。

4. **从最低一级试，每级写退出条件**
   - 完成标准: 每级写明"投入上限（小时）+ 失败后退到哪一级 + 升级的触发信号"。
   - 判停条件: 触到上限且当前级已能交付可用数据 → 停在当前级，用当前级交付，不升级。

5. **交付并留下决策记录**
   - 完成标准: 记录"用了哪一级、为什么没继续、下次升级的触发条件"，供回归时复用。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性取数、几个请求就够——写死脚本或人工更省，不需要排序。
- 数据本身不允许采（授权、robots、ToS、个人信息）——此时成本最低的一级是"不做"，排序无意义。
- 只缺某一级的操作细节（怎么补环境、怎么 Hook、怎么脱壳）——那是各分支 skill 的职责。
- 已经确定只有 native 且调用量极小——直接按 RPC 走，不必再走一遍阶梯。

### 作者在书中警告的失败模式

- "案例终会过期……技术更新迭代很快，尽信书不如无书"（PAGE 6）——阶梯是流程，不是配方。
- "逆向工作本身就很看运气"（PAGE 58）——运气说不能替代退出条件；把"再试一天"当成策略就是没有策略。
- 为单个参数死磕 so："为了一个参数分析so 文件实在不划算"（PAGE 185）。

### 作者的盲点 / 时代局限

- 阶梯里几乎**没有"合法渠道"这一级**：官方 API、数据合作、授权 RPA 未被列为候选，而它们常常是成本最低的一级（BOOK_OVERVIEW 批判段）。
- 缺少"回归成本"项：字段漂移、签名版本升级、灰度带来的重做成本没有被计入总账，书里只有"案例会过期"的免责。
- 工具与环境假设偏 Windows、偏国内大厂，对同等级对抗（银行、政务、航空）没有可迁移的成本估计。
- 未量化封禁与养号成本，导致"绕过成功"被默认等同于"可持续采集"。

### 容易混淆的邻近方法论

- `native-hook-or-unidbg`——同一层内部的二选一，不是全局排序。
- 一般的"技术选型/ROI 评估"——本 skill 的排序有明确的内容偏好（越专业越后置），不是通用 ROI 模型。

### 合规红线

仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
