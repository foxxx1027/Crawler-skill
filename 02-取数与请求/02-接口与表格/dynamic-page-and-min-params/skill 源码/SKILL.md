# 动态页判档与参数最小集

## R — 原文 (Reading)

> 这是为什么呢？可以发现当在网页内向下滑动鼠标滚轮时图片是动态刷新出来的，也就是说，该网页并不是一次加载出全部资源，而是动态加载资源。
>
> — 郑秋生、夏敏捷, 第6章 6.4.2 分析网页的 JSON 数据, PAGE 143

---

## I — 方法论骨架 (Interpretation)

1. **它解决的是误诊，不是解析**：解析结果为空、只有 logo、条数远少于肉眼所见时，先分清是"取数路线走错了"还是"被站点拦住了"。两者处置完全不同，混在一起就会去改选择器或换 UA，越改越远。
2. **判据用行为，不用技术栈**：不问"这站是不是 React/Vue"，只问三件事——查看源代码能否搜到目标数据、滚动/翻页时新内容是否继续出现、解析到的节点数是否远少于肉眼所见。三条同时指向"数据由 JS 异步取回"，就是动态页。
3. **同一页面可以有两档**：前 10 条静态注入、后续走 XHR 很常见。所以"源码里能搜到前 10 条"不能判成静态站，要看你到底要多少条。
4. **判档之后的第一步是定位，不是动手写**：Network 面板清空 → 只触发一次加载动作 → 用 XHR/JS 过滤 → 在 Preview 里找目标数组（如 all_items）→ 再从 Headers 抄地址。找到 JSON 就不必再解析 HTML，也不必上浏览器。
5. **拿到地址后的第一动作是删参数，不是加请求头**：一次只删一个参数并重放，仍返回 200 且结构不变的删掉，失败的就恢复并记为必要。终止条件是"删了也不影响返回"，不是"看起来像必要参数"。
6. **排序决定效率**：把"参数集合不对"排在"身份不对"之前。403 常见于多带了游标/会话标识/调试标记，或服务端校验参数集合；删到最小仍 403，才进入身份、Cookie、签名层。
7. **最小集还有两个副产品**：请求越短越容易看出哪个参数控制分页（start/len/offset），也越容易发现哪些参数是运行时动态值（下一单元建表时要用）。
8. **交接**：判为动态页且最小集稳定后，分页交给 `pagination-acceptance`，多接口时序交给 `api-table-replication`。

## A1 — 书中的应用 (Past Application)

### 案例 1: 搜狗图片瀑布流——先只解析到 Logo
- **问题**: 按常规做法抓页面，`find_all` 只拿到 Logo 与空 img，目标图片一张没有；作者一度以为页面结构变了。
- **方法论的使用**: 先做行为判档——页面滚动还在出新图、查看源代码又搜不到图片地址，判为动态页；转 F12 → Network → XHR → Preview，在 JSON 的 `all_items` 里确认每个元素都指向一张图，再从 Headers 抄下 `getAllRecomPicByTag.jsp` 的完整地址，逐个删参数重放。
- **结论**: 数据不在首屏 HTML，选择器再精确也只能匹配到不存在的节点；应改请求那条 JSON 接口。
- **结果**: 用一条接口替代整页解析，按 `start`/`len` 递增翻页取图。作者把这次误判如实写进了正文："此时发现输出内容并不包含想要的图片元素，而是只剖析到Logo（见图6-3）的 img,这显然不是大家想要的。"（PAGE 144）

### 案例 2: 百度翻译——连判档都不用
- **问题**: 要做中英互译的小工具，纠结该不该抓包、该不该分析页面。
- **方法论的使用**: 先查"有没有官方文档"这一更高一级的条件——有，就按文档拼 `query/from/to/appid/salt/sign`，用 md5 复算签名，直接要 JSON。
- **结论**: 有文档时，"动态页还是静态页"这个问题根本不存在，判档可整段跳过。
- **结果**: JSON 解析后回填 Tkinter 输入框，双向翻译可用。原文："按照百度翻译开放平台文档中的要求，生成URL请求网页，提交后可返回JSON 数据格式的翻译结果，再将得到的JSON格式的翻译结果解析出来。"（PAGE 96–97）代价是 appid 与密钥直接写在源码里（PAGE 104–105），属于错误的密钥管理。

### 案例 3: 豆瓣正在上映列表——源码搜得到，就是静态档
- **问题**: 同一本书第20章又抓豆瓣列表，需要片名与电影 ID，看起来同样"页面有、源码空"。
- **方法论的使用**: 先看源码承载层：`div#nowplaying` → `li.list-item`，`data-subject` 属性是电影 ID、`img.alt` 是片名，两者都在静态 HTML 里；判档结论是静态，不需要 XHR。
- **结论**: 判据落在"源码里有没有"，而不是"页面看起来是不是动态"。原文："从该图中可以看到在 data-subject 属性里面放了电影的 ID 号,而在img 标签的 alt 属性里面放了电影的名字"（PAGE 403）
- **结果**: `find_all` 直接得到 19 条 id/name。反面对照在同一章：评论抓取用裸 `urlopen`、无 UA、无异常分支（PAGE 402），页面为空也继续往下清洗并画词云——正是本 skill 要防的"把空页当成页面无数据"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 抓下来的页面是空的、只有 logo/占位图，或解析出的条数远少于浏览器里肉眼可见的数量。
2. 页面滚动、下拉或翻页还能继续出新内容，但脚本只拿到首屏那一批。
3. 把浏览器里那条 XHR 的完整 URL 拷进脚本，返回 403/400，加 UA、加 Referer 都不管用。
4. 拿到一条能跑通的接口 URL，参数一长串，不知道哪些能删、哪个参数控制分页。
5. 同一页面"源码里能搜到前 10 条"，纠结这站到底算静态还是动态、要不要写 XHR。

### 语言信号 (用户的话里出现这些就应激活)

- "抓下来是空的，是不是被封了？"
- "只抓到 logo / 占位图，图片一张都没有"
- "浏览器里滚动还能加载，脚本只拿到首屏"
- "这条接口在浏览器里能用，拷进脚本就 403"
- "这串参数能不能删掉几个？哪个是分页用的？"
- "page returns only the logo / placeholder images"
- "content loads on scroll but my script only gets the first batch"
- "the XHR returns 403 in my script but 200 in the browser"
- "which query parameters are actually required"
- "is this a dynamic page or am I being blocked"

### 与相邻 skill 的区分

- 与 `data-path-cost-ladder` 的区别: 后者铺整条成本阶梯（打印版/移动版/slug/换源/请求头/JSON/浏览器）并决定走哪一档；本 skill 只做"源码判档 → XHR 定位 → 删参数到最小"这一档的工序，外加两条误判签名。
- 与 `page-owned-api-recon` 的区别: 后者负责"找到页面自己用的那条接口"并把五要素归档；本 skill 负责"找到之后怎么减到最小、怎么确认它真的可用"。
- 与 `semantic-selector-robustness` 的区别: 后者解决"确定要解析 HTML 时，选择器怎么写才不脆"；本 skill 先判断"该不该解析 HTML"。
- 与 `anti-bot-triage-and-human-parity` 的区别: 后者在确认确实被拦之后按渲染/参数/会话/身份/交互分层诊断；本 skill 的 403 处置只到"先删参数"，删完仍 403 才转过去。
- 与 `http-request-replication` 的区别: 后者解决"这条请求为什么重放不出来"（头、体、会话、编码）；本 skill 解决"请求能跑，但不知道哪些参数必要"，只做减法和稳定性验收。
- 与 `requirements-first-data-model` 的区别: 后者先定"要哪些字段、唯一键是什么"；本 skill 回答"这条链路能不能取到数据"。字段需求应在判档之前确定，取数成功后再按需求落地。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先固定"预期 vs 实得"的差异证据**
   - 完成标准: 写下三个数——浏览器里肉眼可见条数、脚本解析到的节点数、HTTP 状态码；截图或原始响应片段留档。
   - 判停条件: 若状态码为 401/403 且脚本一条都没拿到，仍先走步骤 4 的删参数（参数集合优先于身份判断），不要直接跳到反爬分诊。

2. **按行为判档，答完三问**
   - 完成标准: 分别回答"查看源代码能否搜到目标数据""滚动/翻页是否继续出新内容""节点数是否远少于肉眼所见"，给出静态/动态/混合（前后两档）结论。
   - 判停条件: 若目标数据在静态 HTML 里，转到 `semantic-selector-robustness` 处理选择器，并记录"静态档"结论后结束；若是混合档，先确认需要多少条再决定是否继续。

3. **在 Network 面板定位那条 JSON 请求**
   - 完成标准: 清空面板 → 只触发一次加载动作 → 用 XHR/JS 过滤 → 在 Preview 里找到目标数组，并记录地址、方法、参数、返回结构。
   - 判停条件: 若整页只有一个巨型 HTML 响应、没有任何 JSON，说明这一档不成立，转 `data-path-cost-ladder` 试其他档（内嵌变量、slug、换源）。

4. **逐个删参数，直到删不动**
   - 完成标准: 每个参数都有一条"删过 / 重放 / 返回是否 200 且结构不变"的记录；最终留下最小必要集，并标出控制分页的那个参数。
   - 判停条件: 删到只剩 1–2 个仍 403 → 停止删减，转身份/会话/签名层（`anti-bot-triage-and-human-parity`）；若发现参数是上一步返回值（ticket/uuid/时间戳），转 `api-table-replication` 标为动态参数。

5. **做稳定性验收**
   - 完成标准: 最小集连续重放 3 次，结构一致、条数与预期一致；改一次分页参数，返回的首条记录随之变化。
   - 判停条件: 条数随页号不变（每页同一批）→ 直接进入 `pagination-acceptance`，不要在此处继续调参。

6. **固化并交接**
   - 完成标准: 输出一行记录：地址 / 方法 / 最小参数 / 动态参数来源 / 返回结构 / 分页变量；静态档与动态档各写一句"为什么选这档"。
   - 判停条件: 若流程涉及多个接口按顺序调用，转 `api-table-replication` 建表。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目标数据必须登录、必须绕过密码/验证码/技术措施才能看到: 这不是判档问题而是授权问题，转 `scraping-compliance-layering`。
- 已经确认被拦（同一条最小请求在浏览器里也失败、或换网络仍 403）: 转 `anti-bot-triage-and-human-parity`，继续删参数只会浪费请求。
- 只是选择器写法问题（数据确实在源码里，只是定位表达式写错）: 用 `semantic-selector-robustness`，别把静态站误判成动态站。

### 作者在书中警告的失败模式

- 只解析 HTML 源码、拿到 Logo 就断言"页面上没有数据"，随后去调选择器、换解析库、甚至怀疑被封——全无效，因为数据根本不在首屏 HTML 里（PAGE 144）。
- 把"改 UA 就能访问"当成通用解法：换完仍 403 就认为没办法了，没有继续查 Cookie/Referer/签名/频率/行为（PAGE 102）。
- 抓到接口后整串 URL 照抄，不删参数：请求臃肿、更难看出哪个参数控制分页，也更容易被服务端的参数集合校验卡住（PAGE 144）。

### 作者的盲点与时代局限

- 项目制教材只写到"能演示"：全书无并发、无限速、无重试，唯一"节奏"是第8章随机 1–4 秒（PAGE 186），且目的是规避风控而非速率预算（PAGE 120–123、150）。
- 异常被吞：`try/except: continue` 遍布各章（PAGE 122、131、142、150），无日志、无失败队列，跑完不知道漏了多少——判档结论因此缺少可核对的证据链。
- 无日志、无请求留档：全书不打印最终请求 URL，也不记录状态码，导致"参数有没有生效"只能靠肉眼观察，正是本书第20章分页 bug 得以潜伏的原因（PAGE 407–408）。
- 平台入口已失效：第7/8章的网页版入口（PAGE 152–190）对多数账号已关闭，书中却当稳定前提；同样的"当时可跑"假设也适用于本书用到的所有第三方接口。
- 样本量极小：全书案例多为几十条数据，结论强度被高估（PAGE 407 声称"10 页""比较有参考价值"，实际约 20 条）。

### 容易混淆的邻近方法论

- "动态页就上 Selenium/无头浏览器"是常识版本；本 skill 先用源码与 XHR 把动态页拆掉，浏览器是兜底而不是起点。
- "403 就换 UA / 加 Referer / 换 IP"是单点试错；本 skill 的排序是先参数集合、后身份，删完仍失败才转分层诊断。
- "源码能搜到前 10 条 = 静态站"是误判；同一页面可以前段静态注入、后续 XHR，判档要带上"要多少条"这个前提。

### 合规红线

- 仅限自有系统、已授权目标或公开测试环境；不提供针对未授权目标的攻击配方。
- 删参数只用于减少自己请求的冗余，不得用于绕过访问控制、签名校验或付费/权限边界；遇到这类门槛应停止并交回授权方。
