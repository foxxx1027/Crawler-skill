# 无文档系统的复刻表法

## R — 原文 (Reading)

> 单击右侧的Response标签，可以看到格式如“window.QRLogin.code=200；window.QRLogin.uuid="QZNW7IsPLg==";”的内容，其中 window.QRLogin.code 代表该请求发送成功
>
> — 郑秋生、夏敏捷, 第8章 8.2.1 获取登录二维码, PAGE 170

---

## I — 方法论骨架 (Interpretation)

1. **它解决的是"先清点再写代码"**：无文档系统最容易出现的失败不是拿不到数据，而是"登录成功但列表为空，不知道断在哪一行"。表法把"能调什么"先变成可核对的清单，再动主循环。
2. **第一步不是打开 F12，是排成本**：三档由低到高——① 有没有官方出口（导出、打印、开放 API、RSS/CSV）；② 有没有现成封装库或 SDK；③ 两者皆无才抓包复刻。复刻排最后，因为它是唯一需要持续维护、且被平台入口存活绑定的档。
3. **单点入口是前置风险，不是运行期 bug**：若整张表只指向一个网页版入口，先确认该入口对当前账号开放，并预留降级路径（换客户端、换导出、放弃）。入口会关，这是设计前提。
4. **表的形式固定为一行五列**：描述 / 地址 / 方法 / 参数 / 返回值。描述写"这一步在业务上干什么"（取码、登录、拉列表），不写函数名。
5. **参数必须分两类**：静态参数（appid、首次生成后固定的 DeviceID、常量 lang）；运行时动态参数（uuid、ticket、时间戳、游标、一次性 token）。动态参数要额外标"来自哪一行的哪个字段"。
6. **表的顺序就是脚本的顺序**：按真实操作顺序排（取码 → 轮询登录 → 初始化 → 拉数据 → 写），上游返回值喂下游；顺序错的表串起来一定卡在某个 ticket 上。
7. **验收门：每行都能单独重放并返回预期结构，才允许串主循环**。做不到单独复现的动态参数行，说明上游契约还没定，必须先串通上游而不是写主循环。
8. **交接**：轮询式登录（出码—等待—换票据）交给 `qr-poll-session`；分页参数交给 `pagination-acceptance`；表里的字段选择交给 `requirements-first-data-model`。

## A1 — 书中的应用 (Past Application)

### 案例 1: 百度翻译——有文档，整张表都不用建
- **问题**: 要做中英互译小工具，需要调用一个外部翻译服务。
- **方法论的使用**: 走成本第一档——先查官方文档。文档给了地址、参数与签名规则（appid + q + salt + 密钥 → md5 32 位小写），按文档拼 URL 直接请求。
- **结论**: 有文档时不必抓包、不必建表；签名是可复算的静态规则，不是需要从流量里猜的动态参数。原文："按照百度翻译开放平台文档中的要求，生成URL请求网页，提交后可返回JSON 数据格式的翻译结果，再将得到的JSON格式的翻译结果解析出来。"（PAGE 96–97）
- **结果**: 拿到 JSON 回填界面，双向翻译可用（PAGE 96–107）。书中做错的一处：appid 与密钥直接写进源码（PAGE 104–105），示范了错误的密钥管理，迁移时应改为环境变量或配置文件。

### 案例 2: itchat——有封装库，就不要复刻协议
- **问题**: 要做微信机器人，需要登录、收消息、回消息。
- **方法论的使用**: 走成本第二档——查现成封装库。`itchat` 把"登录、按消息类型注册处理函数、收发、下载附件"收成函数，8 行左右即可跑通；没有去拆网页版协议。
- **结论**: 封装库存在时，复刻协议是负收益——维护成本高，且同样受"网页版通道是否存活"约束。原文："itchat是一个开源的微信个人账号的接口，可以使用该库进行微信网页版中的所有操作；另外还需要用到图灵机器人 API，图灵机器人是一个中文语境下的对话机器人。"（PAGE 153）
- **结果**: 私聊与群聊都能自动回复，登录态可落盘免重复扫码（PAGE 155）。代价是依赖网页版通道；第7/8章的入口后来对多数账号关闭（PAGE 152–190），这一点书中没有预警。

### 案例 3: 微信网页版——无文档才建表，但整表绑在一个入口上
- **问题**: 想自己控制登录、同步、发消息的全流程，没有开放文档，封装库也已停维护。
- **方法论的使用**: 走成本第三档——抓包建表。保留一次完整操作的全部请求，每个抄成一行五列，汇成表8-1/8-2；把 uuid、时间戳、ticket 标为动态值，注明来自上一行返回；再按"登录 → 初始化 → 同步 → 发消息"串时序。
- **结论**: 表法能成立，但前置风险已经出现：整张表只指向 wx.qq.com 一个入口，没有失效预案。原文对动态值的说明："window.QRLogin.uuid 中的内容为当前登录所需要的二维码信息，将该 uuid 传入获取二维码的URL中即可获取到二维码的图片。"（PAGE 170）
- **结果**: 流程可跑通（PAGE 168–186），但整章 39 页建立在一个后来对多数账号关闭的入口上，书中没有"入口不可用时怎么办"的分支。它只能当方法参照，不能当生产方案。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 单位内网有个只有网页版的 OA / 业务系统，要每天导出"我的待办"，没有任何接口文档。
2. 小众平台或第三方服务只在网页端/客户端提供功能，想确认"到底该抓包还是找别的出口"。
3. 已经有第三方封装库或 SDK，但不确定该不该自己抓协议、复刻一遍。
4. 已经抓了一堆请求，照着写 `requests`，串起来就 401、空列表或返回结构对不上。
5. 系统本身有导出/打印/开放 API，但用户习惯性想直接抓接口，需要先做成本判断。

### 语言信号 (用户的话里出现这些就应激活)

- "只有网页版，没有 API 文档，怎么对接？"
- "能不能直接抓它的接口？"
- "抓包看到一堆请求，不知道怎么串起来"
- "有现成的库，还要不要自己写协议？"
- "登录成功了，但后面接口一直 401 / 列表是空的"
- "web-only system, no API docs"
- "build an API table from packet capture"
- "should I just use the wrapper library / SDK"
- "undocumented internal API"
- "which request gives me the token for the next call"

### 与相邻 skill 的区分

- 与 `http-request-replication` 的区别: 后者解决"单条请求怎么重放对"（头、体、会话、编码）；本 skill 先决定"要不要复刻"，再把多条请求编成有时序、有验收门的表。
- 与 `page-owned-api-recon` 的区别: 后者面向单页的数据通道（一条接口取一页数据，找到就能用）；本 skill 面向多步有状态流程（登录态在流程中间产生并被后续每一行携带）。
- 与 `form-hidden-state-and-readback` 的区别: 后者处理单次表单提交的一次性隐藏字段与写后回读；本 skill 处理跨接口的票据传递，把"动态参数来自哪一行"写进表里，不做表单回读。
- 与 `requirements-first-data-model` 的区别: 后者先定"要抓哪些字段、表怎么建、唯一键是什么"；本 skill 定"能调哪些接口、按什么顺序调"。两者应在建表前后对齐：字段需求决定表里每行的返回值要取哪些字段。
- 与 `data-path-cost-ladder` 的区别: 后者在单页取数时铺整条路径阶梯（打印版/移动版/slug/内嵌变量/接口/浏览器）；本 skill 面向多步有状态流程，先排"文档/封装库/复刻"三档，再建有时序的表。
- 与 `semantic-selector-robustness` 的区别: 后者在"已经决定解析 HTML"时管选择器写法；本 skill 的复刻档只依赖接口返回值，不解析页面。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **按成本三档排查，先找更便宜的出口**
   - 完成标准: 三档各给出是/否与证据（导出功能截图、库名与版本、官方文档链接）。
   - 判停条件: 若有官方出口可用，直接采用并记录，结束；若有可维护的封装库/SDK，采用并记录其通道依赖后结束。

2. **做入口与准入前置检查**
   - 完成标准: 确认目标入口对当前账号开放、是否单点（是否只有一个域名/客户端）、降级路径是什么；写进风险清单。
   - 判停条件: 入口不可用或准入不确定 → 停止，不做复刻；入口单点且无降级 → 明确告知这是一次性方案，不进入长期维护。

3. **完成一次真实操作并抓全请求**
   - 完成标准: 从空白会话开始走完一次完整业务（登录 → 列表 → 翻页 → 详情 → 写操作），保留所有请求的地址、方法、参数、返回样例。
   - 判停条件: 请求数过多（超过约 20 条）或返回体整体加密/二进制不可读 → 回到步骤 1 重新评估成本，不要硬啃。

4. **一行五列成表，并给参数分类**
   - 完成标准: 每行都有 描述 / 地址 / 方法 / 参数 / 返回值；每个参数都标"静态"或"动态"，动态参数注明来源行与字段名。
   - 判停条件: 动态参数由不可复算的签名/加密生成 → 停止并转逆向类 skill（如 `js-param-locate-ladder`），本 skill 不提供绕过配方。

5. **逐行单独重放，过验收门**
   - 完成标准: 每一行用 curl 或最小脚本单独请求，返回结构与表里记录的一致；失败行逐条修复并标注原因。
   - 判停条件: 某行无法单独复现、且上游已串通仍失败 → 该行契约未定，不得进入步骤 6；回到步骤 3 补抓。

6. **按表串主循环，并分派后续**
   - 完成标准: 按表顺序跑通一次端到端流程，产物落盘；失败点能定位到具体行号。
   - 判停条件: 分页行 → 交 `pagination-acceptance`；轮询登录/状态行 → 交 `qr-poll-session`；字段落地 → 交 `requirements-first-data-model`。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 官方文档齐全、有公开 API: 直接按文档写，建表与抓包都是多余成本。
- 只需把一条已知请求重放成功: 用 `http-request-replication`，本 skill 的多行时序表在这里没有增量。
- 抓取字段与数据模型还没定: 先走 `requirements-first-data-model`，否则表建得再全也不知道每行该取哪些字段。
- 目标是绕过登录、签名校验或付费边界: 属于访问控制问题，转 `scraping-compliance-layering`；本 skill 不提供规避配方。

### 作者在书中警告的失败模式

- 整章建立在单一平台入口 wx.qq.com 上，且没有失效预案：入口一旦对部分账号关闭，全部代码不可运行（PAGE 169、152–190）。
- 表里不标动态参数的后果：uuid、时间戳、ticket 被当成固定值，串起来时卡在某一行的"参数无效"，而错误信息不指向根因（PAGE 170–173）。
- 把密钥、appid 直接写进源码（PAGE 104–105）：迁移到任何版本管理或分享场景都等于泄露；表法本身不解决凭据管理。
- 只用一次性短测确定节奏（10 个好友、12 小时、1–4 秒），把"没被限制"当成"没有约束"（PAGE 186）——这类实测结论不能写进默认配置并长期沿用。

### 作者的盲点与时代局限

- 平台入口已失效：第7/8章的网页版微信方案在成书时对多数读者已不可复现，书中仍当稳定前提（PAGE 152–190），39 页内容只能作方法参照。
- 无并发、无限速、无重试：全书单线程串行，唯一"节奏"是随机 1–4 秒且目的是规避风控（PAGE 186）；复刻出的主循环不能直接上生产。
- 异常被吞、无日志：`try/except: continue` 遍布（PAGE 122、142、150），失败不计数、不留痕，表的验收门在书里也没有被真正执行过。
- 无版本矩阵与依赖清单，第三方接口无可用性承诺：百度、图灵、搜狗/百度图片接口、MNIST 镜像都会随对方改版失效（PAGE 104、163、143–149、390–391）。
- 样本量极小：全书"实测"多为个例（10 个好友、12 小时；约 20 条评论），不足以支撑"可长期使用"的结论。

### 容易混淆的邻近方法论

- "抓包看接口，照着写 requests"是常识版本；本 skill 的差异在成本排序、静态/动态参数分离、逐行复现验收门。
- "有封装库就用库"是对的，但还要记录"库依赖哪条通道"；通道关闭时库同样失效，这不是库的问题。
- "协议复刻 = 逆向能力强"是价值误置；复刻是最后手段，多数任务的正确解是找导出功能或用现成库。

### 合规红线

- 仅限自有系统、已获授权或公开测试环境；复刻第三方私有协议涉及 ToS 与合规判断，需先取得授权。
- 不提供针对未授权目标的攻击配方，不提供绕过登录、签名、付费墙或访问控制的具体手段。
