# 03 异步会话

## 解决什么

有一类会话不是"发一个请求拿一个响应"，而是**出码 → 等人操作 → 轮询状态 → 换令牌 → 带令牌调用**。扫码登录、设备授权、支付/审批回调、长轮询同步都属于这一类。这个子类把它显式建模成状态机，而不是写成一串 sleep。

## 触发信号（用户原话）

- "扫码登录怎么自动化"
- "轮询登录状态怎么写"
- "等人工审批 / 等回调"
- "长轮询、票据、token 换来换去"
- "重试导致重复提交 / 幂等怎么保证"

## 包含的 skill

| skill | 作用 | 来源 | 何时调用 |
|---|---|---|---|
| `qr-poll-session` | 三态显式建模；探活与取数拆成两个请求；凭据固定信封随请求携带并可落盘 | Python项目案例 | 设计或排查任何"出码—等待—轮询—换令牌"流程 |

## 类内用法

单个 skill，但要点按顺序执行：

1. **先画三态**：待扫 / 已扫待确认 / 已确认（含失败与超时），每个态写明判定字段。
2. **探活与取数分离**：一个请求只问"状态变了吗"，另一个才拿数据，避免把业务副作用带进轮询。
3. **信封固定**：令牌/ticket 用固定结构随每次请求携带，并落盘以便中断后继续。
4. **重试要幂等**：同一票据的重放不应产生第二次业务动作（这是本 skill 的已知弱项，description 未突出，使用时请直接看正文 B 段）。

## 不该在这里解决

- 单次表单隐藏字段 —— 转 `02-取数与请求/01-单请求复现`。
- 有文档的一次性接口 —— 不必建模，转 `02-取数与请求/02-接口与表格`。
- 验证码识别本身 —— 转 `03-反爬对抗与逆向/02-人机验证`。
- 长跑任务的断点续跑与缓存 —— 转 `06-工程化与运行/03-缓存与复用`。

## 内容速览

- 最常见的失败不是请求写错，而是**状态没建模**：把"未确认"当"已登录"，后续所有请求都带错令牌。
- 轮询间隔应有退避，且要有终态（成功/失败/超时），不能无限轮。
- 票据落盘是刚需：扫码是人工动作，脚本重启后不应要求人再扫一次。

## 使用示例

### 示例 1：扫码登录跑定时任务
**用户说**：「网站要扫码登录，我每天定时跑一次，怎么自动化？」

**路由**：`qr-poll-session`。

**执行**：
1. **画三态**：待扫 → 已扫待确认 → 已确认（外加失败、超时）；每态写明判定字段（状态码或字段值）。
2. 出码请求拿 `qr_id` + `ticket`，**立刻落盘**。
3. **探活与取数拆开**：一个请求只问"状态变了吗"，另一个才换令牌/取数据，避免轮询带出业务副作用。
4. 轮询加退避（如 1s → 2s → 4s），到超时即终止并告警。
5. 换到令牌后用固定信封随每个请求携带。

**产出**：一个显式状态机 + 一份票据文件；脚本重启后从"已确认"继续，不需要人再扫一次。

### 示例 2：回调没来，加个 sleep
**用户说**：「审批回调一直没来，我先 `sleep 30` 再查一次，行不行？」

**路由**：仍是 `qr-poll-session`，但诊断结论是"状态没建模"，不是"等得不够久"。要把"未确认"和"已确认"分开，并补上失败/超时终态；sleep 只是退避的一种，不能替代状态判定。
