# 缓存是成本置换，不是可选项

## R — 原文 (Reading)

> 如果你需要执行一个大型爬取工作，那么它可能会由于错误或异常被中断，缓存可以帮助你无须重新爬取那些可能已经抓取过的页面。……不过，如果你的最高优先级是获得网站最新和当前的信息，那此时缓存就没有意义。
>
> — Katharine Jarmul / Richard Lawson, 第3章 3.1 何时使用缓存（PAGE 73）

> 一些URL 会被映射为相同的文件名。……这就意味着，如果其中一个URL 生成了缓存，其他3 个URL 也会被认为已经生成缓存，因为它们映射到了同一个文件名。
>
> — 同上, 第3章 3.3.5 磁盘缓存缺点（PAGE 84）

---

## I — 方法论骨架 (Interpretation)

缓存要先用两个判据决定"要不要用"，再谈"怎么实现"。

- **判据一，数据是否必须最新**：如果是，缓存没有意义——命中即读到旧值，省下的请求换来的是错误内容。
- **判据二，任务是否会中断或需要重跑**：大型抓取一定会因异常、重启、改代码而中断，缓存把"重跑几周"换成"读本地"；同时带来离线分析与降低对方负载两个副产品。
- 缓存承担三件事：**断点续跑、离线分析、降低对方负载**，加速只是其中最容易被看见的一件。
- 规模阶梯是：进程内字典 → 磁盘（URL 映射成文件名、可压缩、可设过期）→ 共享键值存储（Redis）。
- 磁盘这一级有两个结构性缺陷：**URL→文件名是有损映射**（字符替换与长度截断都不可逆，四个不同 URL 会撞成同一个文件名，命中率虚高且读到别人的内容），以及**文件数上限**（FAT32 单目录 65535、ext4 约 3100 万，而大站动辄上亿页）。
- 缓存里存的是"HTML + 状态码"，因此 **5xx 必须作废重下**；缓存里的表示形态（str 还是 bytes）必须与下游解析器的输入形态一致，否则解析环节会直接抛错。
- 换算方式始终是：`省下的请求数 × 单请求成本` 对比 `存储 + 过期风险 + 键设计错误带来的返工`。

## A1 — 书中的应用 (Past Application)

### 案例 1: 同一条爬虫，加缓存后从一分多钟到 1.1 秒

- **问题**: 反复调试选择器时，每次都要把示例站重新下载一遍，等待时间压在调试循环上。
- **方法论的使用**: 把 `download` 重构成 `Downloader` 类，在 `__call__` 里先查缓存、未命中才真正下载；限速移到"真下载"分支里，缓存命中不触发等待。之后给 `DiskCache` 加 zlib 压缩。
- **结论**: 缓存是可以在不改抓取逻辑的前提下插入的一层，且"命中不走限速"是正确语义。
- **结果**: 第一次（空缓存）下载耗时超过 1 分钟；第二次全部命中只有 **1.1 秒（约 94 倍）**；开启压缩后缓存从 416 KB 降到 156 KB，加载耗时 260 ms（PAGE 80–82）。

### 案例 2: 磁盘缓存的键是有损映射，规模一大就失效

- **问题**: 作者原本认为"把网页存成文件"是最容易想到的方案，实现后却发现同一条 URL 有时读不到自己刚写的内容。
- **方法论的使用**: 检查 `url_to_path()` 的映射规则（非法字符替换为下划线、每段截断到 255 字符），构造 `?a+b / ?a*b / ?a=b / ?a!b` 四个 URL 做对照。
- **结论**: 四个 URL 映射到同一个文件名，一条缓存被当成四条；长 URL 在第 255 字符后才不同也会撞名。即使改成哈希文件名，仍受文件系统文件数上限约束（FAT32 单目录 65535、作者的 ext4 约 3100 万）。
- **结果**: 作者判定 `DiskCache` "想要通用的话存在太多限制"，把后端换成 Redis 键值存储（PAGE 84–85）。

### 案例 3: 换 Redis 后端，加载快 3 倍以上

- **问题**: 磁盘缓存受文件系统限制，且加载要经过文件打开 + 解压 + JSON 反序列化。
- **方法论的使用**: 实现 `RedisCache`，保持与 `DiskCache` 相同的 `__getitem__/__setitem__` 接口，键=URL、值=JSON、过期用 `setex`；用同一爬虫跑两遍对比。
- **结论**: 第一次全量下载与磁盘缓存耗时基本相同，差别只在**缓存加载**这一侧。
- **结果**: 第二遍 `Wall time: 282 ms`，"与未压缩的磁盘缓存系统相比，有着超过3 倍的速度增长"（PAGE 92）。附带的代价是 Redis 存的是 bytes，取回要先 `decode` 才能进 JSON（PAGE 89）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 抓取任务预计要跑几小时到几天，中途会被重启、断网或改代码打断。
2. 同一批 URL 已经被抓过，用户在问"还要不要再抓一遍 / 能不能直接读上次的"。
3. 调试阶段反复跑同一条流水线，等待时间几乎全花在下载上。
4. 抓过一轮后，发现某些页面"明明没抓过却显示命中缓存"，或缓存目录越来越大、单目录文件数逼近上限。
5. 想要每天增量更新，但不知道"过期时间设多久"才既省请求又不读到旧数据。

### 语言信号 (用户的话里出现这些就应激活)

- "缓存 / cache / 加个缓存层"
- "抓过的还要再抓吗 / 能不能复用上次的结果"
- "重跑一遍太慢 / 断点续跑 / 中断了怎么接着跑"
- "TTL 设多久 / 过期策略 / 30 天合理吗"
- "缓存命中率 / 缓存键 / 文件名撞了 / 缓存里是旧内容"
- "ETag / Last-Modified / 304 / 条件请求"
- "磁盘缓存还是 Redis"

### 与相邻 skill 的区分

- 与 `crawl-pacing-and-concurrency` 的区别：后者算的是"每秒钟允许发多少请求"；本 skill 算的是"哪些请求可以根本不发"。两者的接缝是"缓存命中不触发限速"——限速只在真下载时生效。
- 与 `scrapy-production-setup` 的区别：JOBDIR 里的 `requests.seen` 是**URL 级去重游标**，用于中断续跑；本 skill 是**内容级缓存**（HTML + 状态码 + 过期），可以离线复用与再解析。二者常同时开，但不是同一层。
- 与 `form-hidden-state-and-readback` 的区别：后者要求 cookie jar 可序列化才能断点续跑——那是"有状态抓取"的前置条件，本 skill 只负责内容缓存本身。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **先过两个判据**
   - 明确回答："数据是否必须最新？""任务是否会被中断或需要重跑？"
   - 完成标准: 两个问题都有明确答案；两句都是"否"时给出结论"不需要缓存"。
   - **判停条件**: 若"必须实时最新" → 停止本流程，改做条件请求或直接不缓存；若"会中断/要重跑" → 继续。

2. **定失效策略（TTL 还是条件请求）**
   - 按数据变化周期分层设 TTL（如详情页 7 天、库存 1 小时、价格 15 分钟）；变化率低而存量高时优先用 `ETag` / `Last-Modified` + 304。
   - 完成标准: 每一类页面都有明确的 TTL 或条件请求方案，并写出依据（观察到的变更周期），而不是照抄"30 天"。

3. **设计缓存键**
   - 键至少包含 URL；若同一 URL 会因身份/参数返回不同内容，加入区分维度（会话标识、关键查询参数、渲染模式）。
   - 完成标准: 用 4 个"字符替换后相同"的相近 URL（如 `?a+b`、`?a*b`、`?a=b`、`?a!b`）自测，确认不会互相命中。

4. **选后端并对齐规模**
   - 单进程调试 → 内存字典；单机长期 → 磁盘（注意单目录文件数上限）；多进程/多机 → 共享键值存储（Redis / SQLite）。
   - 完成标准: 后端与"并发写者数量"匹配（有多个进程写磁盘同一目录即不合格）；预估文件数低于文件系统上限。

5. **定作废规则与表示形态**
   - 5xx 结果不参与命中、必须重下；缓存读出的类型（bytes/str）与下游解析器要求一致。
   - 完成标准: 故意让一次请求返回 500，验证下次会重新下载；用一个要求 bytes 输入的解析器跑通缓存命中路径。

6. **度量收益**
   - 记录缓存命中率、缓存加载单页耗时、省下的请求数。
   - 完成标准: 给出两个数（命中率、单页均耗时）并与"直接请求"对比。
   - **判停条件**: 若命中率很高但缓存加载耗时超过直连的一半，说明后端选错（典型是磁盘 + 解压），换共享 KV 或降低压缩。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性、不可重复的抓取（如只跑一次的促销页快照）：缓存只增加存储与键设计成本。
- 必须拿到最新状态的场景（价格监控、库存、行情）：命中缓存等于读到错误值。
- 只想要"同一 URL 不重复入队"：那是去重游标（seen/JOBDIR），不是内容缓存，用错层会既占空间又解决不了重复调度。

### 作者在书中警告的失败模式

- **缓存键不唯一**：磁盘映射会让不同 URL 撞名，"如果其中一个URL 生成了缓存，其他3 个URL 也会被认为已经生成缓存"（PAGE 84）。
- **把过期当唯一旋钮**：书中用 `timedelta(days=30)` 做默认过期，但作者自己没论证 30 天从何而来；TTL 只是"变化检测"的近似替代。
- **缓存 5xx**：书中在 `Downloader.__call__` 里专门判断 `500 <= code < 600` 时"忽略缓存结果并重新下载"，说明缓存不能只存成功页。
- **缓存形态与解析器不匹配**：统一 decode 成 str 后，需要 bytes 的 XML 解析器会直接失败（第9章 XML 分支）。

### 作者的盲点 / 时代局限

- 自建的 `DiskCache` 类与示例目录结构已过时；现代直接用 `requests-cache`（原生支持条件请求）、`diskcache`，或 SQLite/Redis 侧存储。
- 书中未讨论 `ETag` / `Last-Modified` / 304 条件请求——而这恰恰是"变化率低、存量高"场景下收益最高的一档，属于必须外推补上的缺口。
- 未讨论缓存与登录态的关系：会话过期后缓存仍在，会读到"上一个身份的页面"，这是有状态抓取特有的陷阱。

### 容易混淆的邻近方法论

- 限速（少发请求）vs 缓存（不发请求）：两者都在省对方带宽，但记账方式与失效语义完全不同。
- 去重（seen 集合）vs 缓存（内容存储）：前者保证"不重复调度"，后者保证"不重复下载"。
