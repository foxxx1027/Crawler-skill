# 抓取节奏、负载与并发委托

## R — 原文 (Reading)

> 和其他技术领域不同，网页抓取通常并不能单纯依靠“给问题增加更多的进程”来提升速度。虽然运行一个进程（process）很快，但是运行两个进程未必能将速度提升一倍。而当运行3 个进程时，可能你的所有请求都会被远程服务器封杀，因为它认为你是在恶意攻击。
>
> — 瑞安·米切尔，《Python网络爬虫权威指南（第2版）》第16章，p.206

> Throttle 类记录了每个域名上次访问的时间，如果当前时间距离上次访问时间小于指定延时，则执行睡眠操作。我们可以在每次下载之前调用throttle 对爬虫进行限速。
>
> — 凯瑟琳·雅姆尔、理查德·劳森，《用 Python 写网络爬虫（第2版）》第1章，p.26

## I — 方法论骨架 (Interpretation)

抓取的总请求数通常是固定的（要抓的页面就那么多），所以"什么时候发"是一个可以单独设计的变量，而不是越快越好。

第一步不是调参数，而是问必要性: 这些请求真的都要发吗？数据能不能在一个页面/一个接口里拿到？列表页能不能替代大量详情页？"可抓"不等于"该抓"。

第二步是把吞吐换算成对方的配额: 先看 robots/ToS 与对方允许的 QPS，把目标页数换算成所需总请求数与时间窗。单请求往返 1 秒时，单机串行 200 万页要 23 天左右；20 台机器线性叠加看着像 1.2 天，但如果对方按 IP/账号/全站限流，20 台只会把封禁提前，不会缩短工期——机器数不是自变量，对方配额才是。

第三步是用结构摊平峰值，而不是只加 sleep: 循环的嵌套顺序本身就是限速器。外层循环主题、内层循环站点，就能把"对一个站一次上万请求"摊成"十个请求、停几分钟、再来十个"。请求总数不变，峰值压力变了。

第四步是按域名记账: 每个域名记录上次访问时间，未到间隔就睡够差额——这是把"延时"变成"预算"，也是 PY 书 Throttle 类的做法。

第五步才是选并发模型: 多线程适合 I/O，多进程适合 CPU 密集；但并发数增长不是线性的，超过本机拐点后性能下降、错误率上升。因此要先测出本机拐点，再决定并发交给框架（Scrapy 的 DOWNLOAD_DELAY / AUTOTHROTTLE）还是自己控制。

一句话: 并发数与延时是同一笔预算的两个写法，先算对方配额与本机拐点，再决定怎么花。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三个进程就把请求全招来封杀
- **问题**: 想用多进程提升抓取速度，默认"进程越多越快"。
- **方法论的使用**: 作者先给出反直觉判断——网页抓取不能靠"加进程"加速；再用实测表（PY 书 500 页对比表）说明性能增长趋于对数，线程/进程加到一定数量后反而下降。
- **结论**: 运行 3 个进程时，可能所有请求都被远程服务器封杀，因为它认为你在恶意攻击（p.206）；性能拐点比"更多机器"更值得先找。
- **结果**: 作者把"先评估必要性、再配并发度与延迟"写成 Scrapy 一节的固定前置。

### 案例 2: 用循环顺序做负载均衡
- **问题**: 上百个主题 × 几十个网站，如果外层循环站点，会对每个站连续发上万个请求。
- **方法论的使用**: 把外层改成主题、内层改成站点，让每个站的请求被摊到不同时间点（p.52）。
- **结论**: 两种写法最终请求次数一样，但对单个站的峰值压力完全不同；"思考如何构建你的循环"就是最便宜的限速器。
- **结果**: 每个站变成"发 10 个请求、等几分钟、再发 10 个"，负载被均衡到时间轴上。

### 案例 3: server hammering 是不是必要
- **问题**: Scrapy 是单线程但异步发请求，速度比手写爬虫快得多，容易默认全速跑。
- **方法论的使用**: 作者在 item 管线一节插入"好公民"判断: 目标站必须处理每个请求，因此要先评估这种服务器锤击（server hammering）是否有必要，甚至是否明智——许多网站有能力也有意愿阻止它们认为的恶意抓取（p.66–67）。
- **结论**: 判断对象是"必要性"，不是"速度"；快不是充分理由。
- **结果**: 读者被要求把并发度、延迟与 AUTOTHROTTLE 当成全局参数配置，而不是每个 worker 各睡各的。

### 案例 4: Scrapy 的速率旋钮链——先核减请求，再逐个拧
- **问题**: 同一台机器、同一套 settings，单域名站吞吐上不去，CDN 下多子域站却能跑满；直觉做法是把全局并发调大。
- **方法论的使用**: 按单变量顺序动旋钮——先 `DOWNLOAD_DELAY`，再 `CONCURRENT_REQUESTS`，再看 `CONCURRENT_REQUESTS_PER_DOMAIN` / `_PER_IP`，最后才交给 `AUTOTHROTTLE_*`；每改一项回看 stats（request_count、response_status、finish_reason），而不是只看总耗时。固定延时会被摊到并发槽上（3s / 16 槽 ≈ 每 3/16 秒一发），非 200 响应返回更快会挤进更多并发，这正是需要 `RANDOMIZE_DOWNLOAD_DELAY` 打散节奏、并由 AutoThrottle 自适应刹车的因果。作者同时给 bench 划边界：本机 541 请求/10s、2400 pages/min 只是"本机 + 回环 + 不解析"的相对基线，不能外推成站点吞吐（PAGE 223–225）。
- **结论**: 实际并发 = min(TARGET_CONCURRENCY, PER_DOMAIN, PER_IP)——目标并发会被 per-domain / per-IP 截断，所以单域名站要先抬 `PER_DOMAIN`，多子域站瓶颈才回到全局上限与 CPU。"六项优化没有一项减少请求总量"：旋钮只改节奏、不改工作量，因此核减请求永远排在调参之前（PAGE 216–222、225–228）。
- **结果**: 两个站的瓶颈被分别定位到 per-domain 桶与全局上限/CPU，不再笼统地"再调大点"；也避免了把 403 直接丢给并发/重试/超时通用开关。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要为一个抓取任务定频率、并发数、线程/进程数，但没有任何依据。
2. 老板给了死线与机器数（"3 天 200 万页、20 台机器"），问够不够。
3. 已经加了 sleep 仍被封，或在考虑"加机器赶工期"。
4. 用 Scrapy/aiohttp 跑起来后速度异常、错误率上升，想知道该降还是该升。
5. 多台机器/多个进程抓同一站，发现总请求量远超预期。

### 语言信号 (用户的话里出现这些就应激活)

- "开几个线程合适 / 要不要上多进程"
- "限速设多少 / DOWNLOAD_DELAY / AUTOTHROTTLE"
- "加机器能不能更快 / 20 台够不够"
- "抓太快被封了"
- "rate limit / concurrency / QPS / throughput / 速率预算"

### 与相邻 skill 的区分

- 与 `crawler-concurrency-delegator` 的区别: 那个治理"多 worker 下的共享状态（visited/去重/通信）"；本 skill 治理"总量与节奏（发多少、隔多久、开几个）"。两者常配合，但不互相替代。
- 与 `anti-bot-triage-and-human-parity` 的区别: 那个在"已经被封"时定位是哪一层；本 skill 在"还没被封"时就把峰值压到安全区。
- 与 `scraping-compliance-layering` 的区别: 那个判断"该不该抓、能抓多少"；本 skill 把合规结论换算成具体参数。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行:

1. **先做必要性核减**
   - 完成标准: 列出可替代的取数方式（单页/接口/列表页/增量水位），给出核减后的目标请求数。
   - 判停条件: 若核减后规模已在可接受范围，直接跳到步骤 6，不必设计并发。

2. **换算对方配额**
   - 完成标准: 从 robots/ToS/实测响应中拿到允许的 QPS 或最小间隔，把总请求数换算成"所需时间窗 = 总请求数 / 允许 QPS"。

3. **测本机拐点**
   - 完成标准: 用一小批请求做阶梯测试（如 1/5/10/20 并发），记录耗时与错误率，标出性能开始下降或错误开始出现的并发数。

4. **按域名/账号记账**
   - 完成标准: 每个域名（或账号）维护"上次访问时间 + 最小间隔"，未到间隔即等待；全局预算与单机 sleep 不重复计算。

5. **决定并发归属**
   - 完成标准: 明确写出"并发交给谁"——框架全局参数（DOWNLOAD_DELAY/AUTOTHROTTLE）、自建队列 + 有限 worker、或单线程串行；并说明为什么不是另一种。
   - 判停条件: 若所需吞吐超过对方配额，停止加机器，回到步骤 1 缩范围或延长工期。

6. **设停机与告警**
   - 完成标准: 写出触发条件（连续 N 次 429/403、错误率超阈值、达到请求预算）与动作（降并发、暂停、次日续跑），并留出断点位置。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 只有几十个页面、一次性抓完: 直接串行加一个固定间隔即可，设计并发模型是过度工程。
- 还没确认"该不该抓": 先过 `scraping-compliance-layering`，否则只是把不合规的抓取做得更快。
- 目标站已明确按账号/接口/指纹限流而你又无授权提高配额: 本 skill 不能帮你"绕过"配额，只能帮你缩范围或延长工期。

### 作者在书中警告的失败模式

- "想快就多加机器": 作者用实测说明并发增长趋于对数，且 3 个进程就可能招来整体封杀（p.206）。
- 只加 `time.sleep` 就以为解决了礼貌问题: 单机 sleep 表达不了多机/多进程的全局预算，8 台 × 各自 1 QPS = 对站 8 QPS。
- 用高并发"赶工期": 作者明确说"一直被盯着看的机器人是永远不会完成任务的"，被发现后反而更慢（p.232）。

### 作者的盲点 / 时代局限

- 本书成书于 2017–2018。具体手段（time.sleep、Scrapy DOWNLOAD_DELAY/AUTOTHROTTLE、夜间跑）仍有效，但现代目标站的限流粒度已细化到账号/接口/指纹，单机 sleep 不足以表达"全局预算"；本 skill 的"按域名记账 + 中心预算"是对书中原则的现代外推。
- "90%/99% 的机器人能被简单技术挡住"是作者的经验修辞，书中无样本与测量，不应作为基线引用；同理，"加几秒 sleep 就能解决"也只是作者的个人经验。
- 书中并发章节止于 threading/multiprocessing/Queue，未覆盖 asyncio + aiohttp、分布式速率预算（Redis 令牌桶）、自适应限速（按 429 响应动态调整）等现代做法。
- 分布式执行一句"超出本书范围"带过，因此缺少任务持久化、租约、监控告警等生产件；工期与机器数的换算必须自己补。

### 容易混淆的邻近方法论

- "礼貌 = 加个 sleep"是常识版本；本方法论的区别是把循环结构、域名记账、并发度、时段四件事当成同一个预算的四个旋钮。
- "并发越高越容易被封"不等于"并发无用": I/O 等待期的并发仍然有效，关键是总速率不超配额。
