# 遍历范围与停机条件

## R — 原文 (Reading)

> 为了避免一个页面被抓取两次，链接去重是非常重要的。在代码运行时，要把已发现的所有链接都放到一起，并保存在方便查询的集合（set）里。
>
> — 瑞安·米切尔，《Python网络爬虫权威指南（第2版）》，第3章，p.33

> 我曾经遇到过一个网站，该网站根据当前网页的地址生成新的URL 链接。这就导致了像blogs/blogs.../blogs/blog-post.php 这样不断重复的路径。
>
> — 同上，第3章，p.34

> 在你编写爬虫跟随外链跳转之前，请问自己几个问题。
>
> — 同上，第3章，p.37

---

## I — 方法论骨架 (Interpretation)

爬虫跑飞不是"写得不好"，而是**没有装刹车**。这个方法论把"刹车"拆成三条必须同时成立的约束。

第一条是**去重**：所有已发现的 URL 放进一个能 O(1) 查询的集合，只有"新"链接才去抓。没有这一条，环形链接会让同一个页面被反复抓取，日志和请求量都会翻倍。

第二条是**限域**：用域名（`allowed_domains`）或 URL 正则把"允许进入的页面"写死。光有去重不够——有些站点会按当前 URL 生成新 URL（`blogs/blogs/.../blogs/post.php`），每个都是"新的"，集合永远在长，去重在这类站点上几乎失效。光有限域也不够：`allow=.*` 加上 `follow=True` 就等于"遍历整个互联网"，Scrapy 会一直跑下去。

第三条是**限深/限量**：设一个最大递归深度、最大页数或最大请求预算。Python 默认递归上限是 1000，扁平小站可能刚好够用，但这不是设计，是侥幸。

在这三条之上还有一层**范围决策**：要不要跟外链、要不要写出链发现函数，不应该由技术顺手决定，而应由"四问"决定——数据能否靠预定义站点拿到？到站后是深入还是跳走？有没有不想抓的类型（如非目标语言）？如何避免法律责任？四问的答案直接映射到"写不写内外链函数"。

最后是**停机条件**：正常结束（队列空、到达深度上限、连续 N 页无新内容）和异常结束（403/封禁、请求预算耗尽）都要显式定义，并让程序能退出、能告警。

## A1 — 书中的应用 (Past Application)

### 案例 1: 维基百科全站遍历——set 去重救回了指数爆炸
- **问题**: 从主页递归抓维基百科，每个页面约 10 条内链、网站深度约 5 层，理论上是 10^5 即 10 万个页面。
- **方法论的使用**: 作者引入全局 `pages = set()`，每次发现链接先查集合，不在集合里才 `add` 并递归。
- **结论**: "大部分内链都是重复的"，去重把指数级膨胀压回真实页面数。
- **结果**: 爬虫能在合理时间内遍历完整个（当时的）维基百科链接图；但作者同时提醒递归上限 1000 会让它在某个深度自动停止。

### 案例 2: 自我复制 URL 的站点——去重挡不住
- **问题**: 有一个网站会根据当前页面地址生成新的 URL，产生 `blogs/blogs.../blogs/blog-post.php` 这样无限延伸的路径。
- **方法论的使用**: 作者用这个反例说明"去重"不是万能的：每个新生成的 URL 都是集合里没有的"新链接"。
- **结论**: 必须靠深度上限或范围规则兜底，光有 set 不够。
- **结果**: 书中把它列为"罕见的例外"，并明确结论——对典型站点递归可行，对这类站点必须额外设限。

### 案例 3: Scrapy 的 `allow=.*`——框架不会替你刹车
- **问题**: 用 CrawlSpider 抓维基百科文章，只写了 `allowed_domains` 和 `Rule(LinkExtractor(allow=r'.*'), follow=True)`。
- **方法论的使用**: 作者运行后观察日志与标题，发现它不只访问文章页，还会在 `Wikipedia:General disclaimer` 这类非文章页上"漫步"。
- **结论**: 书中直接给出警告——"它不会终止（至少很长一段时间内不会终止），除非你用Ctrl-C 或者关闭终端来强行终止它"。
- **结果**: 作者改写成两条规则：一条 `^(/wiki/)((?!:).)*$` 精确匹配文章页，另一条才处理非文章页；并提醒考虑服务器负载，不要长时间运行。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **新写全站/多页爬虫**：要从一个入口页把整个站点或某个栏目抓下来，还没想清楚边界。
2. **跑飞/跑不完**：脚本跑了一夜还没结束、日志里同一个 URL 反复出现、磁盘被重复数据撑满。
3. **递归报错**：`RecursionError: maximum recursion depth exceeded`，或程序在某层突然停住。
4. **要不要跟外链**：在"只抓自己关心的站"与"顺着链接发现新站"之间犹豫。
5. **框架配置**：用 Scrapy CrawlSpider，不确定 `allowed_domains` / `allow` / `deny` / `follow` 该怎么组合才不会跑遍全网。

### 语言信号 (用户的话里出现这些就应激活)

- "怎么防止重复抓" / "爬虫停不下来" / "跑了一晚上还没完" / "递归爆了"
- "要不要跟外链" / "怎么限制只抓这个域名" / "深度限制设多少"
- "allowed_domains 怎么写" / "allow=.* 是不是会抓全站" / "CrawlSpider 一直不结束"
- "crawler never terminates" / "dedupe visited URLs" / "depth limit" / "infinite crawl" / "scope the crawler"

### 与相邻 skill 的区分

- 与 `crawl-pacing-and-concurrency` 的区别: 那个 skill 管"发多快、并发多少、总预算怎么摊"；本 skill 管"允许去哪些页面、什么时候停"。范围没定就调并发，只是在更快地跑飞。
- 与 `data-path-cost-ladder` 的区别: 那个 skill 先问"要不要爬"（能否用 API/换源/有限页面替代）；本 skill 在"确定要遍历"之后才管边界。
- 与 `crawl-pacing-and-concurrency` 的区别（多 worker 侧）: 并发场景下 visited 集合不共享会导致重复抓，属于共享状态设计；本 skill 解决"单条遍历链本身该不该继续"。
- 与 `page-owned-api-recon` 的区别: 能拿到列表接口时，遍历应改为按接口分页推进，而不是跟 HTML 链接。

## E — 可执行步骤 (Execution)

1. **先答四问，决定要不要"发现链接"**
   - 逐条回答：数据能否靠预定义站点拿到？到站后深入还是跳走？有没有不想抓的类型？如何避免法律责任？
   - 完成标准: 四问有明确答案，并据此写死"不实现外链发现 / 只实现内链发现 / 内外链都实现"三者之一。
   - 判停条件: 若答案落在"预定义站点就能拿全"，直接列出种子 URL 列表，不写递归遍历，流程结束。

2. **写死范围：域名 + URL 正则**
   - 用 `allowed_domains` 或等价的 host 校验，再加一条 URL 正则（如 `^(/wiki/)((?!:).)*$`）排除非目标页（分类页、讨论页、登录页）。
   - 完成标准: 随机抽 20 条候选链接，全部能被规则正确判定"进/不进"，且没有一条"说不清"。

3. **装去重：集合 + 规范化**
   - 已访问 URL 放入 set（或 Redis/DB 唯一索引）；入队前先做归一化（去 fragment、统一大小写、参数排序、去跟踪参数）。
   - 完成标准: 同一逻辑页面在两种 URL 写法下只入队一次。
   - 判停条件: 若站点存在"按当前 URL 生成新 URL"的特征（URL 段自我重复），直接跳到步骤 4 强制设限，不要指望去重。

4. **设停机条件（至少两条兜底）**
   - 必须同时有：最大深度或最大页数、最大请求预算；可选：连续 N 页无新内容、出现 403/验证页即退出。
   - 完成标准: 每一条都有具体数字，并写明触发后的行为（退出 / 告警 / 写断点）。
   - 判停条件: 若无法给出任何上限，视为设计未完成，不得开跑。

5. **干跑验证**
   - 用极小上限（如深度 2、页数 20）跑一遍，检查访问集合里有没有越界域名、重复 URL、非目标页。
   - 完成标准: 日志里每个 URL 都能对应到一条"为什么允许"的规则；无越界、无重复。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **目标页面是固定小集合**（几十个已知详情页）：直接维护 URL 列表，不需要遍历、去重、限深。
- **站点提供了列表接口/RSS/sitemap**：按接口游标推进比分页爬 HTML 更省、更稳，应转 `page-owned-api-recon`。
- **问题其实是"被封"而不是"跑飞"**: 403、验证页、返回空壳属于 `anti-bot-triage-and-human-parity`，加深度上限解决不了。
- **问题其实是"太慢/太猛"**: 那是节奏与并发预算，不是范围问题。

### 作者在书中警告的失败模式

- 只去重不限域、不限深——自我复制 URL 的站点会让 set 永远有新成员（p.34）。
- 只限域不设规则——Scrapy `allow=r'.*'` + `follow=True` 会遍历整站且不终止（p.61–62）。
- 依赖 Python 默认递归上限——"1000 次"是语言默认值，不是设计参数；宽度大的站点会在到达前就耗尽（p.34）。
- 跟外链前不答四问——作者的原话是"在你编写爬虫跟随外链跳转之前，请问自己几个问题"（p.37）。

### 作者的盲点 / 时代局限

- **假设"能遍历就能收敛"**: 书中把自我复制 URL 称为"罕见的例外"，但现代站点大量使用无限滚动、日历分页、筛选参数组合，URL 空间本身是组合爆炸的，深度上限只能截断、不能收敛。
- **没有增量与水位概念**: 全书没有"上次抓到哪、这次从哪继续"，重跑只能全量再抓；日更监控类任务需要自行补 lastSeen/水位。
- **框架写法已过时**: `scrapy.contrib.*` 导入路径、旧版 `Rule`/`LinkExtractor` 用法需按现代 Scrapy 改写；`allowed_domains`/`deny`/深度限制这些概念不变。
- **法律四问只到"避免责任"**: 第 18 章是美国法框架，四问中的"如何避免法律责任"在跨境、涉个人信息场景下不足以给结论，应转 `scraping-compliance-layering`。
- **无断点续爬与任务持久化**: 书中"分布式超出本书范围"，进程一挂就从头再来。
- **全书层面的时代局限**: 动态渲染默认 PhantomJS（2018 年 3 月已停止维护）；反爬手段止于 UA/限速/换 IP，未涉及 TLS 指纹与 JS challenge；法律框架为纯美国法，不覆盖 GDPR 与中国《网络安全法》《数据安全法》《个人信息保护法》。

### 容易混淆的邻近方法论

- **去重 vs 限域 vs 限深**: 三者是合取关系，不是备选；缺任一条都可能跑飞。
- **"范围" vs "节奏"**: 范围决定"去不去这个页面"，节奏决定"多快去"；两者相乘才是对服务器的总压力。
- **"停机条件" vs "异常处理"**: 停机是正常/异常退出的设计，不是 `except` 兜底；没有显式停机，异常只会表现为"卡住"。
